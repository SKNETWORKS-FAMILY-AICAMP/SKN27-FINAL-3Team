## 2. 회의 핵심 요약

이번 회의의 핵심은 구현을 바로 확정하는 것이 아니라, 구현 전에 판단 근거를 만드는 것이다.

특히 과태료·범칙금 고지서 분석, 법률 Agent 연결 여부, LangGraph 기반 Agent 흐름, API 명세서, 화면설계서는 모두 단일 모델이나 단일 의견으로 확정하지 않고 여러 모델과 사례를 비교한 뒤 결정하기로 했다.

## 5. 고지서 OCR과 법률 Agent 연결 판단

필주 담당 흐름에서 핵심 질문은 과태료·범칙금 고지서 분석 시 법률 Agent를 참조해야 하는지 여부다.

회의에서는 이 부분을 문서나 감으로 확정하지 않고, 실제 고지서 샘플을 가지고 비교 실험한 뒤 판단하기로 했다.

### 5.1 판단 절차

1. 실제 과태료·범칙금 고지서 샘플을 5~6개 준비한다.
2. 고지서 이미지만 GPT, Claude, Gemini 등 2~3개 모델에 입력한다.
3. 법령 또는 법률 근거를 함께 제공한 뒤 같은 질문을 다시 입력한다.
4. 일반 분석 결과와 법률 근거 포함 결과를 비교한다.
5. 사용자 관점에서 더 명확하고 유용하면 법률 Agent 연결을 채택한다.
6. 법률 근거를 섞었을 때 가독성이 떨어지거나 실익이 작으면 해당 흐름에서는 호출하지 않는다.

### 5.2 기록해야 할 비교 항목

| 항목 | 확인 내용 |
|---|---|
| 모델 | GPT, Claude, Gemini 등 비교한 모델 |
| 입력 | 고지서 원본, OCR 결과, 법령 포함 여부 |
| 출력 차이 | 일반 분석과 법률 근거 포함 분석의 차이 |
| 장점 | 더 좋아진 설명, 근거, 구조화 항목 |
| 한계 | 가독성 저하, 과도한 법률 설명, 불필요한 추론 |
| 판단 | 법률 Agent를 연결할지, 어느 단계에서 호출할지 |

## 6. LangGraph와 Agent 흐름

회의에서 정리된 LangGraph의 의미는 단순히 여러 Agent를 섞는 것이 아니다.

LangGraph는 Agent의 동작을 통제하는 구조다.

### 6.1 LangGraph를 쓰는 이유

- 어떤 Agent를 언제 호출할지 정한다.
- OCR, 법률 검색, 분석, 요약, 문서 생성의 순서를 고정한다.
- 같은 입력에 대해 답변 흐름이 매번 달라지는 문제를 줄인다.
- 단일 Agent 내부에서도 세부 실행 순서를 제어할 수 있다.
- Supervisor가 각 Agent 결과를 받아 최종 답변을 통합하도록 만든다.

### 6.2 이번 프로젝트 적용 관점

```text
사용자 입력
  -> Supervisor가 입력 유형 판단
  -> 고지서/OCR, 경위서, 이미지, 영상, 법률 질문으로 분기
  -> 필요한 Agent만 호출
  -> 각 Agent는 구조화된 결과와 근거를 반환
  -> Supervisor가 최종 답변, 리포트, 후속 행동을 생성
```

## 7. AI 모델 비교 활용 원칙

회의에서 강조된 핵심은 하나의 모델만 사용하지 않는 것이다.

같은 질문과 같은 입력을 최소 2개 이상 모델에 던져 보고, 결과 차이를 팀 내부에 공유한다.

### 7.1 비교 대상 예시

- GPT
- Claude
- Gemini
- Grok
- Perplexity
- Cursor

### 7.2 공유해야 할 내용

| 항목 | 설명 |
|---|---|
| 동일 질문 | 어떤 질문을 여러 모델에 넣었는지 |
| 결과 차이 | 구조화, 근거, 요약, 누락, 과잉 추론 차이 |
| 모델 성향 | 어떤 모델이 어떤 작업에 유리했는지 |
| 적용 판단 | 우리 프로젝트에 어떤 방식으로 반영할 수 있는지 |

이 경험 자체가 프로젝트 품질뿐 아니라 면접이나 실무 경쟁력에도 연결되는 포인트로 언급됐다.

## 8. 화면설계서, API 명세서, 요구사항 정의서 접근 방식

회의에서는 AI가 잘하는 작업을 분석, 조사, 요약으로 정리했다.

따라서 화면 설계나 API 명세를 처음부터 내부 감각으로만 만들지 않고, 유사 서비스와 공개 문서 사례를 조사한 뒤 우리 서비스에 맞게 정리한다.

### 8.1 화면설계서 조사 방향

- 국내 유사 서비스 5개를 찾는다.
- 해외 유사 서비스 5개를 찾는다.
- 보험/교통 도메인뿐 아니라 OCR, 리포팅, 이미지 분석, 영상 분석, 텍스트 입력 분석 서비스도 본다.
- AI가 가져온 링크는 직접 클릭해서 타당성과 수준을 확인한다.
- 좋은 UI, 좋은 문구, 좋은 정보 구조를 벤치마킹 후보로 기록한다.

### 8.2 API 명세서 조사 방향

- 공개 API 문서 사례를 찾는다.
- GitHub에서 많이 사용되는 API 명세 예시를 조사한다.
- 상용 서비스 API 문서와 비교한다.
- 우리 프로젝트 기능에 맞는 API 초안을 여러 모델에서 받아 비교한다.
- 한 사람이 취합해 팀 기준 초안을 만든다.

## 9. 금요일까지 해야 할 일

금요일까지 해야 할 일은 모델 확정이 아니다.

금요일까지는 구현 전 판단 근거와 schema 초안을 준비해야 한다.

| 항목 | 금요일 전 산출물 |
|---|---|
| 화면설계서 | 홈 화면, 챗봇 화면, 화면설계서 HTML 마무리 |
| 모델 조사 | 각자 담당 파트에 적용 가능한 ML/DL/Agent 후보 조사 |
| Agent 흐름 | 입력, 출력, 분기 조건, 연결 Agent 정리 |
| input/output schema | 전처리 이후 어떤 데이터를 뱉을지 초안 작성 |
| API 명세 | API 명세서 구조 조사 및 우리 서비스 API 방향 고민 |
| 기술 적용 이유 | 본인 파트에 어떤 기술을 왜 적용해야 하는지 문서화 |
| 예상 결과 | 기술 적용 시 기대되는 결과와 한계 정리 |

## 10. 담당자별 금요일 전 체크리스트

### 10.1 요청자/문서·QA

- 홈 화면과 챗봇 화면을 화면설계서에 반영한다.
- 화면설계서 HTML 산출물을 준비한다.
- WBS, 역할, 이슈, 회의 변경사항을 문서화한다.
- Supervisor 결과 통합 schema 초안을 정리한다.

### 10.2 필주

- 고지서 샘플 5~6개를 준비한다.
- 고지서만 입력한 결과와 법령 근거 포함 결과를 비교한다.
- 최소 2개 이상 AI 모델 결과를 비교한다.
- 법률 Agent를 연결해야 하는지 판단 근거를 문서화한다.
- 고지서 OCR input/output schema 초안을 정리한다.

### 10.3 동혁

- 법률 데이터 범위를 법령, 시행령, 시행규칙, 행정 기준, 고시 중심으로 정리한다.
- 법률 원문/조문/근거 metadata schema를 검토한다.
- 법률 데이터에 ML이 필요한지 여부를 근거와 함께 정리한다.
- 판례 데이터와 법률 데이터의 경계를 명확히 유지한다.

### 10.4 재강

- 과실비율 판례, 유튜브 자막 사례, 과실비율심의사례 데이터 후보를 정리한다.
- 텍스트 ML 또는 RAG에 필요한 input/output schema를 정리한다.
- 같은 질문을 여러 AI 모델에 넣어 결과 차이를 비교한다.
- ML이 필요한 이유와 기대 결과를 문서화한다.

### 10.5 주희

- 차량 사고 이미지·영상 분석에 사용할 Vision/DL 후보를 조사한다.
- 이미지/영상 input과 분석 output schema를 정리한다.
- key frame, 장면 요약, confidence, 객체/상황 후보를 어떤 구조로 반환할지 검토한다.
- 모델 확정이 아니라 후보와 적용 이유를 정리한다.
