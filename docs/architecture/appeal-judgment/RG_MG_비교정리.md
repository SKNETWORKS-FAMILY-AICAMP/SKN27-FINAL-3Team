# RG vs MG 비교 정리 — 헷갈리지 않게 나란히 보기

이의가능성 판단 Agent의 핵심 판정 로직은 `RG`(리스크 게이트)와 `MG`(인정사유 분류) 두 개로
나뉘어 있다. 둘 다 `user_appeal_reason`(사용자가 쓴 이의신청 사유)을 입력으로 받는다는 점은
같아서 헷갈리기 쉬운데, **묻는 질문 자체가 다르다.**

> - RG: "이 사유를 쓰면 **내가 위험해지는가**?" (신원노출·범칙금 전환 위험)
> - MG: "이 사유가 **법적으로 인정될 만한가**?" (감경·인용 가능성)

한 문장으로: **RG는 안전 문제, MG는 승산 문제.** 안전한데 승산이 없을 수도 있고, 승산은 있는데
위험할 수도 있다 — 그래서 하나로 합치지 않고 따로 계산한다 (아래 4번 참고).

---

## 1. 한눈에 비교

| | RG (리스크 게이트) | MG (인정사유 분류) |
|---|---|---|
| 묻는 질문 | 이 사유가 **운전자를 특정**하거나 범칙금 전환을 수반하는가 | 이 사유가 **법조문상 인정 사유**에 해당하는가 |
| 왜 필요한가 | 과태료는 원칙적으로 소유자 책임이라 운전자가 특정 안 된 상태로 처리되는데, 절차 중 운전자가 드러나면 범칙금(형사절차)으로 전환될 수 있음 | 이의제기가 실제로 받아들여질 가능성이 있는지, 근거 없이 진행하다 시간만 버리는 건 아닌지 알려줘야 함 |
| 판단 구조 | **2단계**: ① 고신뢰 키워드 매칭 → ② LLM 분류(`category`+`confidence`, v21) | **단일 호출**: 고정 참조 법조문을 컨텍스트로 준 LLM 1회 판단 |
| 왜 구조가 다른가 | 놓치면(false negative) 사용자가 실제 불이익을 당함 → 재현율 우선, 안전장치로 이중 필터 | 애매해도 `merit=보류`로 떨어질 뿐 안전 문제가 아님 → 속도·단순성 우선, 이중 구조 불필요 |
| 입력 | `user_appeal_reason` + `notice_stage` (v16, 카테고리 C 판단용) | `user_appeal_reason` + `notice_stage` + LDB 참조 법조문 원문 |
| 출력 | `risk_flag` (true/false) + `risk_confidence` + `risk_stage_matched`("keyword"/"llm") + `risk_trigger_category`("A"/"B"/"C", v18 추가) | `merit` ("강함"/"보류"/"낮음") + `merit_basis`(인용 근거 요약) |
| 결과가 애매하거나 판단 실패할 때 | 보수적으로 `risk_flag=true` (안전 쪽으로, v21: LLM 호출 실패도 동일) | `merit=보류` (판단 유보, v21: LLM 호출 실패도 동일) |
| 최종 출력 우선순위 | **항상 merit보다 먼저 노출** (안전이 승산보다 중요) | risk 다음에 노출 |

## 2. RG 상세 — "위험한가"

### 판단 기준 (한 가지로 고정)
**"이의신청 사유가 신원(운전자 특정)과 관련이 있는가"** — 이 한 가지만 본다.

- "제가 운전하지 않았습니다" 류 사유나 범칙금 전환 신청 → 절차 중 실제 운전자가 드러나 범칙금(경우에 따라 형사절차)으로 전환될 수 있음 → 위험
- "금액 산정 오류", "표지판 미설치" 같은 사유 → 신원 노출과 무관 → 안전

### 법적 근거
- 서울시 교통위반 단속조회 시스템 공식 안내: 이의제기서가 법원 통보 → 비송사건절차법상 재판 → "범칙금 부과로 결정"되면 관할 경찰서 통보가 정규 절차로 존재
- 도로교통법 시행령: 과태료 50% 감경 대상에서 "의견제출·이의제기 결과 운전자가 밝혀진 경우"를 명시적으로 제외

### 3단계 분류, 도난 예외 + 3가지 트리거 카테고리 (v19 확정)
0. **(v19 신설) 0단계 도난 예외 체크 — 카테고리 A보다 먼저**: "도둑", "도난", "훔쳐서", "차를
   도둑맞아" 등 매칭 시 즉시 `risk_flag=false`로 종료, A/B/C 판단으로 안 넘어감. 이유는 아래
   "도난은 왜 카테고리 A가 아닌가" 참고.
1. **1단계 키워드 매칭** — 0단계 미매칭 시, 세 카테고리로 확정 매칭:
   - **A. 제3자 운전 주장**: "다른 사람이 운전했다", "제가 몰지 않았다" (도난은 제외 — 0단계에서 먼저 걸러짐)
   - **B. 명시적 전환 요청**: "범칙금으로 전환해주세요"
   - **C. 본인 운전 인정형**: 142조 1~5호에 대응하는 시드 키워드 (예: "응급환자를 이송", "장애인 승하차를 돕다가", "도로공사 중")
   → 매칭 시 즉시 `risk_flag=true`, `risk_stage_matched="keyword"`
2. **2단계 LLM 분류**: 1단계 미매칭 시, `category`(A/B/C/null)+`confidence`로 애매한 표현 판단. (v16) `category=C` 판단 기준에 "본인이 위반 당시 운전자였음을 전제로 정황(부득이한 사유/정상참작 요소)을 설명하는가"를 포함. (v19) "도난·절도로 인한 것인가"를 최우선 예외로 먼저 확인해 해당하면 `category=null`. **(v21)** `category`가 있고 `confidence`가 "low"가 아니면 `risk_flag=true`, `category`가 없거나 `confidence`="low"면 `false` — 원래는 `is_identity_related`(불리언)를 `category`와 별도로 판단하게 했으나, 실제 API 테스트에서 두 필드가 서로 모순되는 응답을 내는 게 확인돼(같은 사유를 6번 호출 시 category는 6번 다 "A"인데 is_identity_related는 무작위로 뒤집힘) `category` 하나로 통합했다

**도난은 왜 카테고리 A가 아닌가 (v19)**: "도둑이 운전했다"는 표면적으로 카테고리 A와 같아
보이지만, 도난은 성공(입증)·실패(입증 못함) 어느 쪽이든 누구에게도 범칙금 전환 위험이 실현되지
않는다. 카테고리 A는 성공/실패 무관하게 "밝혀진 특정 운전자"가 즉시 생기지만(그래서 무조건
위험), 도난은 성공하면 도로교통법 제160조4항1호에 따라 처분 자체가 불가로 끝나고, 실패해도
특정된 대체 운전자가 없어 3호(운전자가 밝혀진 경우)가 적용될 근거 자체가 없다. 그래서 도난은
성공·실패 무관하게 안전(risk=false)이며, 카테고리 A 판정보다 먼저(0단계) 걸러내야 한다.

경고 강도도 confidence에 따라 달라진다 — 1단계 확정 매칭은 강한 경고, 2단계 애매한 매칭은 참고용 약한 경고. **차단 로직은 없다** (진행 여부는 사용자 선택).

**카테고리 C 표현 범위 확정 (v16)**: 트리거 기준은 "142조 문구 매칭"이 아니라 **"화자 본인이
위반 당시 운전자였음을 전제로 정황을 설명하는 진술 전반"**이다. 142조 문구로만 한정하면 1차
고지서 단계의 질서위반행위규제법 제14조 정황요소(동기·목적·방법·결과, 태도, 연령·재산상태·환경)
기반 진술을 놓치기 때문이다. 그래서:
- 1단계 키워드는 142조 1~5호(구체적 사유)만 감당 — 6호(포괄조항)와 14조 정황요소는 표현이
  다양해 2단계 LLM 판단으로 위임
- **RG도 `notice_stage`를 입력에 추가**해 어느 계열(142조/14조)까지 카테고리 C로 볼지 판단한다.
  이건 `MG`의 출력이 아니라 OCR이 제공하는 `notice_stage` 원본 필드를 RG도 동일하게 읽는 것뿐
  이라, RG·MG 병렬·독립 구조는 유지된다.

도로교통법 제160조제4항제3호("이의제기의 결과 위반행위를 한 운전자가 밝혀진 경우")는 그 경로가
자백이든 지목이든 구분하지 않으므로, 본인 자인도 같은 위험으로 취급한다.

### RG의 한계 — 텍스트만으로는 못 잡는 리스크
RG는 **사용자가 쓴 텍스트**만 본다. 하지만 리스크는 텍스트에 없어도 **법원이 사실관계를 조사하는 과정 자체**에서 발생할 수 있다. 이건 RG가 사전에 걸러낼 수 없는 영역이라, `risk_flag=false`여도 ⑥번 disclaimer에 이 잔여 리스크를 **항상** 별도 경고로 넣는다.

### 채널(온라인/오프라인)은 판단 기준이 아님
이파인에서 온라인으로도 범칙금 전환 신청이 가능하다는 게 확인돼서, 채널은 리스크 판단에서 제외됐다. 리스크는 오직 **사유 내용**으로만 판단한다.

## 3. MG 상세 — "승산이 있는가"

### 판단 구조가 RG와 다른 이유
처음엔 MG도 RG처럼 "키워드 → LLM" 2단 구조로 설계했다가, LLM 단일 호출로 단순화했다.
- RG는 놓치면 실제 불이익(신원노출)으로 이어지지만, MG는 애매해도 `merit=보류`로 안전하게 수렴 — 재현율용 키워드 필터가 필요한 이유가 약함
- 참조 조문(142조 등)이 이미 공개된 잘 알려진 정보라, LLM에 원문만 줘도 정확히 판단 가능 — 별도 키워드셋 유지 비용이 이득보다 큼
- 법 개정 최신성은 하드코딩 키워드셋이 아니라 **LDB 동기화**로 해결 — 호출 시 최신 법조문 원문을 컨텍스트로 주입

### notice_stage × 위반유형별 참조 조문이 다름 (v19)

| notice_stage | 위반유형 | MG가 주입하는 법조문 |
|---|---|---|
| 사전통지 | 주정차 위반 | **제160조4항1호 본문(도난, v19) + 시행규칙 제142조** 열거 목록 원문 |
| 사전통지 | 비주정차 위반 (v17) | 질서위반행위규제법 제7조 (고의·과실 없음 — 도난도 포함) |
| 1차 고지서 | 주정차 위반 | 제160조4항1호 본문 + 142조 목록 + 질서위반행위규제법 제14조 정황요소(동기·목적·방법·결과, 태도와 정황, 연령·재산상태·환경) |
| 1차 고지서 | 비주정차 위반 (v17) | 제7조 + 제14조 정황요소 |

1차 고지서 단계는 법원 재판으로 넘어가 재량 범위가 넓어지므로, 142조/제7조에 없어도 14조 정황요소에 해당하면 `merit=보류`로 분류될 여지를 열어둔다.

**(v19) 도난은 142조가 아니라 상위 조문에 있다**: "차를 도난당하였거나 그 밖의 부득이한 사유"에서
도난과 부득이한 사유는 병렬 규정이라, 142조 목록만 봐서는 도난을 못 잡는다. 주정차 위반 컨텍스트에는
제160조4항1호 본문 자체도 함께 넣어야 도난 사례를 `merit=강함`으로 정확히 잡는다.

**위반유형 판별**: 새 필드 없이 OCR이 이미 추출하는 `law_code`가 도로교통법 제32~34조(주정차·정차 금지)에 해당하는지로 판별한다. MG가 `law_code`를 읽긴 하지만, 이건 인용 근거로 쓰는 게 아니라 위반유형 라우팅 신호로만 쓰는 것 — "MG는 개별 law_code를 인용 근거로 쓰지 않는다"는 원칙은 유지된다.

### 분류 결과 (3단계)
- **`강함`**: 참조 법조문에 명확히 해당
- **`보류`**: 열거 목록엔 없으나 귀책없음 취지 또는 14조 정황요소 해당 가능성
- **`낮음`**: 참조 법조문과 명백히 무관

### 제142조 적용범위 문제 — 해소됨 (v17)
`법조문_참고자료_142조_14조.md`에서 확인했듯, 시행규칙 제142조는 도로교통법 제160조 제3항(주정차·정차 위반)에서 위임된 조항이라 **주정차 위반에 한정된 근거**였다. 위 표에 정리했듯, 비주정차 위반에는 질서위반행위규제법 제7조를 대체 참조로 써서 해소했다. 상세는 `01_아키텍처_설계서.md` §9-2 참고.

## 4. 왜 하나로 합치지 않는가 — E 노드 통합 방식

`risk_flag`(RG)와 `merit`(MG)는 점수를 더하거나 곱해서 하나로 만들지 않는다. 그렇게 하면 "왜 이런 결과가 나왔는지" 설명이 불투명해지고 법률자문처럼 보일 위험이 커지기 때문에, **6칸 조합 매트릭스**로 각 조합별 권고 톤을 미리 정의해둔다.

| | risk = false | risk = true |
|---|---|---|
| **merit = 강함** | 안심하고 진행 | **(v15 갱신)** 142조 계열 인정사유는 조건부 리스크 — 도로교통법 제160조4항 1호(부득이한 사유)가 인정되면 과태료 자체가 면제돼 위험이 실현되지 않지만, 인정되지 않으면 이미 드러난 운전자 신원 때문에 3호(운전자가 밝혀진 경우)가 적용돼 범칙금으로 전환될 수 있음. "표현 조정"이 아니라 "성공 시 무위험 / 실패 시 전환 위험"으로 고지 |
| **merit = 보류** | 증거 보강 권유 | 판단도 애매하고 위험도 있음 → 가장 신중한 톤, 전문가 상담 권유 |
| **merit = 낮음** | 기대치 낮춰 안내 | 승산 낮고 위험까지 있음 → 진행 재고 권고 |

**우선순위 규칙**: 출력 시 `risk_flag`를 항상 `merit`보다 먼저 노출한다. 신원노출 위험이 승소 가능성보다 사용자 안전에 더 직결되기 때문 — "승산은 있는데 위험도 있다"는 정보가 뒤로 밀리면 안 된다.

**헷갈리기 쉬운 포인트**: `risk_flag=true`라고 해서 `merit`이 자동으로 낮아지거나, `merit=강함`이라고 해서 `risk_flag`가 자동으로 false가 되지 않는다. **두 값은 완전히 독립적으로 계산된다** — 승산 있는 사유가 동시에 위험한 표현일 수도 있고(표 1행 2열), 승산 없는 사유가 안전할 수도 있다(표 3행 1열).

**(v14) "강함×위험"은 더 이상 예외가 아니다**: RG에 카테고리 C(본인 운전 인정형)가 추가되면서,
142조 기반 인정사유는 거의 항상 이 조합으로 떨어진다. "독립적으로 계산된다"는 원칙은 그대로
유지되지만(RG가 MG를 참조하지는 않는다), 두 카테고리가 **같은 종류의 사유(142조 부득이한
사유)에서 구조적으로 함께 나타나는 경우가 많다**는 상관관계는 있다는 뜻이다.

**(v15) 그렇다고 "강함×위험 = 무조건 위험"은 아니다**: 도로교통법 제160조4항에서 1호(부득이한
사유=142조)와 3호(운전자가 밝혀진 경우)는 서로 다른 독립 근거다. 1호 주장이 **받아들여지면**
과태료 처분 자체가 불가해 범칙금 전환도 없이 끝난다 — risk가 실현되지 않는다. 1호 주장이
**받아들여지지 않으면** 이미 드러난 운전자 신원 때문에 3호가 적용돼 범칙금으로 전환될 수 있다.
즉 risk는 **1호 주장이 실패했을 때만 실현되는 조건부 리스크**다. "이 사유를 쓰면 위험하다"가
아니라 "성공하면 위험이 없고, 실패하면 범칙금 전환 위험이 있다"로 안내해야 정확하다.

**(v18) 이 조건부 프레이밍은 `risk_trigger_category = "C"`일 때만 정확하다**: 사유에 카테고리
A(제3자 운전 주장)나 B(명시적 전환 요청)가 C와 함께 매치되는 혼합 사례에서는 위험이 1호 실패를
전제하지 않고 곧바로 3호로 이어질 수 있다. RG는 이제 매치된 카테고리를 `risk_trigger_category`로
출력하고(A/B가 C보다 우선), 가이드는 A/B가 있으면 조건부 문구 대신 무조건 위험 경고를 쓴다.

**(v21) 6칸 전부 구현 완료**: 위 매트릭스는 최초 구현 때 "강함×위험" 한 칸만 코드에 반영돼
있었고 나머지 4칸("보류"·"낮음" 행)은 disclaimer에 아무 코멘트도 안 붙는 상태였다 — "risk=true면
경고만 보내고 끝인가?"라는 질문으로 재검토하다 발견해 `guide_generation_node`의
`_merit_risk_tone()`으로 6칸 전부 마저 구현했다.
