# 폐기·재검토 기능 히스토리 — 의의와 교훈

**과태료 이의가능성 판단 Agent** · 참고 문서 (마스터 설계 문서 부록, 2026-07-02 기준 v18과 정합)

> 이 문서는 설계 과정에서 만들었다가 뺀 기능들을 한곳에 모아, **"왜 뺐는지"뿐 아니라 "그 결정에서
> 뭘 배웠는지"**를 남기기 위한 것이다. 마스터 설계 문서 곳곳에 흩어져 있는 폐기 이력을 다시 찾지
> 않아도 되도록, 이 문서 하나로 전체 그림이 보이게 만드는 게 목적이다.

## ① law_code 검증 — 도입 → 전면 폐기 → 경량 부활

### 원래 의의 (v9에서 만든 이유)
OCR이 뽑아준 `law_code`("도로교통법 제17조 제1항" 같은 자연어 문자열)가 실제로 존재하는 조항인지
확인하려는 시도였다. OCR 오인식(제17조→제77조)이나 법 개정으로 조번호가 바뀌는 경우를 걸러내
려는 목적으로, 정규화→조회→하드블록(재확인 1회 요청 → 실패 시 판단 단계 자체 종료)까지 꽤
무겁게 설계했다.

### 왜 폐기했었나 (v12)
검증해보니 `MG`(인정사유 판단 로직)가 애초에 이 고지서의 개별 `law_code`를 쓰지 않고, **고정된
참조 조문**(시행규칙 제142조 등)만 LLM 컨텍스트로 주입하고 있었다. 즉 이 검증이 아무리 정확해도
판정 결과(`overall_possibility`)에는 전혀 반영되지 않는 순수 오버헤드였다. "판정에 기여하지
않는다 + 계속 관리해야 하는 데이터다"라는 두 조건을 근거로 통째로 뺐다.

### 왜 다시 살렸나 (v13)
근거로 든 "두 조건" 중 두 번째("계속 관리해야 한다")가 **이 항목엔 틀렸다.** law_code 데이터는
팀이 이미 구축한 법령DB 파이프라인이 자동으로 최신 상태를 유지해준다. 유지관리 비용이 사실상
0이라면, 판정에 안 쓰이더라도 **이의신청서에 실제로 인용되는 법조항의 정확성**이라는 문서 품질
가치가 남는다. 다만 하드블록(재확인 루프, Supervisor 왕복)까지 되살릴 이유는 없어서, 단일 조회
+ 플래그만 남기는 경량 버전으로 부활시켰다.

### 남는 교훈
**"판정에 기여하는가"와 "유지관리 부담이 있는가"는 독립적인 두 질문이고, 하나가 참이라고 다른
하나도 참이라고 넘겨짚으면 안 된다.** 이 항목은 첫 번째만 참이었는데 둘 다 참이라고 오판해서
과도하게 제거했던 사례다.

## ② 발부기관(경찰/지자체) 판별 + 접수채널 화이트리스트 — 완전 제거

### 원래 의의
"이 고지서가 경찰이 발부했는지 지자체가 발부했는지"를 판별해서, 정식 이의제기가 온라인으로
가능한지 접수채널을 안내해주려는 기능이었다. 조사해보니 경찰 발부 건은 2021년 법무부 해석으로
온라인이 확정적으로 막혀있고, 지자체는 곳마다 달랐다 (대전은 온라인 가능, 인천·부산은 서면만,
서울시설공단은 혼잡통행료 한정 온라인 가능 등).

### 왜 제거했나
본 서비스의 산출물은 **완성된 이의신청서(문서) 자체**다. 이 문서는 우편으로 보내든 방문해서
내든 온라인에 업로드하든 똑같은 파일이라, 접수채널 정보가 산출물의 형태를 바꾸지 않는다. 그리고
이 데이터(지자체 시스템 현황)는 우리가 계속 수작업으로 리서치해야 하는, 진짜로 유지관리 부담이
있는 항목이었다 — ①번과 달리 자동화된 소스가 없다.

### 왜 계속 제거 상태인가 (재검토 후에도)
①번을 재검토하면서 이것도 다시 봤지만, 여기는 원래 근거가 그대로 유효했다. 데이터 소스 자체가
자동화 안 된 "지자체 웹사이트 운영 현황"이라, 유지관리 부담 논리가 정확히 들어맞는다.

### 남는 교훈
**산출물 형태를 바꾸지 않는 부가 정보는, 아무리 사용자 편의를 높여줘도 정확성을 우리가 보증할
필요가 없다.** "관할 기관에 직접 확인하라"고 위임하는 게 낡은 정보를 우리가 들고 있는 것보다
항상 더 정확하다.

## ③ `ZP` (벌점 0점 화이트리스트 + 빠른 경로) — 대기 상태

### 원래 의의
과태료를 범칙금으로 전환했을 때 벌점이 0점인 위반 유형(예: 제한속도 20km/h 이내 초과)이라면,
이의신청 여부를 고민할 필요 없이 그냥 저렴한 쪽으로 납부하면 된다는 걸 **가이드 최상단에 먼저**
보여주려는 기능이었다.

### 왜 제거했었나 (v12) — 그리고 이 근거가 왜 틀렸는가
"지자체 화이트리스트랑 똑같이 계속 바뀌는 데이터를 우리가 유지관리해야 하는 문제"라고 적고
②번과 같은 이유로 묶어서 제거했다. **이건 잘못된 유비였다.** 벌점 기준(별표28)은 지자체 웹사이트
운영 현황이 아니라 **법령 데이터**라, 소스 자체가 다르다. law_code와 마찬가지로 법령DB
파이프라인 대상이 될 수 있는 데이터였는데, 성격이 다른 ②번과 겉모습만 비슷해 보여서 같은
결론으로 묶어버렸다.

### 그럼 왜 지금도 안 살렸나
진짜 걸림돌은 유지관리가 아니라 **법령DB API가 별표(표 형태 데이터)를 파싱 가능한 구조화
텍스트로 주는지, 아니면 뭉개진 텍스트나 이미지로 주는지가 아직 확인이 안 됐다는 기술적 문제**다
(자세한 3단계 구분은 마스터 문서의 "별표 파싱 가능 상태" 논의 참고). 이건 근거를 다시 세워야
할 뿐 완전히 폐기할 이유는 없어서, "대기 상태"로 명시적으로 남겨뒀다.

### 남는 교훈
**"이 문제, 전에 봤던 그 문제랑 비슷한데"라는 직관은 근거 확인 없이 결론까지 복사해오면
안 된다.** ②번과 ③번은 겉으로 "계속 바뀌는 데이터"라는 점에서 닮아 보였지만, 실제 데이터
소스(지자체 웹사이트 vs 법령DB)가 완전히 달랐다.

## ④ 별표28(벌점 기준표) 전체 매핑 — 대기 상태

③번과 사실상 같은 사안이다. `ZP`가 이 데이터를 소비하는 소비자였을 뿐이라, `ZP`의 재검토 결론이
그대로 적용된다. 정확한 벌점 수치는 이파인 전환 미리보기 화면으로 계속 위임하고, 별표28을 우리가
직접 파싱해서 보여줄지는 법령DB API 응답을 실제로 확인한 뒤 결정한다.

## ⑤ law_refs.py 160조4항1호 RAG 조회 — 도입(2026-07-15) → 같은 날 부분 환원

### 원래 의의 (2026-07-15 도입 이유)
`law_refs.py`가 MG(merit_classification_node) 참조 조문을 법령DB에서 조회할 때 기존엔
`(법령명, 조문번호)` exact match를 썼는데, 법 개정으로 조문번호 자체가 재편되면(예: 142조가
143조로 밀림) 조회가 에러 없이 "성공"하면서 조용히 엉뚱한 조문을 LLM 근거로 주입할 위험이
있었다(`docs/issues/reference-drift-check-followup.md` 배경 참고). 이를 근본적으로 없애려고,
조문번호 대신 검증된 폴백 원문 자체를 검색 질의로 쓰는 의미 기반(RAG) 검색으로 `law_refs.py`의
`PINNED_REFERENCES` 전체(142조·질서법 7~10·14조·160조4항1호 7개)를 전환했다 —
`ai/agents/law_ground_search/search.py`의 `search_law_provisions()`/`evaluate_confidence()`를
재사용해, 신뢰도(코사인 유사도 0.4)와 `source_name` 일치를 통과할 때만 RAG 매칭 원문을 쓰고
아니면 폴백으로 떨어지게 설계했다.

### 왜 160조4항1호만 되돌렸나
실제 DB(law_chunks, 99,315건, openai 임베딩)로 7개 조문을 전부 실행해보니 6개(142조·질서법
7~10·14조)는 스코어 0.92~0.96으로 깨끗하게 매칭됐지만, **160조4항1호만 스코어 0.65로 확연히
낮았다.** 원인을 파보니, 제160조는 ①~④항을 다 포함한 긴 조문인데 ETL의 길이 기반 분할
(`etl/legal/ingestion/parser.py`의 `split_long_text`, 글자수로만 자르고 항 경계는 안 봄)이
③항(20만원 과태료 대상 조문번호 30여 개 열거, 우리가 찾던 내용과 무관)과 ④항(도난·부득이한
사유 등, 우리가 찾던 내용) 전체를 한 청크(1,141자)에 섞어버렸다. 이 청크 하나가 두 주제를
담고 있어 임베딩이 희석돼 신뢰도가 낮게 나온 것이다.

0.65도 임계값(0.4)은 넘겨서 "confident"로 통과하길래, 실제 merit_classification_node의
LLM 호출(gpt-4o-mini)까지 재현해 A/B 비교했다. 결과, **두 가지 실패가 실측으로 확인됐다**:
1. "차를 도난당했다"는 사유에 대해 merit(강함) 자체는 맞았지만, `merit_basis`가 청크에 섞여
   있던 "제11조제4항"(②항 9호에 나온 무관한 조문번호)과 정답의 "제1호"를 뒤섞어
   **"도로교통법 제11조제4항제1호"라는 존재하지 않는 조합을 인용했다.**
2. "다른 사람이 운전했는데 나중에 밝혀졌다"는 사유가, 폴백 버전에서는 "낮음"(참조 조문
   범위 밖)이었는데 RAG 버전에서는 노이즈로 딸려온 ③항1호("운전자를 확인할 수 없어 고지서를
   발급할 수 없는 경우")를 근거로 "보류"로 바뀌었다 — `law160-budeuk-hansayu-scope-analysis2.md`가
   검증한 범위 밖의 내용이 실제 판정에 영향을 준 사례다.

DB 전체를 스캔해보니 이 "길이 분할이 항 경계를 무시해 서로 다른 항이 한 청크에 섞이는" 문제는
160조만의 문제가 아니라, 길이 분할이 일어난 (법령, 조문) 84개 조합 중 59개(70%)에서 재현되는
더 넓은 ETL 이슈였다(도로교통법에만 5건 — 82·93·113·160조 등). 다만 `PINNED_REFERENCES`가
RAG로 조회하는 7개 중 이 문제에 해당하는 건 160조4항1호 하나뿐이라, 이 조문만 예전처럼
`get_merit_context()`에서 `_FALLBACK_ARTICLE_160_4_1_TEXT` 상수를 RAG 없이 직접 쓰도록
되돌리고, 나머지 6개는 RAG를 유지했다.

### 남는 교훈
**신뢰도 임계값을 넘겼다는 것과 "맞는 조문을 찾았다"는 것은 다르다.** 0.65는 0.4보다 높아
"confident"로 분류됐지만, 실제로는 무관한 텍스트가 섞인 청크였다. 코사인 유사도 숫자만으로는
이 차이가 안 드러났고, **실제 다운스트림 LLM 호출까지 재현해서 `merit_basis`를 직접 읽어봐야만**
드러나는 실패 모드였다. 신뢰도 임계값이나 데이터 청크 자체의 검증은, 그걸 소비하는 마지막 단계
(여기선 LLM 판단·인용)까지 실측하지 않으면 충분하지 않다.

### 다음에 이 항목을 다시 열어봐야 할 시점
- ETL 파서(`etl/legal/ingestion/parser.py`)가 `split_long_text`를 항(①②③④) 경계를 인식하는
  분할로 개선해, 제160조 같은 긴 조문도 항 단위로 깨끗하게 청크가 나뉘게 되면 → 160조4항1호도
  다시 RAG 대상에 포함 재검토 가능.
- 그 개선이 도로교통법의 다른 4건(82·93·113조 등)과 나머지 법령의 55건에도 함께 적용되므로,
  ETL 쪽에서 한 번에 고치는 게 이 조문 하나만 개별 대응하는 것보다 효율적이다.

- ETL 파서가 항 경계를 인식하는 분할로 개선되면 → ⑤번(160조4항1호 RAG 재포함) 재검토
- **이 문서의 진짜 용도는 "폐기 목록"이 아니라 "제거 결정에 쓴 근거를 검증 가능한 형태로 남겨서,
  전제가 바뀌면 언제든 재검토할 수 있게 하는 것"이다.** ①번이 그 재검토가 실제로 일어난 사례다.
