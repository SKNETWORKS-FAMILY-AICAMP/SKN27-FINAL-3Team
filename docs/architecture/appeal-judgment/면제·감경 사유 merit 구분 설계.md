# 면제·감경 사유 merit 구분 — 현재 예시 및 구현 설계

> 대상 코드: `ai/agents/appeal_decision_flow/{merit_gate.py, prompts.py, state.py, guide.py}`
> 계기: 질서위반행위규제법 제10조(심신장애) 관련 질의응답 중 발견
> **상태: 구현 완료 (2026-07-08)** — 아래 §1~§6은 최초 설계안, §7은 구현 후 실측 검증에서
> 발견한 추가 보정 내용이다.

## 1. 문제

`merit`은 강함/보류/낮음 3단계뿐이라, **"처분 자체가 없어지는 사유"(면제)**와
**"처분은 유지되고 금액만 깎이는 사유"(감경)**를 구분하지 못한다. 둘 다 조문에 "명확히
해당"하면 LLM이 똑같이 `merit="강함"`을 줄 수 있는데, 사용자 입장에서 두 결과는 완전히
다르다 — 전자는 "이의제기하면 처분이 없어질 수도 있다"는 기대가 정당하지만, 후자는
"이의제기해도 처분은 유지되고 금액만 조금 준다"가 맞는 기대치다.

이 문제가 특히 잘 드러나는 조문이 **질서위반행위규제법 제10조(심신장애)**다 — 한 조문
안에 면제 항과 감경 항이 함께 있다:

```
제10조(심신장애)
① 심신장애로 옳고 그름 판단 능력이 없거나 그 판단에 따른 행위를 할 능력이
   없는 자의 질서위반행위는 과태료를 부과하지 아니한다.        ← 면제
② 심신장애로 인하여 제1항에 따른 능력이 미약한 자의               ← 감경
   질서위반행위는 과태료를 감경한다.
③ 스스로 심신장애 상태를 일으켜 질서위반행위를 한 자에 대하여는   ← 배제
   제1항 및 제2항을 적용하지 아니한다.
```

## 2. 현재 예시 (as-is) — 사용자 사유별 기대 동작 vs 실제 위험

| # | 사용자 사유 예시 | 실제 해당 항 | 법적 효과 | 현재 예상 `merit` | 문제 |
|---|---|---|---|---|---|
| 1 | "그 당시 의식을 완전히 잃은 상태였습니다(발작 등)" | ①(면제) | 처분 자체 불가 | 강함 | 없음 — 결과가 실제로 강력함 |
| 2 | "판단력이 다소 흐려진 상태였습니다" | ②(감경) | 처분 유지, 금액만 감경 | **강함(위험)** | LLM이 "조문에 해당"만 보고 강함을 줄 수 있음 — 사용자는 "처분 자체가 없어질 수도 있다"고 오해 |
| 3 | "그날 술을 마셔서 판단력이 흐려졌습니다" | ③(배제, 자초) | 면제·감경 모두 불가 | 낮음(정상) | 조문이 명시적으로 배제하므로 LLM이 대체로 정확히 "낮음"을 줄 것으로 예상되나, 검증된 적 없음 |
| 4 | "표지판이 가려져 몰랐습니다" (제8조, 위법성의 착오) | 위법성의 착오(면제) | 처분 자체 불가 | 강함 | 없음 — 제8조는 감경 항이 없어 이 문제가 없음 |
| 5 | "14세 미만 자녀가 대신 운전했습니다" (제9조, 책임연령) | 책임연령(면제) | 처분 자체 불가 | 강함 | 없음 — 제9조도 감경 항이 없음 |

**핵심**: 문제는 10조 전체가 아니라 **10조② 하나**다. 7·8·9조와 10조①·③은 전부 "면제 또는
배제"라는 단일 결과라 지금 구조로도 정확하다. 10조②만 "면제가 아니라 감경"이라는 제3의
결과가 있어서 3단계 merit로는 표현이 안 된다.

## 3. 구현 설계 (실제 구현에 그대로 반영됨)

### 3-1. 새 필드: `merit_relief_type`

`merit`(강함/보류/낮음)은 그대로 두고, **면제인지 감경인지를 별도 축으로 분리**한다 —
RG의 `risk_flag`와 `risk_trigger_category`를 분리한 것과 같은 패턴(§9-5 선례를 재사용).

```python
# state.py
MeritReliefType = Literal["면제", "감경", None]

class AppealJudgmentState(TypedDict, total=False):
    ...
    merit:              Optional[MeritLevel]
    merit_relief_type:  Optional[MeritReliefType]  # 신설 — merit="강함"일 때만 의미 있음.
                                                    # "감경"이면 처분 자체가 아니라 금액만
                                                    # 줄어드는 사유라는 뜻. None이면 참조
                                                    # 조문 전부가 면제형이라 구분 불필요
                                                    # (또는 merit != 강함이라 무의미).
    merit_basis:        Optional[str]
```

### 3-2. 프롬프트 수정안 (`prompts.py::MERIT_CLASSIFICATION_PROMPT`)

```diff
 판단 기준:
 - "강함": 참조 법조문에 명확히 해당하는 경우
 - "보류": 열거 목록엔 없으나 귀책없음 취지이거나 정황요소 해당 가능성이 있는 경우
 - "낮음": 참조 법조문과 명백히 무관한 경우

+relief_type 판단 기준 (merit="강함"일 때만 채우세요, 그 외엔 null):
+- "면제": 해당 조문이 인정되면 과태료 처분 자체가 불가능해지는 경우
+  (예: 질서법 제7·8·9조, 제10조①, 도로교통법 제160조4항1호·142조)
+- "감경": 해당 조문이 인정돼도 처분은 유지되고 금액만 줄어드는 경우
+  (예: 질서법 제10조②, 제14조의 정황참작에 의한 감경)
+- null: merit이 강함이 아니거나, 참조 조문에 면제/감경 구분이 없는 경우
+
 반환 필드:
 - merit       : "강함" | "보류" | "낮음"
+- relief_type : "면제" | "감경" | null
 - merit_basis : 인용한 조문·근거 한 줄 요약
```

### 3-3. `merit_gate.py` 파싱

```python
result = _call_llm_merit(reason, law_context)
merit = result.get("merit")
merit_basis = result.get("merit_basis")
relief_type = result.get("relief_type") if result.get("relief_type") in ("면제", "감경") else None
```
LLM 호출 실패·값 검증 실패 경로(`merit_judgment_failed=True`)에서는 `relief_type=None`으로
둔다 — 애초에 판단 자체가 안 된 상태라 면제/감경 구분도 의미가 없다.

### 3-4. `guide.py` 문구 보강

`_merit_risk_tone()` 또는 `_disclaimer_text()`에 조건 추가:

```python
if state.get("merit") == "강함" and state.get("merit_relief_type") == "감경":
    parts.append(
        "이 사유는 인정되더라도 과태료 처분 자체가 없어지는 게 아니라 "
        "금액이 일부 감경되는 사유입니다 — 처분이 취소될 거라 기대하지 마세요."
    )
```

`_structured_result()`에도 `merit_relief_type` 노출 (구조화 응답에서 프로그램적으로도 구분
가능하게).

## 6. 미결 사항

- **적용 범위**: 지금 당장 감경/면제 구분이 실제로 필요한 조문은 10조②뿐이다. 다른 참조
  조문(7·8·9조, 142조, 160조4항1호)은 전부 면제형이라 relief_type이 항상 "면제"로 나올
  것 — 이 필드를 프롬프트에 추가하는 비용(토큰·복잡도) 대비, 지금 실익은 10조② 하나를 위한
  것임을 감안해서 진행 여부를 판단할 것.
- **14조와의 관계**: 1차 고지서 단계에서 추가되는 제14조("정황요소 고려")도 성격상 "감경"에
  가깝다(법원 재량으로 참작하는 것이지 면제 사유가 아님). relief_type을 도입한다면 14조
  기반 판단도 기본적으로 "감경"으로 처리하는 게 일관적이다 — 3-2 프롬프트 수정안에 이미
  반영해뒀다.
- **RG와의 상호작용은 없음**: relief_type은 merit(승산) 축에만 영향을 주고, risk_flag(신원노출
  위험) 판단·톤 선택 로직(카테고리 A/B/C)에는 영향을 주지 않는다 — 두 축은 계속 독립적으로
  유지한다.

## 7. 구현 완료 및 실측 검증 (2026-07-08)

§3의 설계를 `state.py`(`MeritReliefType`, `merit_relief_type`)·`prompts.py`(relief_type
판단 기준 추가)·`merit_gate.py`(파싱·검증)·`guide.py`(감경 전용 disclaimer 문구,
`_structured_result` 노출)에 그대로 구현했다.

### 7-1. 실제 GPT API로 검증하다가 발견한 문제 — 프롬프트만으로는 부족했다

실제 OpenAI API(`gpt-4o-mini`, temperature=0)로 심신장애 사례를 직접 호출해봤다.

| 사유 | 기대 | 1차 구현(프롬프트만) 결과 |
|---|---|---|
| "판단능력이 **미약한** 상태였습니다" | 감경(②) | ❌ `merit=강함, relief_type=면제` (근거로 **①을 잘못 인용**) |
| "의식이 완전히 **없는** 상태였습니다" | 면제(①) | ✅ `merit=강함, relief_type=면제` |
| "판단력이 다소 흐려진 상태" | 애매 → 보류 | ✅ `merit=보류, relief_type=None` |
| "술을 마셔서 판단력이 흐려짐" (③ 자초) | 낮음 | ✅ `merit=낮음, relief_type=None` |

첫 번째 케이스가 문제였다 — 사용자가 명확히 "미약한"(②의 표현)이라고 썼는데도 모델이
"면제"(①)로 잘못 분류했다. `MERIT_CLASSIFICATION_PROMPT`에 "①/②를 사용자 표현의 정도로
정확히 구분하라"는 지시를 추가로 강화해도(예시 표현까지 명시) **재현됐다** — 즉 프롬프트
튜닝만으로는 gpt-4o-mini 수준에서 이 구분을 안정적으로 못 지켰다.

**이건 정확히 이 기능이 막으려던 오해(감경일 뿐인데 면제로 오인)를 기능 자체가 재현한
것**이라 그냥 넘어갈 수 없었다.

### 7-2. 해결 — RG의 "키워드 안전장치" 패턴을 MG에도 적용

`risk_classification_node`가 LLM 판단 앞에 1단계 키워드 매칭을 두는 것과 같은 패턴으로,
`merit_gate.py`에 LLM 판단 **뒤에** 보수적 재보정 단계를 추가했다:

```python
_DIMINISHED_CAPACITY_HEDGE_WORDS = ("미약", "약간", "다소", "조금", "일부")

def _downgrade_relief_type_if_hedged(reason: str, relief_type: str | None) -> str | None:
    if relief_type == "면제" and any(word in reason for word in _DIMINISHED_CAPACITY_HEDGE_WORDS):
        return "감경"
    return relief_type
```

사용자 사유 원문에 정도를 낮추는 표현("미약", "다소" 등)이 있는데 LLM이 "면제"를 줬다면,
안전한 쪽(감경)으로 강제 재보정한다. 재검증 결과:

| 사유 | 재보정 후 |
|---|---|
| "판단능력이 **미약한** 상태였습니다" | ✅ `relief_type=감경` (LLM은 여전히 "면제"라고 했지만 코드가 재보정) |
| "의식이 완전히 없는 상태였습니다" | ✅ `relief_type=면제` (그대로 유지, 과잉 보정 안 됨) |

### 7-3. 리뷰 중 지적된 문제 — 키워드 안전장치가 문맥을 안 봄

`_downgrade_relief_type_if_hedged`가 사유 **전체**에서 정도완화 단어만 찾다 보니,
심신장애와 무관한 순수 면제형 사유에서도 오작동하는 게 리뷰 중에 지적됐다:

- "장애인 승하차를 돕느라 **다소** 시간이 걸렸습니다" (142조5호) → 감경으로 오재보정
- "표지판이 나뭇가지에 **일부** 가려져 있어서 몰랐습니다" (8조) → 감경으로 오재보정
- "제 차를 도둑맞았는데 **약간** 파손된 채로 발견됐습니다" (도난, 160조4항1호) → 감경으로 오재보정

142조/7·8·9조/160조4항1호는 애초에 "감경" 개념 자체가 없는 순수 면제형인데, 무조건
깎아버리면 **정당한 면제 사유를 과소평가**하게 된다. `_CAPACITY_CONTEXT_WORDS`
("심신", "판단", "의식", "정신")를 추가해서, 정도완화 단어와 능력-판단 문맥 단어가
**함께** 있을 때만 재보정하도록 좁혔다. 실측으로 위 3개 오탐이 전부 해소되고, 원래
목표(제10조② 케이스)는 그대로 잡히는 것을 확인했다.

### 7-4. 아키텍처 개선 — 키워드 안전장치만으로는 한계, LLM 호출 분리로 전환

"문맥 표현이 제각각인데 키워드 목록으로 다 못 잡지 않느냐"는 문제 제기에 따라 대안을
검토했다. RG가 `is_identity_related`+`category`를 한 호출에서 같이 물었다가 모순
응답이 나와서 `category` 하나로 쪼갠 선례(§11-1)의 **반대 방향과 같은 교훈** —
merit과 relief_type을 한 호출에서 같이 물으면 정확도가 떨어지므로, relief_type을
**merit="강함"일 때만 호출하는 별도 LLM 호출**로 분리했다(`RELIEF_TYPE_CLASSIFICATION_PROMPT`,
`_call_llm_relief_type`). 키워드 안전장치(`_downgrade_relief_type_if_hedged`)는
최후 방어선으로 그대로 유지한다 — LLM이 또 실수해도 알려진 실패 패턴은 잡아준다.

**분리 직후 실측에서 또 다른 오탐 발견**: relief_type 전용 프롬프트가 "사유에
다소/약간이 있으면 감경"이라는 규칙을 **참조 조문과 무관하게 일반화**해서 적용해,
"장애인 승하차를 돕느라 **다소** 시간이 걸렸다"(142조5호, 감경 항 자체가 없음)를
`relief_type=감경`으로 잘못 냈다 — 코드의 키워드 안전장치는 "심신/판단" 문맥이 없어서
개입하지 않았는데, 프롬프트 자체가 §7-3과 같은 실수를 반복한 것이다.

**최종 수정**: 프롬프트에 "①먼저 사유가 정확히 어느 조·항에 해당하는지 특정 →
②**그 항 자체의 법률 효과만** 따르고 사유의 정도완화 표현으로 임의 판단하지 말 것 →
③단, 같은 조문 안에 정도가 다른 항이 실제로 공존하는 경우(제10조)에만 예외적으로
정도 구분 적용"이라는 순서를 명시하고, `matched_clause`(실제 해당 조·항) 필드를
추가로 반환하게 해서 모델이 판단 근거를 먼저 특정하도록 유도했다. 재검증(2회 반복,
결정론적 확인):

| 사유 | 결과 |
|---|---|
| "판단능력이 **미약한** 상태였습니다"(10조②) | ✅ `relief_type=감경` |
| "의식이 완전히 없는 상태였습니다"(10조①) | ✅ `relief_type=면제` |
| "장애인 승하차를 돕느라 **다소** 시간이 걸렸습니다"(142조5호) | ✅ `relief_type=면제` (더 이상 오탐 없음) |
| "제 차를 도둑맞았는데 **약간** 파손된 채로"(도난) | ✅ `relief_type=면제` |

**부수 발견(별도 이슈, 이번엔 안 건드림)**: 위 재검증 중 "판단능력이 미약한 상태"
사유가 1차(merit) 호출에서 아예 `merit="보류"`로 나온 적이 있었다(`merit="강함"`이
아니면 relief_type 호출 자체가 생략됨). 감경형 사유를 모델이 "덜 확실한 사유"처럼
과소평가하는 것으로 보이는데, 이건 relief_type 정확도가 아니라 `MERIT_CLASSIFICATION_PROMPT`
자체의 "강함" 기준 문제라 별도 사안으로 남겨둔다 — 사용자에게 유리한 방향(과대평가 아닌
과소평가라 §7-1 같은 안전 문제는 아님)이라 급하지 않지만, 조현병처럼 명백한 사유가
"보류"로 떨어지는 건 개선 여지가 있다.

### 7-6. 남은 한계

- 키워드 안전장치는 여전히 "면제→감경" 한 방향, "심신/판단/의식/정신" 문맥 단어에
  한정된 최후 방어선일 뿐이다 — §7-4에서 relief_type 판단의 주력을 LLM 전용 호출로
  옮겼으므로 이 한계의 실제 노출은 줄었지만, 완전히 사라진 건 아니다.
- `merit_basis`(LLM이 생성한 근거 요약 텍스트)는 여전히 조문 번호를 부정확하게
  인용할 수 있다(예: 실제론 ②인데 "제10조①"이라고 씀). `merit_basis`는
  `_structured_result()`에 노출되지 않아 사용자에게 직접 보이지 않으므로 실제 영향은
  없지만, 로그·디버깅 시 헷갈릴 수 있다.
- §7-4 "부수 발견"에 적은 대로, 감경형 사유가 1차 merit 호출에서 "강함" 대신 "보류"로
  과소평가되는 경향은 미해결 — relief_type과는 별개 사안.
