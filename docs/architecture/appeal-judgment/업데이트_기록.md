## 2026-07-02 — RG·MG의 LLM 호출에 temperature 미설정으로 인한 재현성 문제

| 항목 | 값 |
|------|-----|
| 발견 경로 | `test/test_appeal_decision_flow_real_llm.py::TestRealTheftCase::test_도난_케이스는_merit강함_risk안전` 실제 GPT API 스모크 테스트를 반복 실행하던 중 |
| 영향 범위 | `ai/agents/appeal_decision_flow/merit_gate.py`(`_call_llm_merit`), `ai/agents/appeal_decision_flow/risk_gate.py`(`_call_llm_classifier`) — RG·MG의 2단계 LLM 호출 전부 |
| 상태 | 해결됨 |

### 증상

동일한 입력("제 차를 도둑맞았는데 그 도둑이 운전하다가 위반한 것 같습니다", 사전통지·주정차 위반)으로
`merit_classification_node`를 반복 호출했을 때, 어떤 회차는 `merit="강함"`, 어떤 회차는
`merit="보류"`로 서로 다른 결과가 나왔다. 도로교통법 제160조제4항제1호(도난)에 명확히 해당하는
사례라 설계상 항상 "강함"이 나와야 하는데, 실행할 때마다 결과가 달라져 테스트가 간헐적으로
실패했다.

### 원인

두 가지가 겹쳐 있었다.

1. **`temperature` 파라미터 미설정** — `_call_llm_merit`·`_call_llm_classifier` 둘 다
   `client.chat.completions.create(model=..., max_tokens=..., messages=...)`만 호출하고
   `temperature`를 지정하지 않았다. OpenAI API는 이 경우 기본값 `1.0`을 쓰는데, 이는 창의적
   글쓰기에 적합한 값이지 "정해진 카테고리 중 하나로 분류하는 작업"에는 불필요하게 높은
   무작위성을 부여한다.
2. **입력 문구의 헤징(hedging) 표현** — 위 테스트 사유가 "...위반한 **것 같습니다**"로,
   "확정된 사실"이 아니라 "추측"으로 서술돼 있다. MG 판단 기준("강함"=참조 법조문에 **명확히**
   해당, "보류"=애매함)상 이런 문구는 강함/보류 경계선에 걸치는 입력이라, temperature가 높을
   때 결과가 흔들리는 폭이 특히 커졌다.

두 원인 중 1번이 근본 원인이고, 2번은 그 증상이 눈에 띄게 드러난 계기였다 — temperature가
낮았다면 2번 같은 경계선 케이스에서도 훨씬 일관된 답이 나왔을 것이다.

### 해결

`merit_gate.py`의 `_call_llm_merit`, `risk_gate.py`의 `_call_llm_classifier` 양쪽 API 호출에
`temperature=0`을 추가했다. 분류(classification) 작업은 창의성이 필요 없으므로 가장 낮은
temperature가 정석이다.

```python
response = client.chat.completions.create(
    model="gpt-4o-mini",
    max_tokens=256,
    temperature=0,
    messages=[...],
)
```

### 검증

- `test/unit/`, `test/integration/`(GPT 호출을 mock 처리하는 101개 테스트)은 `MagicMock`이
  임의의 키워드 인자를 그대로 받아들이므로 `temperature=0` 추가로 인한 영향이 없음을 확인 —
  101개 전부 통과.
- 실제 GPT API로 `TestRealTheftCase::test_도난_케이스는_merit강함_risk안전`을 3회 연속
  재실행해, 매번 `merit="강함"`으로 안정적으로 재현되는 것을 확인 (수정 전에는 "강함"/"보류"가
  섞여 나왔음).

### 남은 한계

`temperature=0`은 무작위성을 최소화할 뿐 완전한 결정성을 보장하지는 않는다 — OpenAI 모델은
`temperature=0`에서도 내부적으로 미세한 비결정성이 남아있을 수 있다(공식적으로 완전 결정론을
보장하지 않음). 따라서 `test_appeal_decision_flow_real_llm.py`는 여전히 "스모크 테스트"
성격을 유지하며, 실패 시 먼저 재실행으로 재현되는지 확인하는 절차(ARCH-001 §11-3)는 그대로
둔다. 다만 이번 수정으로 그 재현 빈도는 크게 낮아질 것으로 기대된다.

## 2026-07-08 — 질서위반행위규제법 제10조(심신장애)를 형법 개념으로 오인, 참조 조문(8~10조)도 통째로 누락

  양쪽 모두에 제7~10조를 함께 주입하도록 변경했다(`1867ef9`). 같은 커밋에서 도로교통법

## 2026-07-08 — merit 3단계(강함/보류/낮음)로는 "면제"와 "감경"을 구분 못함 → `merit_relief_type` 도입 과정에서 반복된 실측 트러블

| 항목 | 값 |
|------|-----|
| 발견 경로 | 질서위반행위규제법 제10조(심신장애) 관련 질의응답 — 위 항목에서 8~10조를 추가하다가, 10조①(면제)과 ②(감경)이 같은 조문 안에 공존한다는 것을 발견 |
| 영향 범위 | `ai/agents/appeal_decision_flow/{merit_gate.py, prompts.py, state.py, guide.py}` |
| 상태 | 구현 완료, 일부 한계 남음 |

### 증상

`merit`은 강함/보류/낮음뿐이라 **"처분 자체가 없어지는 사유"(면제)**와 **"처분은 유지되고
금액만 깎이는 사유"(감경)**를 구분하지 못했다. 둘 다 조문에 "명확히 해당"하면 LLM이 똑같이
`merit="강함"`을 주는데, 사용자 입장에서 "이의제기하면 처분이 없어질 수도 있다"(면제)와
"이의제기해도 처분은 유지되고 금액만 준다"(감경)는 완전히 다른 기대치다. 질서법 제10조가
①(면제)·②(감경)을 한 조문 안에 함께 규정하고 있어 이 문제가 특히 잘 드러났다.

### 원인 및 해결 — 4단계에 걸친 실측 트러블

`merit_relief_type`(면제/감경) 필드를 신설해 해결하려 했으나, 프롬프트·코드 수정 후 매번
실제 OpenAI API(`gpt-4o-mini`, temperature=0)로 검증할 때마다 새로운 오탐이 나와 총 4단계로
수정했다. 각 단계의 상세 실측 로그·근거는
[`면제·감경 사유 merit 구분 설계.md`](./면제·감경%20사유%20merit%20구분%20설계.md) §7과
[`면제·감경 relief_type 정확도 개선.md`](./면제·감경%20relief_type%20정확도%20개선.md)에
그대로 남겨뒀다 — 여기서는 무엇이 왜 반복됐는지만 요약한다.

1. **1차 구현(프롬프트만)**: "판단능력이 미약한 상태"(②=감경 사유)라고 명확히 썼는데도
   LLM이 계속 "면제"(①)로 잘못 분류했다 — 프롬프트에 "①/②를 표현 정도로 구분하라"는
   지시를 강화해도 재현됐다. **기능 자체가, 이 기능이 막으려던 오해(감경인데 면제로 오인)를
   그대로 재현한 것**이라 넘어갈 수 없었다.
2. **키워드 안전장치 추가**: RG의 "LLM 판단 앞에 키워드 매칭을 두는" 패턴을 반대로
   적용해, LLM 판단 **뒤에** "미약/약간/다소/조금/일부" 같은 정도완화 단어가 있으면
   면제→감경으로 강제 재보정하는 로직(`_downgrade_relief_type_if_hedged`)을 추가했다.
3. **문맥을 안 보는 부작용 발견 (리뷰 중 지적)**: 이 키워드 매칭이 사유 전체에서 정도완화
   단어만 찾다 보니, "감경" 개념 자체가 없는 순수 면제형 조문(142조5호 "장애인 승하차를
   돕느라 **다소** 지체", 8조 "표지판이 **일부** 가려짐", 도난 "**약간** 파손")까지
   감경으로 잘못 낮췄다 — 정당한 면제 사유를 과소평가하는 새 버그였다. "심신/판단/의식/정신"
   문맥 단어와 함께 있을 때만 재보정하도록 좁혀 해소했다.
4. **키워드 방식의 근본 한계 지적 → LLM 호출 분리**: "문맥이 제각각인데 키워드 목록으로
   다 못 잡는다"는 후속 지적에 따라, RG가 `is_identity_related`+`category`를 한 호출에서
   같이 물었다가 모순 응답이 나와 분리했던 선례(ARCH-001 §11-1)와 같은 교훈으로,
   relief_type 판단을 `merit="강함"`일 때만 실행하는 별도 LLM 호출(`RELIEF_TYPE_
   CLASSIFICATION_PROMPT`, `_call_llm_relief_type`)로 분리했다. **그런데 분리 직후 재검증에서
   똑같은 유형의 오탐이 또 나왔다** — 새 프롬프트가 "사유에 다소/약간이 있으면 감경"이라는
   규칙을 참조 조문과 무관하게 일반화해서, 142조5호를 또 감경으로 잘못 냈다(3번과 같은 실수를
   프롬프트가 반복). 최종적으로 프롬프트에 "① 사유가 정확히 어느 조·항에 해당하는지 먼저
   특정 → ② 그 항 자체의 법률 효과만 따르고 사유 표현으로 임의 판단 금지 → ③ 같은 조문
   안에 정도가 다른 항이 실제로 공존하는 경우(현재는 10조뿐)에만 예외 적용"이라는 순서를
   명시하고, 모델이 판단 근거를 먼저 밝히도록 `matched_clause` 필드를 추가해서 해소했다.

### 검증

2회 반복 결정론적 확인(실제 OpenAI API)으로 아래 4개 케이스가 전부 기대대로 나옴을 확인:
"판단능력이 미약함"(10조②)→감경, "의식 완전 상실"(10조①)→면제, "장애인 돕느라 다소
지체"(142조5호)→면제, "차량 도난, 약간 파손"(도난)→면제. `test/unit/
test_appeal_decision_flow_nodes.py`에 관련 테스트 총 13개 추가(파라미터화 포함),
`test/unit` + `test/integration` 전체 136개 통과.

### 남은 한계

- 키워드 안전장치(`_downgrade_relief_type_if_hedged`)는 여전히 "면제→감경" 한 방향,
  제한된 문맥 단어(심신/판단/의식/정신)에만 반응하는 최후 방어선이다 — 주력 판단을 2차
  LLM 호출로 옮겨 실제 노출 빈도는 줄었지만 완전히 대체되진 않았다.
- **부수 발견(별도 사안, 이번엔 안 건드림)**: 검증 중 "판단능력이 미약한 상태" 같은
  사유가 1차 `merit` 호출에서 아예 `merit="보류"`로 나온 적이 있었다(`merit="강함"`이
  아니면 relief_type 호출 자체가 생략됨). 감경형 사유를 모델이 "덜 확실한 사유"처럼
  과소평가하는 경향으로 보이는데, 이건 relief_type 정확도가 아니라
  `MERIT_CLASSIFICATION_PROMPT` 자체의 "강함" 판정 기준 문제다. 사용자에게 불리한 방향은
  아니라서(과대평가가 아닌 과소평가) 급하지 않다고 판단해 미루었다.
- `merit_basis`(LLM이 생성한 근거 요약 텍스트)는 여전히 조문 번호를 부정확하게 인용할 수
  있다(예: 실제론 ②인데 "제10조①"이라고 씀). `_structured_result()`에 노출되지 않아
  사용자에게 직접 보이진 않지만, 로그·디버깅 시 헷갈릴 수 있다.

## 2026-07-09 — LLM 호출 실패를 "판단이 애매함"(보류)과 구분 없이 리턴, 승산 있는 사유를 사용자가 오해로 포기할 위험

| 항목 | 값 |
|------|-----|
| 발견 경로 | `merit_relief_type` 작업 직후 예외 처리 경로 재점검 중 |
| 영향 범위 | `ai/agents/appeal_decision_flow/{merit_gate.py, state.py, guide.py}` |
| 상태 | 해결됨 |

### 증상

MG는 LLM 호출·파싱이 기술적으로 실패해도 안전하게 `merit="보류"`로 수렴하도록 설계돼
있었다(RG와 달리 안전 문제가 아니라는 이유로). 문제는 `guide_generation_node`가 이 "보류"를
**"사유를 검토했지만 애매하다"는 보류**와 **"기술적 실패로 아예 검토를 못 했다"는 보류**를
구분하지 못하고 똑같은 톤 문구를 붙였다는 점이다 — 실제로는 승산 있는 사유인데 일시적 API
오류로 판단 자체가 안 된 경우에도 사용자에게 "애매한 사유"라고 안내되어, 재시도해보면
"강함"이 나올 수도 있는 사유를 사용자가 지레 포기할 위험이 있었다.

### 원인

`merit_classification_node`의 예외 처리 경로(`except Exception`)와 `_VALID_MERIT` 밖의
값이 나온 경로가 둘 다 `{"merit": "보류", "merit_basis": "..."}`만 반환하고, 이게 "정상
검토 후 보류"인지 "기술적 실패로 인한 기본값"인지 구분할 상태 값이 없었다.

### 해결

`state.py`에 `merit_judgment_failed: Optional[bool]` 필드를 추가하고, LLM 호출 예외·응답
파싱 실패·유효하지 않은 merit 값 세 경로 모두에서 이 플래그를 `True`로 세우도록
`merit_gate.py`를 수정했다(`e9a1318`). `guide.py`(`_merit_risk_tone`)는 이 플래그가 서면
"판단이 애매하다"가 아니라 "판단을 못 했다, 재시도하면 다를 수 있다"는 별도 정정 문구를
기존 톤 앞에 덧붙이도록 했고, `_structured_result()`에도 이 값을 노출해 프로그램적으로도
구분 가능하게 했다. 이후 `merit_relief_type` 작업에서도 이 패턴을 재사용해, 실패 경로는
전부 `merit_relief_type=None`을 함께 반환하도록 일관되게 맞췄다.

### 검증

`test/unit/test_appeal_decision_flow_nodes.py`·`test/integration/
test_appeal_decision_flow_graph.py`에 실패 경로별 회귀 테스트 추가, 전체 통과.

명확히 구분된다.
