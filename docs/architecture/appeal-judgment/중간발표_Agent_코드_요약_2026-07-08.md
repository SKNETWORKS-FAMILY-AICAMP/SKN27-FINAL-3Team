# 중간발표 대비 — Agent 코드 요약 (질의응답용)

대상: `ai/agents/fine_notice_analysis`(OCR Agent), `ai/agents/appeal_decision_flow`(판단 Agent)
근거: 실제 구현 코드 + `docs/architecture/appeal-judgment/` 설계서 4종

---

## 0. 전체 그림 — 왜 Agent를 두 개로 쪼갰나

```
사용자 → Supervisor → OCR Agent(fine_notice_analysis) → Supervisor
                    → 판단 Agent(appeal_decision_flow) → Supervisor → 사용자
```

**단일 책임 원칙으로 분리**: OCR·문서 분류는 OCR Agent, 법적 판단·안내는 판단 Agent가
전담한다. 판단 Agent는 사용자와 직접 대화하지 않는다 — 입력이 부족하면(사유 미입력 등)
`status="input_required"`로 Supervisor에 되돌리고, Supervisor가 재질문한다.

누가 이 질문을 하면: **"왜 하나의 Agent로 안 만들었나?"**
→ OCR은 이미지 인식이라는 완전히 다른 기술 축(Vision)이고, 판단은 텍스트·법조문 기반
LLM 분류 축이라 책임이 다르다. 또 OCR 실패(이미지 품질 등)와 법적 판단 실패(사유 불충분
등)는 원인과 복구 방법이 달라서, 실패 처리 로직도 갈라놓는 게 자연스럽다.

## 1. OCR Agent (`fine_notice_analysis`) — "고지서를 구조화된 데이터로"

### 1-1. 파이프라인 (2노드)

```
ocr_node → confidence_verification_node → END
```

- `ocr_node` (`agent.py`): 이미지/PDF 입력 → GPT-4o Vision 1회 호출 → 21개 필드 추출 →
  자체 후처리(마스킹·날짜/숫자 정규화·fine_type 분류) → 1차 완결성 체크(`evaluate_ocr`)
- `confidence_verification_node` (`verification.py`): OCR 결과의 **형식** 유효성을
  V-01~V-05 규칙으로 재검증 → 최종 `ocr_status` 확정

이렇게 2단계로 나눈 이유: `ocr_node`는 "필드가 있는가/없는가"(존재 여부)를 보고,
`confidence_verification_node`는 "있는 값이 형식적으로 말이 되는가"(유효성)를 본다 —
둘을 합치면 한 함수가 너무 많은 책임을 지게 된다.

### 1-2. 핵심 설계 포인트 (질문받기 쉬운 부분)

**(a) `fine_type` 분류는 우선순위 7단계 키워드 매칭**
```python
if "즉결심판" in title and "과태료" not in title: return "범칙금"  # P-0
if "검찰" in authority:                            return "벌금"    # P-1
...
if any(kw in authority for kw in ("구청","시청")):  return "과태료"  # P-6
```
→ **왜 LLM이 아니라 키워드로 분류하나?**: `document_title`·`issuing_authority`는 GPT
Vision이 이미 추출한 값이라, 이 위에 다시 LLM 판단을 얹으면 이중 불확실성이 생긴다.
분류 기준 자체(서식명에 "범칙금"이 있으면 범칙금 등)가 명확한 룰이라 키워드 매칭이
더 결정론적이고 저렴하다. **벌금(형사처벌)은 서비스 범위 밖**이라 감지되면 즉시 거부.

**(b) 개인정보 이중 마스킹 (R-11)**
- `mask_personal_info()`: GPT 원문 응답 **전체**에 정규식으로 1차 마스킹(주민번호,
  차량번호 패턴 등) — JSON 파싱 **전에** 먼저 적용
- `mask_field()`: 파싱 후 `vehicle_number` 필드에 **다시** 한 번 코드 레벨 마스킹
→ **왜 두 번 하나?**: 1차는 GPT 응답 원문 전체(혹시 다른 필드에 개인정보가 섞여
나올 경우 대비, 방어적), 2차는 구조화된 필드 단위로 확실하게. 한쪽이 정규식 패턴을
놓쳐도 다른 쪽이 커버하는 이중 방어 구조.

**(c) `evaluate_ocr` — critical/important 2단 필드 구분**
```python
CRITICAL_FIELDS  = {"과태료": ["law_code","violation_text","notice_stage"], ...}
IMPORTANT_FIELDS = {"과태료": ["fine_amount","opinion_deadline",...], ...}
```
- critical 필드 하나라도 없으면 → `partial` (판단 Agent로 못 넘김, 재업로드 요청)
- important 필드만 없으면 → `degraded` (일단 진행, 누락 필드만 안내)
- 다 있으면 → `success`

→ **왜 두 등급으로 나눴나?**: `law_code`·`notice_stage`가 없으면 판단 Agent가 아예
분기를 못 탄다(치명적) 반면, `fine_amount`나 `issuing_authority`는 없어도 판정 로직에는
영향이 없고 안내 문구만 좀 아쉬워지는 수준이라 굳이 사용자에게 재업로드를 강요할 이유가
없다.

**(d) 서식 구조상 존재하지 않는 필드 예외 처리 (`_STRUCTURAL_ABSENT`)**
즉결심판 출석통지서는 애초에 `law_code`·`vehicle_number`가 인쇄되지 않는 서식이다.
이런 필드를 critical/important 체크에서 아예 빼서, "원래 없는 게 정상인 필드"를
"누락"으로 잘못 판정하지 않게 한다.

**(e) `confidence_verification_node`의 V-01~V-05 형식 검증**
- V-01/V-02: `notice_stage`·`fine_type`이 허용된 값 집합 안에 있는지
- V-03: `fine_amount`가 있다면 양수인지 (없는 건 OK — 즉결심판은 금액 필드 자체가 없음)
- V-04: `law_code`가 `"...법 제N조"` 같은 형식 정규식에 맞는지
- V-05 (`VALID_COMBINATIONS`): `(fine_type, notice_stage)` 조합이 실제 존재하는 4가지
  조합(과태료×사전통지/1차고지서, 범칙금×사전통지/즉결심판) 중 하나인지
→ 하나라도 걸리면 `ocr_status`를 `partial`로 **오버라이드**한다 — `ocr_node`가
`success`라고 판단했어도 형식이 이상하면 최종적으로는 막는다는 뜻. **오류가 있어도
V-01~V-05를 전부 실행**하는 이유는 재업로드 요청 시 "무엇이 문제인지" 한 번에 다
알려주기 위함(단계별로 하나씩만 알려주면 재시도 왕복이 늘어남).

**(f) `fine_type`에 따른 `next_actions` 분기**
- 과태료 + success → `["법률 근거 검색 노드 호출"]` (판단 Agent로 이어짐)
- 범칙금 + success → `["OCR 결과만 반환 — 이의신청 불가"]` (법원행정 영역이라 서비스
  범위 밖, 절차 안내만)

**(g) PDF는 10페이지 초과 시 즉시 거부** — Vision API 호출 비용·응답 크기 제어 목적으로
보임(코드에 명시적 사유 주석은 없음, 필요시 확인 권장).

### 1-3. 출력 상태값 5가지
`success`(완전) / `degraded`(important만 누락, 진행) / `partial`(critical 누락, 재업로드
요청) / `failed`(디코딩·GPT 호출 자체 실패) / `rejected`(벌금이거나 인식 불가 — 서비스
범위 밖)

## 2. 판단 Agent (`appeal_decision_flow`) — "이의제기가 승산이 있고 안전한가"

### 2-1. 파이프라인 (8노드, LangGraph)

```
fine_type 분기 ─(범칙금)→ 가이드 생성 → 출력
      │(과태료)
      ▼
deadline_gate_node → law_code_check_node → reason_intake_node
      │(기한 경과)                              │(사유 없음)
      ▼                                          ▼
   가이드 생성→출력                        재질문 요청→출력
                                                 │(사유 있음)
                                                 ▼
                                    risk_classification_node(RG) ∥ merit_classification_node(MG)
                                                 │ (병렬 실행)
                                                 ▼
                                          verdict_node → guide_generation_node → 출력
```

### 2-2. 핵심 설계 포인트 — **이 부분이 이 프로젝트의 가장 중요한 설계 결정**

**(a) 판정을 두 개의 독립 축으로 분리: RG(안전) vs MG(승산)**

| | RG (리스크 게이트) | MG (인정사유 분류) |
|---|---|---|
| 질문 | 이 사유가 **운전자를 특정**하는가 (신원노출·범칙금 전환 위험) | 이 사유가 **법조문상 인정 사유**에 해당하는가 (승산) |
| 왜 필요 | 과태료는 소유자 책임 원칙이라 운전자 미특정 상태로 처리되는데, 이의제기 과정에서 운전자가 드러나면 범칙금(형사절차)으로 전환될 수 있음 | 이의제기가 실제로 받아들여질 가능성 안내 |

→ **왜 하나의 점수로 합치지 않았나?** (자주 나올 질문): 점수를 더하거나 곱하면 "왜 이런
결과가 나왔는지" 설명이 불투명해지고, 법률자문처럼 보일 위험이 커진다. 대신 **6칸 조합
매트릭스**(risk 2값 × merit 3값)로 각 조합별 권고 톤을 미리 정의해뒀다(`guide.py`의
`_merit_risk_tone()`). 예: risk=true·merit=강함은 "조건부 위험"(1호 성공 시 무위험,
실패 시 범칙금 전환)으로 안내하지, "그냥 위험"으로 뭉뚱그리지 않는다.

**(b) RG와 MG는 구조가 다르다 — 의도적 비대칭**

- **RG는 2단계**(① 고신뢰 키워드 매칭 → ② LLM 분류): 도난 예외 체크 → 카테고리
  A(제3자 운전 주장)/B(명시적 전환 요청)/C(본인 운전 인정형) 키워드 매칭 → 안 걸리면
  2단계 LLM이 애매한 표현까지 판단
- **MG는 단일 LLM 호출**: 고정 참조 법조문(시행규칙 142조 등)을 컨텍스트로 주고 LLM이
  1회 판단

→ **왜 구조가 다른가?**: RG를 놓치면(false negative) 사용자가 실제 불이익(범칙금 전환)
을 당하는 **안전 문제**라 재현율을 우선해 이중 필터를 뒀다. MG는 애매해도 `merit="보류"`
로 안전하게 수렴할 뿐이라(안전 문제가 아님) 속도·단순성을 우선해 단일 호출로 설계했다.

**(c) 폴백(실패 시 기본값) 방향도 RG·MG가 다르다**
- RG 판단 실패(LLM 호출 오류, confidence="low" 등) → **`risk_flag=true`** (위험 쪽,
  놓치는 것보다 과잉 경고가 안전)
- MG 판단 실패 → **`merit="보류"`** (판단 유보)

→ 최근 리뷰에서 지적된 한계: MG가 LLM 호출 실패로 "보류"를 반환하면, 실제로는 승산이
강한 사유였어도 사용자에게는 "애매하다"고 안내돼 **실제로는 승산 있는 이의신청을
포기할 위험**이 있다 — "판단 유보"와 "시스템 오류로 판단 못함"이 구분 안 되는 게
현재 코드의 한계다. (개선안은 `04_RG_MG_품질검증_보완_설계서.md`에 정리해둠 — 재시도
+ 상태 필드 분리 + disclaimer 문구 분기)

**(d) 기한 계산이 `notice_stage`에 따라 완전히 다른 로직 (`deadline.py`)**
- 사전통지·즉결심판: 고지서에 인쇄된 `opinion_deadline`을 그대로 씀
- **1차 고지서**: 인쇄된 `opinion_deadline`은 법정 이의제기 마감이 **아니다** — 법정
  마감은 `notice_received_date`(수령일) + 60일로 **따로 계산**해야 한다(질서위반행위
  규제법 제20조, 도달주의).

→ 이게 왜 중요한 질문 포인트인가: "인쇄된 기한을 그대로 쓰면 안 되나?"라는 질문이
나올 수 있는데, 답은 "1차 고지서 단계에서는 인쇄 기한(납부기한)과 법정 기한(이의제기
마감)이 다른 개념이라 인쇄값을 그대로 쓰면 오안내가 된다"는 것. 다만 `notice_received_date`
는 OCR로 못 뽑는 값이라(고지서에 발송일 필드 자체가 없음), Supervisor가 사용자에게
별도로 물어 공급한다 — **없어도 하드블록하지 않고** `computed_deadline=None`으로 방어적
통과시키되, 가이드에 "법정 기한 계산 불가" 경고를 추가한다(선택 입력으로 완화한 이유는
"승산만 궁금한" 사용자가 수령일 없이도 판정을 받을 수 있게 하기 위함).

**(e) 위반유형(주정차 vs 비주정차)에 따라 MG가 다른 법조문을 주입**
시행규칙 142조는 원래 주정차 위반 전용 근거(도로교통법 160조 3항에서 위임)라, 비주정차
위반에는 대신 질서위반행위규제법 제7조(고의·과실 없음)를 참조로 쓴다. 위반유형은 새 필드
없이 OCR이 이미 주는 `law_code`가 32~34조(주정차 금지 조항)인지로 판별한다 — **`law_code`
는 인용 근거가 아니라 라우팅 신호로만 쓴다**는 원칙이 있다(개별 고지서 law_code를
그대로 인용하면 부정확할 수 있어서, 인용은 항상 사전 검증된 고정 조문만 쓴다).

**(f) 가이드는 판정과 분리된 공용 산출물 — 항상 6종 전부 출력**
①타임라인 ②기대치 조정 ③절차 방식 ④철회 가능 시점 ⑤벌점·전과 오해 정정 ⑥disclaimer.
`judgment_status`(성공/거부/불가)와 무관하게 6개 다 나간다 — 판정이 실패해도 사용자가
알아야 할 일반 정보(예: "이의제기가 항상 유리한 건 아니다", "벌점 40점 추가부과 조건")
는 그대로 제공해야 하기 때문.

**(g) `verdict_node`는 생각보다 하는 일이 적다**
실제 톤/문구 조합(6칸 매트릭스)은 `guide_generation_node`가 담당하고, `verdict_node`는
`judgment_status="success"` 고정 + `notice_stage`에 따른 라벨(`overall_possibility`)만
정한다. **RG·MG 결과값 자체는 건드리지 않고 그대로 통과**시킨다 — "판정 통합"이라는
이름과 달리 실질적인 통합 로직(매트릭스)은 가이드 노드에 있다는 점은 헷갈리기 쉬운
부분이라 질문받으면 명확히 구분해서 답해야 한다.

### 2-3. 알려진 한계 (질문 나오면 회피하지 말고 인정할 부분)

1. **142조 6호(포괄조항)류 표현의 정확도를 별도로 측정한 전용 테스트셋이 없다** —
   1단계 키워드는 1~5호 시드만 커버, 6호·14조 정황요소는 전부 2단계 LLM에 위임되는데
   이 경로만 격리한 정확도 측정이 아직 없음
2. **LLM 호출 실패와 실제 "애매함" 판단이 사용자에게 구분되지 않는다** (위 2-2c) —
   기술적 실패가 안전한 방향(보류/위험)으로 흡수되긴 하지만, 그 결과 승산 있는 사유를
   포기하게 만들 수 있음
3. **패러프레이즈 강건성 테스트가 없다** — `temperature=0`은 같은 입력에 대한 재현성만
   보장하지, 같은 의미의 다른 문장이 같은 판정을 받는지는 별도로 검증한 적 없음
4. 위 3가지는 `docs/architecture/appeal-judgment/04_RG_MG_품질검증_보완_설계서.md`에
   개선 설계를 정리해둠 (아직 미구현, 설계 단계)

## 4. 예상 질문 빠른 대응표

| 예상 질문 | 핵심 답변 한 줄 |
|---|---|
| RG랑 MG 왜 따로 계산해요? | 안전(신원노출)과 승산(법적 인정)은 독립적인 문제라 합치면 판단 근거가 불투명해짐 |
| 왜 RG는 2단계, MG는 1단계예요? | RG는 놓치면 실제 불이익(안전 문제)이라 재현율 우선 이중 필터, MG는 애매해도 "보류"로 안전 수렴이라 단순 구조 |
| LLM 실패하면 어떻게 돼요? | RG는 위험 쪽(risk_flag=true), MG는 보류 쪽 — 안전한 방향으로 폴백. 단, 현재는 "진짜 애매함"과 "시스템 오류"가 사용자에게 구분 안 되는 한계가 있고 개선 설계는 이미 문서화함 |
| 1차 고지서 기한은 왜 따로 계산해요? | 인쇄된 납부기한 ≠ 법정 이의제기 마감(수령일+60일). 도달주의 원칙 때문에 수령일 기준으로 별도 계산 필요 |
| OCR이랑 판단을 왜 분리했어요? | 단일 책임 원칙 — Vision 기반 인식과 텍스트 기반 법적 판단은 실패 원인·복구 방법이 달라서 |
| degraded/partial 차이가 뭐예요? | critical 필드(law_code 등) 없으면 partial(재업로드 요구), important 필드(금액 등)만 없으면 degraded(일단 진행) |
| 벌금은 왜 처리 안 해요? | 벌금은 형사처벌이라 서비스 범위(행정 이의제기) 밖 — OCR 단계에서 감지 즉시 거부 |
| 개인정보는 어떻게 지켜요? | GPT 응답 원문 전체 1차 마스킹 + 구조화 필드 2차 마스킹, 이중 방어 |
| temperature=0인데 왜 결과가 흔들려요? | temperature=0은 같은 입력의 재현성만 보장, OpenAI 모델은 완전한 결정론을 공식 보장하지 않음. 실제 API 테스트 7개는 그래서 스모크 테스트로 운영 |
