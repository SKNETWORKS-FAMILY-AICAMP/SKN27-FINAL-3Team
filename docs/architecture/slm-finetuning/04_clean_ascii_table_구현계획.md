## 목표

`law_chunks.provision_text`(또는 그걸 소비하는 지점)에서 박스 드로잉 문자·과도한 반복
공백·표 테두리 잔재를 제거해, 사람이 읽을 수 있는 텍스트로 정리한다. 표 안의 정보(위반유형
· 조문 · 금액 등) 자체는 보존해야 한다 — 단순히 문자를 지우기만 하면 열 구분이 사라져서
"신호·지시 위반 제5조 7만원"처럼 의미가 뭉개질 위험이 있다.

## 문제 상세 (실제 예시)

`law_chunks`에 저장된 원문(도로교통법 시행령 별표8 조각):

```
┃4. 신호·지시 위반                │제5조               │1) 승합자동차등: 7만원    ┃

┃5. 중앙선 침범, 통행구분 위반     │제13조제1항부터 제  │2) 승용자동차등: 6만원    ┃
```

이 방식대로면 원본 PDF/HTML의 표(위반유형 | 조문 | 범칙금액 3열 표)가 파싱 과정에서
텍스트로 평면화되면서 각 셀 사이에 박스 문자와 정렬용 공백이 남은 것으로 보인다. 셀 내용이
길면 다음 줄로 넘어가면서(`5. 중앙선 침범...` → 다음 줄에 `제13조제1항부터 제`) 한 항목이
여러 줄에 걸쳐 쪼개지기도 한다 — 단순 문자 제거만으로는 이 줄바꿈 문제를 못 푼다.

## 설계 옵션 (결정 필요 — 다시 볼 때 여기부터)

### 옵션 A — 적재(ingestion) 시점에 정리, DB에 클린 텍스트 저장

- 위치: `etl/legal/ingestion/`(파서 단계)
- 장점: 한 번 고치면 모든 소비자(law_ground_search Agent, SFT 파일럿, 향후 다른 Agent)가
  자동으로 혜택. `law_chunks` 자체가 깨끗해짐.
- 단점: 기존 99,315개 행에 대한 **백필(backfill) 마이그레이션**이 필요 — 재적재 스크립트
  실행 또는 UPDATE 쿼리. 원본 파싱 로직을 건드리므로 회귀 위험이 상대적으로 큼(다른 Agent
  들이 이미 이 데이터를 쓰고 있음).

### 옵션 B — 조회(query) 시점에 정리, DB는 원본 그대로

- 위치: `etl/legal/search.py::search_laws()`(결과 반환 직전) 또는 그 상위 소비자
  (`ai/agents/law_ground_search/search.py`, `etl/legal_sft/build_pilot_dataset.py`)
- 장점: DB 마이그레이션 불필요, 회귀 위험 낮음(적재 로직 안 건드림), 소비자별로 다르게
  적용 가능(예: SFT는 정리하고 다른 곳은 원문 유지하는 것도 가능).
- 단점: 여러 소비자가 각자 정리해야 해서 중복 위험 — 공용 유틸(`etl/common/` 등)로
  빼서 재사용해야 함. 원본 DB는 계속 지저분한 채로 남음(다른 직접 쿼리·디버깅 시 불편).

### 옵션 C — 둘 다: 공용 함수는 `etl/legal/` 유틸로 만들고, 우선 조회 시점(B)에 적용 →
검증되면 나중에 적재 시점(A) 마이그레이션으로 승격

- 이번 세션에서 가장 현실적인 절충안으로 보임(재검토 시 확정) — 마이그레이션 없이 빠르게
  체감 개선을 얻고, 부작용 없다고 확인되면 A로 넘어감.

**미해결 설계 문제**: 단순 문자 제거·치환만으로는 "여러 줄에 걸쳐 쪼개진 셀"(위 예시의

**표 구조 자체를 다시 파싱**(줄 단위로 박스 문자 위치를 보고 열 경계를 추정 → 행 단위로

주장한 것보다 실제로는 더 큰 작업일 가능성 — 재검토 시 이 부분부터 다시 따져볼 것.
