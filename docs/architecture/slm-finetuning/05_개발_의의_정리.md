## 배경

`01_SFT설계서.md`(SFT-ARCH-001)의 원래 전제("Supervisor가 최종 답변 생성에 호출하는 대형

그것도 참고 가격표만 있으면 됨)이 드러났다. 이 문서는 그 논의 끝에 남은, **실제로 유효한
개발 의의**를 정리한다.

## 최우선 의의 — SLM 여부와 무관하게 필요한 것

`compose_agent_response()`(`app/services/chat_orchestration_service.py:144-178`)는 지금
각 Agent의 하드코딩 템플릿 `summary` 문자열을 이어붙이기만 한다 — `law_ground_search`가
정확한 조문을 찾아도 사용자는 "조문 3건 검색됨" 같은 진단 문구만 받는다. **"근거→답변
합성" 기능 자체가 없다는 게 근본 문제이며, 이건 SLM으로 하든 대형 LLM을 실시간 호출하든
반드시 만들어야 하는 기능이다.**

## 진짜 결정 포인트 — 왜 하필 자체 SLM인가 (vs 대형 LLM 실시간 호출)

비용·평가 비교군이 결정 요인이 아니라면, 아래가 남는 이유다. 강한 순서로 정렬:

| 순위 | 근거 | 강도 |
|---|---|---|
| 1 | **데이터 프라이버시** — 사고 경위·개인 사정 같은 민감한 상담 내용이 매 요청마다 외부(OpenAI)로 전송되지 않음 | 가장 흔들리지 않는 근거 |
| 2 | **트래픽 성장 대비 선제적 투자** — 지금은 트래픽 0이라 비용이 안 느껴지지만, 서비스가 커지면 결국 문제가 됨. 데이터 파이프라인(합성데이터 생성·품질검수 체계, `etl/legal_sft/`)만이라도 지금 만들어두면 나중에 급하게 전환할 필요가 없음 | 강함(단, ROI 시점은 트래픽 규모에 달림 — 미계산) |
| 3 | **벤더 종속 탈피** — OpenAI API 하나에만 의존하지 않는 자체 역량 확보 | 중간 |
| 4 | **레이턴시** — 로컬 서빙이면 외부 API 왕복이 없음 | 중간(로컬 GPU 서빙 자체의 인프라 복잡도와 상쇄될 수 있음) |
| 5 | **행동 통제 강건성** — 프롬프트가 아니라 학습으로 "이 근거만 인용, 애매하면 발뺌"을 박아넣으면 더 일관될 거라는 가설 | **부분 검증됨(완전 기각 안 됨)** — §7-1 게이트를 실제로 실행(gpt-4o-mini, `test.jsonl` 27건, 비용 $0.006): 정밀도 1.000·재현율 0.400·포맷준수율 0.963·헤징정확도 0.630. 근거가 멀쩡한데도 헤징하는 사례(`dangerous_driving`)가 있어 프롬프팅만으로는 행동이 불안정함을 확인 — 파인튜닝 투자 근거 확보. 다만 표본이 작고(n=27) gold 품질 이슈가 섞여 있어 단정적 결론은 아님(`01_SFT설계서.md` §7-1) |

| 근거 | 왜 폐기됐나 |
|---|---|

| "비교군(대형 LLM)이 있어야 평가할 수 있으니까" | §7의 5개 지표 중 4개(정밀도·재현율·포맷 준수율·저신뢰도 문구 정확도)는 `test.jsonl` gold 라벨 대비 절대 평가로 충분. 비교가 필요한 건 latency/비용 하나뿐이고, 그것도 실제 비교 시스템이 아니라 참고 가격표(예: GPT-4o-mini $0.15/$0.60 per 1M 토큰)만 있으면 됨 |

## 결론 한 줄 (2026-07-14 기준 — 2026-07-15 재검토로 뒤집힘, 아래 새 섹션 참고)

**이 프로젝트의 의의는 "비용 절감"이 아니라 "프라이버시 확보 + 향후 확장을 위한 선제적
파이프라인 구축"이다.** 평가 하네스(§7)는 비교군 없이 지금 바로 시작할 수 있고, §7-1
게이트 실행으로 순위 5(행동 통제 강건성) 가설도 부분 검증됐다 — 다만 `test.jsonl`의 gold
`output`이 사람이나 대형 LLM이 검증한 "좋은 답변"이 아니라 규칙 기반 템플릿이라는 점은
남아있는 별개의 데이터 품질 문제였다. **2026-07-14 갱신**: 이 문제의 상당 부분(gold가
카테고리 주제는 맞지만 질의가 요구하는 정보를 실제로 담고 있는지 확인 안 되던 문제, D그룹)
을 자동 필터로 해결했다 — `03_파일럿_품질검수_발견사항.md`·`01_SFT설계서.md` §8-14 참고.

## 2026-07-15 재검토 — SLM 투자 보류

2026-07-15, 두 가지 전제 변화를 계기로 위 순위표(§진짜 결정 포인트, 2026-07-14 기준)를
다시 검토했다 — (1) 보안·프라이버시 처리를 AWS 인프라 쪽에서 담당하기로 함, (2) RAG
검색 성능 자체는 이미 양호하다는 판단. 이 두 전제로 순위 1·5를 다시 짚어보니 둘 다
무너졌고, 새로 발견한 사실(아래 3번)까지 더해져 결론이 바뀌었다.

1. **순위 1(데이터 프라이버시) 재검토** — "가장 흔들리지 않는 근거"였던 이 항목이 AWS
   처리 방식에 따라 무력화될 수 있음을 확인했다. Django 백엔드를 AWS에 올려두고 OpenAI
   API를 그대로 호출하는 것뿐이라면 상담 내용은 여전히 OpenAI로 나가 프라이버시 문제가
   해결된 게 아니다. 반면 AWS Bedrock처럼 자체 AWS 계정/VPC 경계 안에서 파운데이션
   모델을 호출하는 방식이면(Bedrock은 기본적으로 고객 데이터를 모델 학습에 재사용하지
   않음), 커스텀 SLM 없이 범용 모델만으로도 같은 프라이버시 요건을 충족한다. **"AWS에서
   처리"가 정확히 어느 방식인지는 아직 팀 확정 사항이 아니다 — 이것부터 확정이
   필요하다(§액션 아이템 참고).**

2. **순위 5(행동 통제 강건성) 재검토 + 근본적인 반례 발견** — §7-1 게이트가 채점 기준으로
   쓴 `test.jsonl`의 gold `output` 자체가 `etl/legal_sft/build_pilot_dataset.py::
   build_output_text()`라는 **규칙 기반 템플릿**으로 생성된다는 점을 다시 확인했다.

   ```python
   if low_confidence or not gold:
       return "검색된 근거의 신뢰도가 낮아 정확한 조문을 특정하기 어렵습니다. 추가 확인이 필요합니다."
   parts = []
   for g in gold:
       title = f"{g.article_title}" if g.article_title else "관련 조문"
       parts.append(f"{title}({g.source_ref})에 따르면 {g.provision_text}")
   return " ".join(parts)
   ```

   이 로직은 조건문 몇 줄로 "gold면 인용 조립, 아니면 고정 한정 문구"를 결정하며, 정의상
   100% 정확하다(규칙이 곧 정답이므로 오답·헤징 오류 자체가 있을 수 없음). 그런데 §7-1
   게이트 실측(gpt-4o-mini)은 이 템플릿이 만든 정답을 근사하는 것조차 재현율 0.400·헤징
   정확도 0.630으로 완벽하지 못했다 — **LLM이 그 정답을 만드는 규칙 자체보다 부정확했다.**
   즉 "인용 규율을 학습으로 박아넣으면 더 일관될 것"이라는 순위 5 가설은, 정답 생성
   메커니즘이 이미 결정론적 규칙이라는 사실 앞에서 방향이 뒤집힌다 — 이 핵심 태스크
   ("정답만 인용 + 근거 약하면 헤징")는 규칙 기반이 LLM(프롬프트든 파인튜닝이든)보다
   더 정확하고, 감사 가능하고, 인프라·라이선스 비용이 없다.

3. **남은 순위(2·3·4)도 "SLM"을 특정해서 뒷받침하지 않는다** — 순위 2(선제 투자)가
   지금 만들어둬야 한다고 말하는 자산은 "파인튜닝된 SLM 가중치"가 아니라 "잘 만들어진
   규칙 기반 합성 엔진 + 평가 체계"로 대체 가능하다. 순위 3(벤더 종속 탈피)은 Bedrock
   같은 멀티 모델 게이트웨이로 상당 부분 해소된다. 순위 4(레이턴시)는 규칙 기반 로직이
   추론 자체가 없어 SLM보다도 더 빠르다.

### 결론

**커스텀 SLM(QLoRA 파인튜닝) 학습·배포는 보류한다.** 대신:

- `compose_agent_response()`(§8-12 미결 사항)에는 `build_output_text()`류 규칙 기반
  합성 로직을 직접 연결하는 것을 1차 해법으로 채택한다 — evidence를 받아 정답 인용
  또는 한정 문구를 결정론적으로 조립.
- 문장을 더 자연스럽게 다듬는 게 필요하면(여러 근거를 매끄러운 문단으로 종합, 사용자
  질문 표현에 맞춘 어조), 그 역할만 파인튜닝 없는 범용 모델(프롬프트 호출)에 맡긴다 —
  "무엇을 인용할지"는 규칙이 결정하고 LLM은 "어떻게 표현할지"만 맡아, LLM이 실수해도
  리스크가 "어색한 문장" 수준으로 낮아지고 "틀린 조문 인용" 같은 치명적 오류로는 안
  이어지는 구조.

이건 이미 투자한 것(파일럿 데이터셋 1,905건, `ai/evaluation/` 평가 하네스,
`ai/training/train_qlora.py`)이 헛수고라는 뜻은 아니다 — 이 작업들이 정확히 "SLM을
만들어야 하는가"를 실측으로 검증하는 게이트 역할을 했고, GPU 인프라·모델 라이선스(§8-15,
EXAONE NC 라이선스 등)까지 딸린 더 큰 투자를 사전에 걸러낸 것이다. 데이터셋과 평가
하네스는 폐기하지 않고, 트래픽이 실제로 커져 이 판단을 재검토할 시점을 위한 자산으로
남겨둔다.

### 액션 아이템

1. `compose_agent_response()`에 규칙 기반 합성 로직을 연결하는 작업 착수(§8-12의 대체
   해법 — SLM 통합이 아니라 규칙 기반 통합으로 범위 축소).
2. "보안 처리를 AWS에서 담당"이 정확히 어떤 방식인지(Bedrock 등 자체 계정/VPC 내 모델
   호출 vs 단순 인프라 호스팅) 팀 차원에서 확정 — 결과에 따라 위 결론(순위 1 재검토)이
   다시 바뀔 수 있음.
3. QLoRA 학습 실행(`ai/training/train_qlora.py`을 실제 GPU에서 돌리는 것)은 이 재검토
   결론이 다시 뒤집히기 전까지 보류.
