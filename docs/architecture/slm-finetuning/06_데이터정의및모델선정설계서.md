## 1. 개요 및 목적

sLLM 파인튜닝에 바로 착수하지 않고, 아래 순서로 선행 확정한다.

1. 어떤 데이터를 얼마나 쓸지 (팀 보유 데이터 + 팀원 개별 데이터 취합) — §2
2. 입력(input)/출력(output)을 어떤 형태로 정의할지 — §3
3. 위 정의에 맞는 sLLM 모델군을 무엇으로 추천받아 파인튜닝할지 — §4

이 순서를 지키는 이유는 SFT-ARCH-001 §1의 원칙과 동일하다 — 데이터·스키마가 확정되지 않은 채
모델부터 고르면, 모델 선택 기준(컨텍스트 길이, 다국어/한국어 성능, 파라미터 규모) 자체가
근거 없이 정해진다. 반대로 데이터·스키마를 먼저 고정하면 모델 후보를 "이 스키마를 이 정도
데이터량으로 학습시켰을 때 성능이 나올 후보"로 좁혀 추천받을 수 있다.

### 2-2. 데이터 규모 계획

| 단계 | 규모 | 상태 |
|---|---|---|
| 파일럿 | 381건 (27/27 카테고리 커버리지 확인) | 완료 — mock 모드로 파이프라인 구조 검증, real 모드로 end-to-end 검증 |
| **1차 정식 학습셋** | 목표 1,500~2,000건 → **실제 1,905건** | ✅ **완료**(2026-07-14). 당초 계획한 "`--seed` 변경 재실행"이 아니라 **paraphrase 증강**(gpt-4o-mini 배치 호출, 카테고리당 1회) 방식으로 확장 — 검색 캐싱(카테고리당 임베딩 호출 381회→27회)까지 함께 구현해 실비용 $0.0188에 완료 |
| 팀원 데이터 반영 이후 | 미정 | §5-1 취합 결과에 따라 재산정 — **주의: §5-4 원래 권장 순서(팀원 데이터 취합 후 확장)를 지키지 못하고 먼저 진행됨**(위 표지 안내 참고) |

### 2-3. 데이터 생성 방식

1. **합성 데이터 (1단계 유일 경로)**: `law_chunks`에서 정답 조문 1건 고정 + 같은 `domain_tags`의
   오답 distractor 1~2건을 섞어 `evidence` 배열을 구성한다. 정답 응답은 규칙 기반 템플릿으로
   생성한다(SFT-ARCH-001 §4-4 항목4). 표현 다양성은 **paraphrase 증강**(gpt-4o-mini 배치
   호출)으로 확보했다 — 원본 질의의 의도(위반유형·질문 유형)는 유지한 채 표현만 다양화하도록
   프롬프트로 제약.
2. **품질 검수 안전장치 (5단계로 확장됨, 최초 3단계에서 증가)**: 조문 내용 유효성(폐지·공백·
   표조각) → 법령명 일치 → 조문 신뢰성(별표는 점수만, 일반 조문은 키워드 매칭) → **수치
   요구 질의 필터**(D그룹, "벌점 몇 점?" 질의인데 후보에 숫자가 없으면 신뢰 안 함, 신규) →
   최종 점수 임계값(0.6). 다섯 단계 전부 통과해야 gold로 승격, 하나라도 걸리면 정직하게
   `low_confidence=True`로 처리한다(SFT-ARCH-001 §8-14 D그룹, `03_파일럿_품질검수_발견사항.md`).
3. **운영 로그 재사용(향후)**: 서비스 운영 개시 후 로그가 카테고리당 의미 있는 표본을 넘기면
   합성 데이터를 실사용 분포로 점진 대체한다(SFT-ARCH-001 §8-1b).

## 3. 입력(Input) / 출력(Output) 스키마 정의

### 3-1. 태스크 정의

이 sLLM이 학습하는 태스크는 **"법 지식을 암기해서 답하는 것"이 아니라 "검색된 근거(evidence)를
보고 정답만 골라 인용하고, 근거가 약하면 과신하지 않는 행동"**이다 (RAFT: Retrieval-Augmented
Fine-Tuning 패턴, SFT-ARCH-001 §1 원칙 1). 법 조문 원문은 SLM 파라미터에 암기시키지 않는다 —
법이 개정되면 RAG가 최신 조문을 다시 검색해오므로, SLM은 매번 새로 주어지는 근거를 "다루는 법"만
학습하면 된다.

### 3-2. 스키마 (JSONL, 한 줄당 한 학습 예시)

```json
{
  "instruction": "사용자 질의와 evidence 배열을 보고, 정답 근거만 인용해 답변하라. 근거가 약하면 단정하지 말 것.",
  "input": {
    "query": "안전띠 미착용 하면 처벌이 어떻게 돼?",
    "evidence": [
      {
        "source_ref": "...", "chunk_id": "...", "source_name": "...", "source_type": "law",
        "article_no": "제50조", "appendix_no": null, "article_title": null,
        "provision_text": "...", "source_url": "...", "retrieval_score": 0.605,
        "match_reason": "vector_search_keyword_matched"
      }
    ]
  },
  "output": "관련 조문(제50조)에 따르면 ...",
  "_meta": {"category_code": "seatbelt_violation", "category_type": "violation_type", "low_confidence": false}
}
```

| 필드 | 정의 | 비고 |
|---|---|---|
| `instruction` | 모든 예시에서 고정 문자열 | 태스크 자체가 고정돼 있어 예시마다 달라질 이유 없음 |
| `input.query` | 사용자 질의 원문 | `storage/rag/law_query_terms.yaml`의 27개 카테고리 `user_terms` 기반 템플릿 생성 |
| `input.evidence[]` | 검색된 근거 배열(정답 1~2건 + distractor 0~2건, 총 2~4건) | `law_ground_search` Agent의 실제 출력 envelope과 필드명 동일 — 연동 계약을 바꾸지 않는다 |
| `output` | 근거를 인용한 자연어 답변, 또는 저신뢰도 한정 문구 | `low_confidence=true`면 "검색된 근거의 신뢰도가 낮아 정확한 조문을 특정하기 어렵습니다. 추가 확인이 필요합니다." 고정 문구 |
| `_meta` | 카테고리·저신뢰도 플래그 등 검수·분석용 | 학습 스크립트는 무시 |

### 3-3. Distractor 비율

실 검색이 완벽하지 않다는 전제를 반영해 evidence 배열은 **정답 1~2건 + 오답 1~2건**을 기본
비율로 섞는다(SFT-ARCH-001 §4-3). 오답이 없는 "깨끗한" 예시만 학습하면 실 서비스의 노이즈
섞인 검색 결과에 취약해진다.

## 4. sLLM 모델 선정

### 4-1. 모델 추천 요청 기준

아래 조건을 만족하는 모델군을 추천 대상으로 한다.

| 기준 | 값 | 근거 |
|---|---|---|
| 파라미터 규모 | 7B급 (QLoRA로 로컬/단일 GPU 학습 가능한 범위) | §5-2 GPU 자원 제약 |
| 한국어 성능 | 법령·판례 한국어 문어체 이해 필수 | 도메인이 한국 교통법규 |
| 컨텍스트 길이 | evidence 2~4건(조문 원문 포함) + 질의를 한 번에 담을 수 있는 길이 | §3-2 스키마 |
| 파인튜닝 방식 | QLoRA 지원(어댑터 기반, 베이스 모델 교체 비용 낮음) | SFT-ARCH-001 §6 |
| 서빙 경로 | 어댑터 merge → GGUF 변환 → `langchain-ollama` 연동 가능 | 기존 시스템 연동 조건 |

### 4-2. 현재 검토 중인 후보 (최종 확정 아님)

| 후보 | 특징 | 라이선스 | 확정 여부 |
|---|---|---|---|
| Qwen2.5-7B-Instruct | 다국어·한국어 성능 준수, QLoRA 생태계 자료 풍부(Unsloth 공식 지원) | Apache 2.0 (상업적 이용 제한 없음) | SFT-ARCH-001 §6 기본값으로 채택 |
| EXAONE-3.5-7.8B-Instruct | 한국어 벤치마크에서 Qwen2.5-7B를 크게 앞섬(KoMT-Bench 7.96 대 5.19, LogicKor 9.08 대 6.38) | **EXAONE AI Model License Agreement 1.1 - NC(비상업적 용도 한정)** | 미확정 — 라이선스 조건 검토 선행 필요(SFT-ARCH-001 §8-15) |

두 후보는 SFT-ARCH-001 §6에서 이미 언급된 후보를 그대로 승계한다. **본 문서 작성 시점 기준
추가 모델 추천은 아직 받지 않은 상태**이며, §3의 스키마·데이터 규모가 확정된 뒤 이 기준(§4-1)에
맞춰 정식으로 추천을 요청한다. EXAONE-3.5-7.8B-Instruct는 성능상 유력하지만 라이선스가
비상업적 용도로 한정돼 있어, 이 프로젝트가 상업적 서비스를 전제로 한다면 팀 차원에서 상업적
운영 여부를 먼저 확정한 뒤 후보 유지 여부를 결정해야 한다(SFT-ARCH-001 §8-15).

### 4-3. 후보 비교 절차

1. **QLoRA 착수 전 게이트(이미 실행됨)**: gpt-4o-mini 프롬프트 전용 프로토타입으로 `test.jsonl`
   27건을 채점 — 인용 정밀도 1.000(n=6), 재현율 0.400(n=15), 포맷 준수율 0.963, 헤징 정확도
   0.630. 프롬프팅만으로는 헤징 정확도가 불안정해 파인튜닝 투자 근거를 확보했다(SFT-ARCH-001
   §7-1).
2. **모델 후보 비교(§4-2의 후보 확정 이후 실행 예정)**: 동일 `test.jsonl`을 각 후보 모델에
   QLoRA 파인튜닝 후 `ai/evaluation/run_eval.py`로 채점, 인용 정밀도·재현율·포맷 준수율·헤징
   정확도·latency·비용(G4) 기준으로 비교한다. **학습 스크립트는 작성 완료**(`ai/training/
   train_qlora.py`, Unsloth+trl SFTTrainer, 기본 베이스 모델 Qwen2.5-7B-Instruct) — GPU
   자원(§5-2)만 확보되면 바로 실행 가능한 상태다. §7-1과 같은 프롬프트 포맷을 재사용해
   비교 조건을 맞춰뒀다.

## 5. 미결 사항

### 5-1. 팀원 개별 데이터셋 취합 (신규, 최우선)

팀원 각자가 보유한 데이터셋(수집 중이거나 아직 공유되지 않은 것 포함) 목록이 아직 취합되지
않았다. §2-1 인벤토리의 "팀원별 개별 보유 데이터셋" 행을 채우는 것이 §2-2 규모 재산정과 §3
스키마 확장(팀원 데이터가 새로운 도메인·형식을 포함할 경우) 여부를 결정하는 선행 조건이다.

### 5-2. GPU 학습 자원

팀 공식 결정은 아직 없음 — 다만 RunPod(GPU 대여) + Unsloth 조합으로 진행하는 방향으로
논의 중(2026-07-14). 학습 스크립트(`ai/training/train_qlora.py`)는 이 조합을 전제로
작성돼 있다. QLoRA라도 7B급 모델은 16~24GB 이상 VRAM 필요(SFT-ARCH-001 §8-3).

### 5-3. 모델 최종 확정

**Qwen2.5-7B-Instruct가 학습 스크립트의 기본값으로 채택됨**(SFT-ARCH-001 §6, 2026-07-14)
— Unsloth 공식 지원 모델(2026-07-14 확인)이고 Apache 2.0 라이선스라 상업적 이용 제약이
없다는 게 근거. 다만 이건 "당장 실행 가능한 기본값"이지 §4-3 절차로 실측 비교해 확정한 게
아니다 — 멘토 추천 결과를 받으면 §4-1 기준표와 대조하고 §4-3 절차로 실측 비교해 최종
선정한다. EXAONE-3.5-7.8B-Instruct는 한국어 성능은 유력하지만 비상업적(NC) 라이선스라
후보에서 보류 중(§4-2, SFT-ARCH-001 §8-15).

### 5-4. 1차 정식 학습셋 확장 시점 — ⚠️ 권장 순서를 지키지 못하고 이미 진행됨

당초 §2-2의 1,500~2,000건 확장은 §5-1(팀원 데이터 취합)이 끝난 뒤 착수하는 것을
권장했었다 — 취합 전에 먼저 확장하면 팀원 데이터 반영 시 재작업 범위가 커지기 때문.
**그런데 2026-07-14, §5-1이 아직 미착수인 상태에서 1차 정식 학습셋(1,905건)을 이미
생성 완료했다.** 팀원 데이터가 나중에 취합되면 카테고리 재정의·재생성이 필요할 수 있다는
리스크를 안고 진행된 것이므로, 멘토/팀 논의에서 이 순서 이탈을 투명하게 공유할 필요가 있다.
