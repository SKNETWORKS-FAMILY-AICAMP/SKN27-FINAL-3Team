## 1. 오늘 회의에서 내가 해야 할 일

오늘 내 역할은 구현자가 아니라 PM이다. 팀원별 산출물이 다음 주 구현으로 바로 이어지도록 범위, 입력, 출력, 완료 기준을 정리해야 한다.


| 내 역할        | 해야 할 일                                                      | 결과물                 |
| ----------- | ----------------------------------------------------------- | ------------------- |
| 회의 진행       | 이슈별 코멘트를 기준으로 안건을 순서대로 진행한다.                                | 결정/보류/검증 필요 항목 분류   |
| 범위 통제       | 문서에 없는 기능 추가, 모델 확정, API 확정을 막는다.                           | 미확정 항목은 `검증 필요`로 기록 |
| 담당자 정렬      | 각 팀원이 자기 담당 범위만 말하게 하고, 다른 담당 영역은 연결 지점만 정한다.               | 담당자별 다음 액션          |
| 구현 착수 조건 확인 | 다음 주 구현에 필요한 schema, routing, sample, model 후보가 준비됐는지 확인한다. | 구현 전 체크리스트          |
| 이슈 업데이트 관리  | 회의 결정 내용을 GitHub 이슈 코멘트에 추가한다.                              | 이슈별 회의 결정 코멘트       |

## 9. 다음 주 구현 착수 기준


| 영역                 | 구현 착수 전 필요한 상태                                    |
| ------------------ | ------------------------------------------------- |
| 화면                 | 홈→로그인→챗봇→결과/리포트 흐름이 확정되어야 한다.                     |
| 공통 schema          | Agent 결과 공통 필드와 상태값이 확정되어야 한다.                    |
| 고지서 OCR·과태료/범칙금 분석 | 필수 필드, 누락 필드 처리, 샘플 검증 방식이 정해져야 한다.               |
| 법률 근거 검색           | 법률 데이터 범위와 호출 조건이 정해져야 한다.                        |

| 영상·이미지 분석          | 후보 모델, 입력, 출력, confidence 기준, 개인정보 리스크가 정리되어야 한다. |
| QA                 | Cross-MVP 통합 시나리오와 리스크 로그가 있어야 한다.                |


## 10. PM으로서 회의에서 지켜야 할 원칙

1. 정해지지 않은 것은 확정처럼 말하지 않는다.
2. 담당자가 아닌 사람이 다른 담당 범위를 확정하지 않게 한다.
3. 모델명보다 입력/출력/검증 기준을 먼저 정한다.
4. 구현은 다음 주부터 시작하되, 오늘은 구현 가능 조건을 만드는 데 집중한다.
5. 이슈 코멘트는 회의 결정의 source of truth로 유지한다.
6. 약칭은 쓰지 않고 정식 명칭을 사용한다.
7. 각 담당자에게 “무엇을 언제까지 어떤 산출물로 줄 것인지”를 반드시 확인한다.
