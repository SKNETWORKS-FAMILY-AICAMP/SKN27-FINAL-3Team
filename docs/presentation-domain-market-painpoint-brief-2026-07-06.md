## 1. 발표 전체 흐름 제안

발표는 단어 설명이 아니라 문제 흐름을 설명하는 방식이 좋다.

```text
교통사고/과태료 분쟁은 왜 어려운가
-> 사고·고지서·보험 분쟁에서 소비자가 겪는 실제 pain point
-> 시장/소비자 트렌드: 디지털 상담, 셀프 확인, 근거 기반 리포트 수요
-> 기존 서비스/경쟁사의 한계
-> 우리 서비스의 해결 방식: OCR + 법령 RAG + 과실비율 사례검색 + 이의가능성 판단 + 리포트
-> 기술 구조와 보안/개인정보 보호 설계
```

이 순서가 좋은 이유는 기능을 나열하지 않고, 사용자가 겪는 실패 지점에서 기능이 자연스럽게 등장하기 때문이다.

## 2. 도메인 기본 설명

### 2.1 도메인 범위

이 프로젝트의 도메인은 단순한 "교통사고 챗봇"이 아니라, 교통사고 이후 발생하는 분쟁성 의사결정을 돕는 AI 상담/근거 정리 서비스다.

핵심 영역은 네 가지다.

| 영역 | 사용자가 겪는 상황 | 서비스가 도와야 하는 일 |
|---|---|---|
| 과태료/범칙금 고지 | 고지서가 왔는데 사유, 기한, 이의제기 가능성을 모름 | OCR로 고지서 필드 추출, 기한/유형 분기, 이의가능성 판단 |
| 교통사고 과실비율 | 보험사나 상대방 주장과 내 생각이 다름 | 유사 판례/심의사례/인정기준 검색, 근거 기반 비교 |
| 법률 근거 확인 | 도로교통법, 시행령, 시행규칙 조문을 직접 찾기 어려움 | 일상어를 법률 용어로 바꾸고 관련 조문/RAG 근거 제공 |
| 상담/리포트 | 말로 설명한 사건을 제출 가능한 문서나 상담 요약으로 정리하기 어려움 | 상담 이력, 증거, 한계, 다음 조치를 리포트로 구조화 |

### 2.2 과태료와 범칙금 차이

발표에서는 깊은 법률 강의보다 서비스 설계에 영향을 주는 차이만 설명하면 된다.

| 구분 | 의미 | 서비스 설계 포인트 |
|---|---|---|
| 과태료 | 행정질서 위반에 대한 금전 제재 성격 | 이의신청/의견제출 가능성, 기한, 고지서 OCR 분석이 중요 |
| 범칙금 | 운전자 특정 및 교통법규 위반 처리와 연결 | 벌점/운전자 특정 리스크가 있어 단순 이의신청서 생성 범위 밖으로 제한 |
| 사고 과실비율 | 사고 당사자 간 책임 비율 | 보험금, 구상, 분쟁심의, 소송 가능성과 연결 |
| 법률사고 | 법령 해석, 기한 도과, 잘못된 진술, 개인정보 노출로 불이익이 생기는 상황 | "확정 판단"이 아니라 근거와 한계가 있는 안내가 필요 |

### 2.3 교통사고 트렌드와 흐름

교통사고 도메인은 다음 방향으로 이동하고 있다.

| 흐름 | 발표 메시지 | 프로젝트 연결 |
|---|---|---|
| 단순 사고 건수보다 분쟁의 복잡성 증가 | 블랙박스, CCTV, 무인단속, 보험 심사, 과실비율 기준이 얽히면서 소비자가 직접 판단하기 어려워짐 | 멀티 에이전트 구조로 OCR, 법령, 판례, 과실비율, 리포트를 분리 |
| 사망사고 중심 통계에서 생활형 분쟁으로 관심 확대 | 큰 사고뿐 아니라 접촉사고, 주정차, 보호구역, 진로변경 같은 일상 사고도 비용과 시간이 듦 | 과실비율 심의사례 226건, 과실비율 판례 973건, 교통 판례 3,562건을 검색 기반으로 사용 |
| 오프라인 전문가 상담 전 셀프 점검 수요 증가 | 보험사/변호사 상담 전에 "내 주장의 근거가 있는지" 확인하려는 수요 | 상담형 UI와 근거 기반 리포트 |
| 영상·이미지 증거의 중요성 증가 | 고지서, 사고사진, 블랙박스가 판단의 출발점이 됨 | 파일 업로드, scan gate, OCR/vision adapter 설계 |
| AI 상담의 보안/책임 문제 부각 | 법률/보험/개인정보가 섞인 입력은 저장·출력·권한 통제가 필요 | guest 제한, 파일 검사, token 분리, RAG evidence, limitations |

## 3. 실질적 사례로 설명할 수 있는 시나리오

### 사례 A. 과태료 고지서 이의가능성

사용자 상황:

```text
"불법주정차 과태료 고지서를 받았는데, 차를 도난당한 상태였고 이의신청을 해도 되는지 모르겠다."
```

Pain point:

- 고지서에서 위반유형, 기한, 법조문, 금액을 읽기 어렵다.
- 도난, 부득이한 사유, 본인 운전 인정형 진술처럼 결과가 크게 달라지는 사유를 구분하기 어렵다.
- 무심코 "제가 운전했다" 식으로 입력하면 범칙금/벌점 리스크로 이어질 수 있다.

우리 기능:

- `fine_notice_analysis`: 고지서 OCR 필드 추출
- `appeal_decision_flow`: 과태료/범칙금 분기, 기한, 사유, 리스크/인정가능성 분리 판단
- `law_ground_search`: 도로교통법/질서위반행위규제법 근거 검색
- `report`: 판단 결과, 한계, 다음 조치 정리

발표 문장:

> 이 서비스는 "이의신청 가능/불가능"을 단정하는 것이 아니라, 고지서 필드와 사용자의 사유를 분리해 법적 리스크와 인정 가능성을 따로 보여준다.

### 사례 B. 보험 과실비율 분쟁

사용자 상황:

```text
"상대 차량이 진로변경을 했는데 보험사는 제 과실도 크다고 합니다. 비슷한 사례가 있나요?"
```

Pain point:

- 보험사가 말한 과실비율이 어떤 기준에서 나온 것인지 알기 어렵다.
- 인정기준, 판례, 심의사례가 흩어져 있어 일반 소비자가 직접 찾기 어렵다.
- "내 사건과 진짜 비슷한 사례"인지 판단하려면 사고 장소, 진행 방향, 신호, 정지 여부가 필요하다.

우리 기능:

- `text_ml_case_search`: 과실비율 판례/심의사례 유사 검색
- 과실비율 판례 973건, 심의사례 226건/904 chunks, 교통 판례 3,562건 적재
- `road_context_analysis` 제안: 사고 위치, 단속/도로 환경, 보호구역 여부를 보조 근거로 연결
- `report workbench`: 유사 사례, 근거, 한계, 추가로 필요한 증거 표시

발표 문장:

> 보험 분쟁의 핵심은 "정답 비율"이 아니라, 내 사고가 어떤 기준·사례와 닮았고 어떤 증거가 부족한지 확인하는 것이다.

### 사례 C. 상담 중 개인정보/보안 리스크

사용자 상황:

```text
"차량번호, 고지서 사진, 이름, 주소, 사고 위치를 챗봇에 그대로 올린다."
```

Pain point:

- 상담 데이터에는 개인정보, 위치정보, 차량정보, 법률 민감정보가 섞인다.
- LLM은 입력을 그대로 프롬프트/로그/출력에 노출할 위험이 있다.
- 업로드 파일은 악성코드, 개인정보 원문, 프롬프트 인젝션 문구를 포함할 수 있다.

우리 기능/설계:

- guest/auth 권한 분리, guest는 preview 중심
- Google token과 app JWT 분리, Google token은 backend-only 저장
- 파일 scan gate: `scan_status=clean` 전에는 Agent input 차단
- history/event는 원문 저장소가 아니라 allowlist metadata 중심
- secret은 코드/문서/클라이언트 JS에 저장하지 않는 정책
- LLM 보안은 OWASP LLM Top 10 기준으로 prompt injection, sensitive information disclosure, excessive agency를 우선 관리

## 4. BM 모델과 소비자 트렌드

### 4.1 고객 세그먼트

| 세그먼트 | 니즈 | 지불/도입 가능성 |
|---|---|---|
| 일반 운전자 | 과태료/사고 후 빠른 셀프 점검 | Freemium, 건별 리포트 결제 |
| 보험 가입자/피해자 | 보험사 주장에 대한 근거 확인 | 고급 리포트, 전문가 연결 |
| 보험설계사/손해사정 보조 | 상담 전 사건 요약과 유사 사례 검색 | B2B SaaS, 좌석당 과금 |
| 법률/행정 상담 기관 | 반복 민원 상담의 1차 정리 | 기관용 API/대시보드 |
| 보험사/모빌리티 플랫폼 | 고객 응대 자동화, 분쟁 예방 | API/화이트라벨 |

### 4.2 BM 후보

| 모델 | 설명 | 장점 | 리스크 |
|---|---|---|---|
| Freemium + 건별 리포트 | 기본 상담 무료, 상세 리포트/다운로드 유료 | 소비자 진입장벽 낮음 | 법률 자문으로 오해되지 않게 표현 통제 필요 |
| 구독형 개인 플랜 | 사고/과태료 이력 관리, 마이페이지, 문서 보관 | 반복 사용자에게 적합 | 사고 빈도가 낮아 개인 구독 지속성이 약할 수 있음 |
| 전문가 연결 수수료 | 변호사/손해사정/보험 상담 연결 | 고관여 사건에서 수익화 가능 | 광고성 추천, 이해상충 관리 필요 |
| B2B SaaS | 보험/상담기관 직원용 사건 요약·검색 도구 | 안정적 매출, 내부 업무 효율화 | 도입 심사, 보안/감사 요건 높음 |
| API 제공 | OCR, RAG, 과실비율 검색, 리포트 모듈 제공 | 확장성 높음 | 책임 경계와 SLA 필요 |

추천 포지션:

1차 MVP는 `Freemium + 건별 근거 리포트`가 가장 설명이 쉽다. 이후 `B2B 상담 보조 SaaS`로 확장한다.

### 4.3 소비자 트렌드 분석

발표에서 사용할 트렌드 문장:

- 사용자는 보험사/기관에 바로 맡기기 전에, 모바일에서 먼저 본인 상황을 점검하고 싶어한다.
- 자동차보험·교통분쟁은 정보 비대칭이 크기 때문에, "전문가 답변"보다 "근거가 보이는 답변"에 신뢰가 생긴다.
- 과실비율정보포털의 검색 순위와 심의사건 조회 기능은 소비자가 이미 온라인에서 과실비율을 직접 확인하려는 행동을 보여준다.
- 보험개발원은 일반 소비자를 대상으로 카히스토리, 보험료 할인할증조회, 보험통계조회서비스 같은 정보 서비스를 제공하고 있어, 보험 데이터 기반 셀프 확인 경험이 이미 시장에 존재한다.

## 5. 시장조사 범위

시장조사는 너무 넓히지 말고 아래 범위로 제한하는 것이 좋다.

| 범위 | 포함 | 제외 |
|---|---|---|
| 국내 개인 운전자 교통분쟁 | 과태료, 범칙금 안내, 사고 과실비율, 보험 분쟁 전 단계 | 형사사건 변호, 법원 소송 대리 |
| 자동차보험 소비자 지원 | 과실비율 이해, 유사 사례 검색, 증거 정리 | 보험금 직접 산정/지급 결정 |
| 온라인 법률/보험 상담 보조 | 문서 OCR, RAG 근거, 리포트 | 변호사법상 법률 대리 행위 |
| 공공/공식 데이터 기반 근거 | TAAS, 과실비율정보포털, 법령, 판례/심의사례 | 개인 처분 이력, 비공개 보험사 내부자료 |

시장조사의 발표용 결론:

> 이 시장은 "교통사고 전체 시장"이 아니라, 사고·고지서·보험 분쟁에서 소비자가 전문가 상담 전 스스로 근거를 확인하려는 pre-claim/pre-consulting 시장으로 정의한다.

## 6. 보험사례와 법리 싸움 증가 관점

보험 분쟁에서는 단순히 "누가 잘못했나"보다 다음 쟁점이 반복된다.

| 쟁점 | 소비자 pain point | 필요한 기능 |
|---|---|---|
| 과실비율 산정 | 보험사 산정 근거를 이해하기 어려움 | 인정기준/심의사례/판례 검색 |
| 증거 부족 | 블랙박스, 사진, 위치, 신호 정보가 부족함 | 추가 증거 체크리스트 |
| 유사 사례 판단 | 내 사고와 비슷한 사례인지 모름 | 사고 유형/방향/도로상황 기반 검색 |
| 법리/기준 차이 | 판례와 심의사례, 보험 실무 기준이 다름 | evidence source와 limitation 표시 |
| 소송 전 단계 판단 | 소송 가치가 있는지 모르고 시간/비용 부담 | 리스크/가능성/다음 조치 리포트 |

발표에서는 "법리 싸움 증가"를 통계 단정으로 말하기보다 이렇게 표현하는 편이 안전하다.

> 블랙박스와 온라인 분쟁 절차가 보편화되면서 소비자는 보험사의 설명을 그대로 받아들이기보다, 유사 사례와 법적 근거를 직접 확인하려는 방향으로 움직이고 있다. 따라서 서비스의 가치는 결과를 단정하는 것이 아니라 근거 탐색 비용을 낮추는 데 있다.

## 7. 경쟁사 분석

SWOT의 기초를 지키려면 약점만 말하지 말고 S/W/O/T를 모두 보여준 뒤, 우리 프로젝트가 어떤 pain point를 개선했는지 연결해야 한다.

### 7.1 경쟁/대체 서비스

| 구분 | 예시 | 강점 | 약점/Pain point |
|---|---|---|---|
| 과실비율정보포털 | 손해보험협회 과실비율 정보포털 | 공식 인정기준, 검색순위, 심의사례, 상담 메뉴 | 사용자가 사고 사실을 구조화해서 넣어야 하며, 개인 사건 리포트로 이어지지 않음 |
| 보험사 앱/콜센터 | 각 보험사 사고접수/보상상담 | 실제 보험 처리와 연결 | 보험사 관점의 설명으로 느껴질 수 있고, 근거 비교가 제한적 |
| 법률 상담 플랫폼 | 로톡 등 변호사 상담 플랫폼 | 전문가 연결, 실제 사건 상담 가능 | 비용/시간 부담, 초기 셀프 점검에는 무거움 |
| 일반 챗봇/검색 | ChatGPT, 네이버 검색 등 | 접근성 높음 | 최신 법령/사례 근거, 개인정보 보호, 리포트 저장, 사건별 증거 추적이 약함 |
| 공공 사이트 | TAAS, 법령정보, 공공데이터 | 공식 데이터 | 일반 사용자가 사고·고지서 문맥과 연결하기 어려움 |

### 7.2 SWOT

| 구분 | 내용 |
|---|---|
| Strength | OCR, 법령 RAG, 과실비율 사례검색, 이의가능성 판단, 리포트가 하나의 상담 흐름으로 연결됨 |
| Weakness | MVP 단계에서는 실제 보험사 내부 데이터, 실시간 판례 API, 실제 vision 모델 연결이 제한적 |
| Opportunity | 소비자의 셀프 점검 수요, 온라인 보험/법률 상담 확대, 공공 데이터와 RAG 결합 가능성 |
| Threat | 법률 자문 오해, 개인정보/보안 사고, 공식기관/보험사 서비스의 기능 확장 |

왜 약점 위주가 아니라 pain point 위주인가:

> 경쟁사 약점만 말하면 비판처럼 보인다. SWOT에서는 경쟁사의 강점도 인정한 뒤, 사용자가 여전히 해결하지 못하는 fail point를 정의하고 우리 기능이 그 지점을 어떻게 메우는지 보여줘야 설득력이 생긴다.

## 8. Fail Point -> 우리 기능/설계 연결

| Fail/Pain point | 사용자의 실패 장면 | 우리 프로젝트의 대응 기능 | 구현/문서 근거 |
|---|---|---|---|
| 고지서 내용을 읽기 어렵다 | 고지서 사진만 있고 위반유형/기한/금액을 모름 | `fine_notice_analysis` OCR state, missing fields, sync upload | `ai/agents/fine_notice_analysis/` |
| 이의신청이 위험할 수 있다 | 사유를 잘못 말해 운전자 특정/범칙금 리스크 발생 | `appeal_decision_flow`의 RG/MG 분리, 위험 폴백 | `ai/agents/appeal_decision_flow/`, ARCH-001 |
| 법령 용어를 모른다 | "전동킥보드", "스텔스 차량" 같은 일상어로 검색 | Neo4j Hint Graph + 법령 vector search | `law_ground_search`, 법령 chunk 99,594개 |
| 보험사 과실비율 근거가 불투명하다 | 유사 판례/심의사례를 못 찾음 | `text_ml_case_search`, 과실비율 판례/심의사례 RAG | 과실비율 판례 973건, 심의사례 226건 |
| 사고 위치 맥락이 빠진다 | 보호구역/단속카메라/도로환경 확인이 안 됨 | `road_context_analysis` MCP 제안 | `docs/architecture/road-traffic-context-mcp-proposal-2026-07-02.md` |
| AI 결과를 믿기 어렵다 | "왜 이런 답이 나왔는지" 알 수 없음 | evidence, limitations, report_quality, retrieval_events | Agent output envelope, report workbench |
| 파일/개인정보가 위험하다 | 고지서/차량번호/주소/영상 업로드 | file scan gate, PII/secret 정책, token 분리 | guest hardening, secret management |
| 상담이 일회성으로 끝난다 | 나중에 다시 볼 수 없음 | MyPage/history/report 저장/다운로드 | MVP demo spine |

## 9. 주요 기능만 발표하기

모든 기능을 설명하면 산만해진다. 발표에서는 아래 5개만 잡는 것이 좋다.

### 9.1 고지서 OCR + 이의가능성 판단

핵심 메시지:

> 고지서에서 필요한 필드를 뽑고, 과태료/범칙금을 분기한 뒤, 사용자의 이의 사유를 법적 가능성과 리스크로 나눠 판단한다.

설명 포인트:

- OCR Agent는 문서에서 구조화된 필드를 만든다.
- Appeal Agent는 `merit`와 `risk`를 분리한다.
- 도난, 제3자 운전 주장, 본인 운전 인정형 같은 위험 패턴을 구분한다.
- 기한을 모를 때는 막지 않고 경고와 한계를 표시한다.

### 9.2 법령 RAG

핵심 메시지:

> 사용자의 일상어를 법률 용어로 확장하고, 조문 단위 chunk와 embedding으로 근거를 찾는다.

설명 포인트:

- 법령 chunk 99,594개
- OpenAI embedding + Neo4j Graph-RAG 후보
- Rule guard로 비법령/출처 누락 결과 필터링
- 근거와 limitation을 리포트에 남김

### 9.3 과실비율 사례검색

핵심 메시지:

> 사고 설명을 기반으로 유사 판례와 심의사례를 찾아 과실비율 판단의 출발점을 제공한다.

설명 포인트:

- 교통 판례 3,562건
- 과실비율 판례 973건
- 심의사례 226건/904 chunks
- 판례, 심의사례, 인정기준은 성격이 다르므로 source를 구분해야 함

### 9.4 상담 리포트/마이페이지

핵심 메시지:

> 상담 결과는 채팅으로 끝나지 않고, 근거·한계·다음 조치가 있는 리포트와 이력으로 저장된다.

설명 포인트:

- `analysis_jobs`, `agent_results`, `reports`, `history_events`
- partial report도 숨기지 않고 품질 metadata를 표시
- demo path: guest -> login -> upload -> scan -> worker -> report -> history

### 9.5 보안/운영 설계

핵심 메시지:

> 법률/보험 AI 서비스는 기능보다 신뢰 경계가 먼저다.

설명 포인트:

- Google token과 app JWT 분리
- guest는 preview 중심, save/download는 로그인 필요
- scan 통과 전 파일은 Agent input 차단
- Redis progress cache에는 민감 원문 저장 금지
- secret은 코드/문서/클라이언트에 저장 금지
- LLM prompt injection, sensitive information disclosure, excessive agency 대응

## 10. 웹/AI 서비스 필수 보안 요소

| 보안 요소 | 왜 필요한가 | 우리 프로젝트 반영/추가 필요 |
|---|---|---|
| 인증/인가 분리 | guest, 로그인 사용자, 관리자 권한이 다름 | guest/auth session, Google code flow, JWT |
| OAuth token backend-only 저장 | 브라우저에 Google refresh token 노출 시 피해가 큼 | app JWT만 프론트에 반환 |
| 개인정보 최소수집 | 고지서/차량번호/주소는 민감 데이터 | history는 allowlist metadata 중심 |
| 파일 검사 | 업로드 파일에 악성코드/PII/프롬프트 인젝션 가능 | scan gate, clean 파일만 Agent 전달 |
| 입력/출력 검증 | LLM 결과를 그대로 실행/저장하면 위험 | Agent envelope validator, known node_code |
| Prompt injection 대응 | 사용자가 업로드한 문서가 모델 지시를 오염시킬 수 있음 | system/data 분리, tool 최소권한, evidence 검증 |
| 비밀정보 관리 | API key, DB password, OAuth secret 노출 방지 | `.env` Git 제외, secret store 권장 |
| 감사 로그 | 사고/분쟁/다운로드/인증 실패 추적 필요 | history_events, retrieval_events, auth events |
| 보관/삭제 정책 | 법률·보험 데이터는 오래 보관할수록 위험 | anonymous/guest/user 보관기간 차등 필요 |
| 법률 책임 제한 | AI 답변이 법률 자문처럼 보이면 위험 | 정보 제공, 근거/한계, 전문가 상담 안내 |

발표 문장:

> 이 프로젝트의 보안 설계는 "AI가 답을 잘하는가"보다 "민감한 사건 자료가 어디까지 들어가고, 어디에는 절대 남지 않는가"를 기준으로 잡았다.

## 11. 각 담당/브랜치 기반 Pain Point 추정

전달 문서가 없는 담당자는 Git 브랜치와 이슈 흐름 기준으로 발표용 pain point를 만들 수 있다.

| 담당/흐름 | 브랜치/이슈 단서 | 발표용 pain point | 연결 기능 |
|---|---|---|---|
| Supervisor/MVP | `feature/mvp-*`, `agent-results-persistence`, `worker-progress-polling` | 여러 Agent 결과가 흩어지면 사용자에게 일관된 상담 흐름이 안 보임 | job/result/report/history spine |
| Auth/Security | `google-auth-jwt`, `auth-token-lifecycle`, `auth-ownership-guard` | 법률/보험 상담에서 인증과 저장 권한이 느슨하면 개인정보 사고로 연결 | Google code flow, app JWT, ownership guard |
| OCR/과태료 | `fine-notice-*`, `feat/fine-appeal-decision-flow` | 고지서 필드와 이의 사유를 사용자가 직접 해석하기 어려움 | OCR + appeal decision flow |
| 법령 RAG | `feature-law-ground-search`, `feat/legal-data-mcp-contract` | 일상어와 법령어가 달라 근거 조문을 못 찾음 | law_ground_search, Graph-RAG |
| 과실비율/사례 | `feature/connect-fault-ratio-agent`, `text-ml-case-search-adapter` | 보험사 과실비율의 근거를 소비자가 검증하기 어려움 | text_ml_case_search |
| Vision/DL | `feat-accident-image-video-agent-result-flow`, `test-vision-*` | 사고 사진/영상은 중요한데 아직 텍스트 상담과 연결이 약함 | vision schema, key frame/object evidence |
| Data Pipeline | `feature-Data-Pipeline`, `fault-ratio-knowledge-base` | 판례/심의사례 원문은 많지만 검색 가능한 구조로 바꾸기 어렵다 | preprocessing, chunks, embeddings |
| Frontend/UI | `frontend-workbench-ui`, `report-quality-ux` | AI 분석 결과가 많아도 사용자가 읽기 어렵다 | workbench, progress, report quality |
