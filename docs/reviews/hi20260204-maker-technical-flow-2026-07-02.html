실서비스 전환을 위한 Supervisor, Worker, RAG, Readiness 설계 정리

오늘 작업의 핵심은 화면 추가가 아니라, mock/contract 기반 MVP를 실제 운영 가능한 실행 경계로 바꾸는 일이었다. 발표에서는 “요청이 들어오면 누가 판단하고, 어떤 인증/보안 경계를 거치고, 어디에 저장하고, 어떤 기준으로 운영 가능성을 검증하는가”를 중심으로 설명한다.

Supervisor LLM LLM planner를 옵션으로 연결하고, 실패 시 기존 rule fallback이 계약을 유지하도록 설계했다.
Worker Queue Agent 실행을 inline 처리에서 DB work item 기반 queued -> running -> success/failed 흐름으로 분리했다.
Legal RAG Django 영속 테이블과 pgvector ETL 테이블의 역할을 분리하고 fallback 경로를 명확히 했다.
Production Readiness 운영 설정, OAuth, LLM, RAG, queue, storage를 한 번에 점검하는 readiness 계약을 만들었다.
Google Auth & Security Authorization Code Flow, app JWT, backend-only OAuth token 저장, mock off 검증 경계를 정리했다.

사용자의 상담 입력이 들어온 뒤 Supervisor가 판단하고, Agent 작업이 queue로 분리되며, RAG와 결과 저장을 거쳐 화면/리포트로 돌아오는 구조다.

5

3. 요청 처리 시퀀스 다이어그램

아래 시퀀스는 실제 상담 요청 하나가 들어왔을 때 저장, 큐잉, RAG 검색, 결과 반영이 어떤 순서로 일어나는지 보여준다.

4. Google 인증과 보안 경계

로그인은 Google Identity Services Authorization Code Flow로 분리했다. 브라우저는 authorization code와 우리 서비스의 app JWT만 다루고, Google access token/refresh token 원문은 백엔드 저장소 밖으로 나가지 않는다.

1

Frontend code 요청

google.accounts.oauth2.initCodeClient()로 openid email profile 기본 scope의 authorization code만 받는다.

2

Backend code 교환

POST /api/auth/google/code/가 X-Requested-With: XmlHttpRequest를 확인하고 Google token endpoint와 통신한다.

3

App JWT 발급

서비스 내부 인증은 Google token이 아니라 HMAC 기반 app Bearer JWT로 분리한다.

4

OAuth token 보호 저장

oauth_connections에 access/refresh token을 보호 문자열로 저장하고 응답에는 원문을 포함하지 않는다.

5

Mock off 운영 검증

GOOGLE_AUTH_ALLOW_MOCK=0, APP_AUTH_ALLOW_MOCK_BEARER=0, secret 길이를 readiness에서 차단 조건으로 본다.

보안 포인트 구현/설정 발표에서 보여줄 핵심
토큰 분리 access_token 응답은 우리 서비스 app JWT, Google token은 backend-only 브라우저가 Google refresh token을 보관하지 않는다.
계정 연결 social_accounts.provider_user_id에 Google sub 저장 email 변경과 무관하게 provider subject 기준으로 계정을 묶는다.
OAuth 저장소 oauth_connections.access_token_encrypted, refresh_token_encrypted 원문 token은 API 응답과 화면에 노출하지 않는다.
Refresh/Logout /api/auth/refresh/, /api/auth/logout/ app JWT 재발급과 세션 revoke 이벤트를 분리해서 감사 가능하게 둔다.
운영 차단 조건 APP_JWT_SECRET, OAUTH_TOKEN_SECRET, mock off 설정 secret과 mock 설정은 readiness에서 fail로 막는다.

5. 저장소와 테이블 설계

오늘 설계에서 헷갈리기 쉬운 부분은 RAG 저장소가 두 계층이라는 점이다. Django 런타임 테이블은 서비스 화면/감사/계약을 위한 저장소이고, pgvector 테이블은 법률 ETL 산출물의 semantic search 저장소다.

영역 테이블/구성 역할 발표에서 강조할 말
Supervisor 실행 analysis_jobs, analysis_job_events, ai_sessions 상담 하나의 분석 실행 단위와 진행 상태를 저장 LLM을 붙여도 API/DB 계약은 흔들리지 않는다.
Agent 호출 agent_invocations, agent_results Agent별 실행 상태, 결과, evidence, limitation 저장 개별 Agent 구현을 바꾸지 않고 공통 envelope만 맞춘다.
Worker Queue agent_work_items 비동기 실행, retry, progress 전환을 위한 운영 경계 inline 실행에서 운영 가능한 worker 모델로 넘어가는 발판이다.
Django RAG source_documents, rag_chunks, retrieval_events 서비스 런타임에서 쓰는 문서/청크/검색 이벤트 저장 검색 결과의 출처와 근거를 화면과 리포트까지 추적한다.
pgvector RAG law_chunks, law_embeddings 법률 ETL 산출물을 벡터 검색하는 별도 경로 Postgres에 pgvector가 있는 건 맞지만, 런타임 연결 검증이 필요하다.

6. Readiness 결과 해석

현재 사용자가 실행한 결과는 설정 자체는 대부분 통과했지만, Windows 호스트에서 POSTGRES_HOST=postgres를 사용해 DB DNS 해석이 실패한 상태다.

통과한 부분

Django security, Google OAuth code flow, Supervisor LLM, Object Storage 설정은 production-shaped로 확인됐다.

실패한 직접 원인

postgres는 Docker Compose 내부 서비스명이다. Windows 호스트에서 직접 manage.py를 실행하면 localhost를 써야 한다.

파생 실패

DB introspection 실패 때문에 Legal RAG 테이블과 worker queue 테이블도 검증하지 못했다. DB 연결 후 다시 확인해야 한다.

7. 현재 프로젝트 반영 체크

오늘 기준으로 코드와 문서에서 확인한 반영 상태다. 발표에서는 “완료된 구현”과 “운영 전 검증”을 분리해서 말하면 된다.

분류 반영된 업데이트 확인한 근거 다음 확인
Supervisor LLM planner optional adapter와 fallback contract supervisor_llm_service.py, SUPERVISOR_LLM_ENABLED 실제 API key 환경에서 planner output smoke test

Legal RAG Django RAG 테이블과 pgvector 우선 검색/fallback 경로 source_documents, rag_chunks, retrieval_events law_chunks, law_embeddings ETL 적재 확인
Google Auth Authorization Code Flow, app JWT, backend-only OAuth token 저장 /api/auth/google/code/, social_accounts, oauth_connections Google Cloud 설정 후 mock off code exchange smoke test
Production Readiness security, DB, OAuth, LLM, RAG, queue, storage 통합 점검 check_production_readiness, .env.production.example 호스트 실행 시 POSTGRES_HOST=localhost로 DB 포함 재검증

8. 아직 남은 일

오늘 작업은 운영 전환의 뼈대를 세운 것이고, 실제 release 전에 아래 항목이 순서대로 닫혀야 한다.

DB 연결과 RAG ETL

로컬 호스트 실행은 POSTGRES_HOST=localhost로 점검하고, 실제 vector search를 위해 law_chunks, law_embeddings 적재를 검증해야 한다.

Worker 운영화

management command 기반 처리를 운영 프로세스, scheduler, 또는 queue worker로 상시 구동하고 retry/cancel/monitoring 정책을 닫아야 한다.

Real Agent 연결

각 담당자의 실제 Agent 구현은 건드리지 않고, owner가 제공한 output을 공통 envelope와 display DTO에 맞춰 검증해야 한다.

운영 smoke test

Google Cloud OAuth 설정, mock off 로그인, object storage, production readiness DB 포함 점검을 한 번의 release checklist로 묶어야 한다.
