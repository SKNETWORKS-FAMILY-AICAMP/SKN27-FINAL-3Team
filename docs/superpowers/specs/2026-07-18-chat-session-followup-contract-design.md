# 채팅 세션·역질문 연속성 계약 설계

## 목표

사용자가 `needs_input` 역질문을 받은 뒤 다음 메시지에서 `session_id`와 새 답변만 보내도, 같은 사용자의 기존 확인 사실과 미해결 질문을 서버가 복원하여 상담을 이어 간다.

## 범위와 비범위

- 기존 `ChatSession`, `ChatMessage`, `metadata`만 사용한다. 새 테이블과 마이그레이션은 만들지 않는다.
- 대상은 표준 `POST /api/chat/messages/`의 역질문 연속성이다.
- `needs_input`과 `case_ready`는 상담 상태를 저장한다. `scope_guidance`와 `supervisor_unavailable`은 기존처럼 상담 상태를 만들거나 저장하지 않는다.
- 분석 작업, 에이전트 작업 항목, 리포트를 역질문 상태 저장만으로 만들지 않는다.
- 장기 보관 정책·대화 목록 UI·새로운 세션 조회 API는 이 이슈 범위가 아니다.
- 기존 `conversation_save_state` 정책을 바꾸지 않는다. `pending`과 `session_only`는 역질문을 잇기 위한 세션 상태만 유지하고, 기존처럼 히스토리와 마이페이지에는 노출하지 않는다.

## 선택한 접근

### 권장안: 기존 세션을 서버 원본으로 사용

`ChatSession.metadata`에는 최신의 구조화된 역질문 스냅샷을, `ChatMessage`에는 개인정보 보호를 거친 사용자 발화를 저장한다. 다음 요청은 소유권 검증을 통과한 뒤 서버 상태를 읽어 입력과 병합하고, 그 결과만 Supervisor와 상담 상태 계산에 전달한다.

클라이언트의 `facts`, `fact_sources`, `conversation_history`는 보조 입력일 뿐이다. 저장된 서버 확인 사실은 reducer 입력에서 먼저 고정한다. 충돌하는 클라이언트 사실·과거 대화는 무시하거나 충돌로 기록할 뿐 서버 사실을 덮어쓸 수 없다. 새 답변은 저장된 미해결 질문의 답으로 정상 병합될 수 있다.

### 검토했으나 선택하지 않은 안

1. 클라이언트의 `conversation_history`만 신뢰: 누락·변조·다른 세션 혼입을 막을 수 없어 제외한다.
2. 전용 사건 메모리 테이블 추가: 장기 보관 정책과 마이그레이션 범위를 동반하므로, 현재 모델의 JSON 메타데이터로 해결 가능한 이 이슈에는 과하다.

## 구성 요소와 데이터 흐름

1. 뷰는 기존과 동일하게 요청 신원, 입력 개인정보 보호, 기존 세션 접근 권한, 첨부파일 검사를 먼저 수행한다.
2. 유효한 기존 `session_id`가 있으면 저장소가 해당 세션의 최신 역질문 상태와 저장된 사용자 메시지를 읽는다.
3. 전용 병합 서비스가 서버 확인 사실·미해결 질문·대화 턴을 우선으로 하여 현재의 안전 처리된 payload를 만든다.
4. `submit_message`는 병합된 payload만 사용한다. 따라서 Supervisor의 fact reducer와 LLM은 연속된 상담 문맥을 받는다.
5. 결과가 `needs_input` 또는 `case_ready`이면 저장소는 사용자 메시지와 최소 스냅샷을 원자적으로 저장하고, 작업 큐 없이 응답한다. `case_ready`도 저장하므로 이후 사건 생성 API가 실제 세션을 찾을 수 있다.
6. 일반 분석 요청은 현행 `enqueue_analysis_job_work` 흐름을 유지한다.

스냅샷의 계약 버전은 `chat_session_followup_state.v1`이다. 저장 값은 다음으로 제한한다.

- `facts`, `fact_sources`, `fact_conflicts`
- `pending_questions`
- 이전 서버가 선택한 `routing_intent`
- `consultation_state`의 구조화된 준비 상태
- 이전 보조자 질문과 저장된 사용자 메시지에서 만든 제한된 `conversation_history`

원문 요청 본문, 개인정보 보호 이전 값, 제공자 원시 응답, 숨겨진 프롬프트·도구 상태는 저장하지 않는다.

## 권한·개인정보·오류 처리

- 상태를 읽기 전에 기존의 `authorize_resource_access` 검사를 실행한다. 다른 로그인 사용자·다른 비회원 식별자의 세션은 복원하지 않고 현행 접근 거부 응답을 유지한다.
- 저장 함수는 기존 `_get_or_create_session`의 소유권 결합 검사를 재사용한다.
- 저장 대상은 `protect_chat_input_payload` 이후의 payload와 안전한 응답 필드뿐이다.
- 상담 상태 저장 실패는 정상 응답을 가장하지 않는다. 사용량을 환불하고 서버 오류 흐름으로 처리하여, "저장된 것처럼 보이는" 역질문을 남기지 않는다.

## 검증 기준

1. 첫 요청이 `needs_input`이면 `ChatSession`과 사용자 `ChatMessage`가 생성되고, 분석 작업·에이전트 작업 항목은 생성되지 않는다.
2. 같은 신원으로 `session_id`와 새 답변만 보내면 이전 확인 사실·미해결 질문·서버가 선택한 상담 의도가 복원되어 새 답변과 함께 Supervisor 입력에 반영된다.
3. 클라이언트가 서버 확인 사실과 충돌하는 `facts` 또는 `conversation_history`를 보내도 서버 확인 사실이 유지되며, 클라이언트가 임의로 `confirmed: true`를 지정해도 이를 덮어쓸 수 없다.
4. 다른 사용자 또는 다른 비회원 식별자는 같은 `session_id`의 상태를 읽거나 덮어쓸 수 없다.
5. `scope_guidance`는 기존처럼 분석 작업·역질문 상태 저장을 만들지 않는다.
6. `pending`과 `session_only` 세션은 역질문을 이어 갈 수 있지만 기존처럼 히스토리·마이페이지에 노출되지 않는다.
7. 기존 상담, 권한, 개인정보 보호 회귀 테스트를 함께 통과한다.
