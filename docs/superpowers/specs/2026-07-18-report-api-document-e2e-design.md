# 리포트 API 조회·다운로드 계약 및 문서 E2E 설계

> 이 문서는 GitHub 이슈 #226의 구현 전 설계 합의서다. 구현과 PR 검토는 이 문서의 범위와 검증 기준을 기준으로 판단한다.

## 1. 목표

이미 존재하는 리포트 조회·상세·PDF 다운로드 HTTP 경로를 공개 API 계약으로 승격한다.

- `GET /api/reports/`: 로그인한 사용자가 소유한 리포트 목록을 조회한다.
- `GET /api/reports/{report_id}/`: 접근 권한이 있는 리포트의 안전한 상세 DTO를 조회한다.
- `GET /api/reports/{report_id}/download/`: 접근 권한이 있고 준비된 리포트의 PDF를 내려받는다.

이 작업은 리포트 생성 기능을 새로 만들거나, 기존 생성 흐름을 변경하는 작업이 아니다. 사용자는 목록에서 상세를 보고, 이어서 PDF를 다운로드할 수 있어야 하며, 이 흐름은 Django HTTP E2E 테스트로 검증한다.

## 2. 현재 코드 확인 결과

기존 경로와 런타임 동작은 이미 존재한다.

| 영역 | 확인된 구현 | #226에서 보완할 점 |
| --- | --- | --- |
| URL | `backend/chatbot/urls.py`의 `reports/`, `reports/<report_id>/`, `reports/<report_id>/download/` | 경로는 유지한다. |
| HTTP 진입점 | `backend/chatbot/views.py`의 `report_action`, `report_detail`, `download_report` | 응답 조립을 서비스/DTO 경계로 분리한다. |
| 저장소 | `backend/chatbot/repositories.py`의 `list_report_records`, `get_report_record_detail`, `get_report_access_metadata`, `get_report_download_metadata` | 저장소 반환값을 그대로 공개하지 않는다. |
| 권한 | 상세/다운로드에서 접근 메타데이터 확인 후 권한 검증, PDF 렌더링 전 권한 확인 | 목록도 요청 주체 기반으로만 조회하고, 모든 공개 응답의 권한·오류 계약을 명시한다. |
| 프런트엔드 | `app/web/apiClient.js`, `app/web/FrontendAppShell.jsx`에 목록·상세·다운로드 호출 존재 | UI 재구현은 하지 않고 기존 호출과의 호환성을 검증한다. |
| API 계약 | 세 GET 경로가 `app/contracts/api_route_specs.py`의 `DEFERRED_ROUTE_SPECS`에 있음 | 세 GET 경로만 정식 OpenAPI v1 경로로 승격한다. POST는 보류 상태로 남긴다. |

특히 `get_report_record_detail`은 저장소 성격의 `content`, `metadata`, `object_storage` 등을 포함할 수 있다. 이를 그대로 JSON 응답으로 반환하면 내부 저장소 정보 또는 공개 의도가 아닌 원문 필드가 노출될 수 있으므로, 공개 DTO는 명시적 허용 목록으로 만든다.

## 3. 범위와 비범위

### 포함

- 목록·상세 응답을 조립하는 모듈화된 조회 서비스

- 프로젝트 준비도 체크리스트에서 #224 완료, #226 진행 상태 및 공통 품질 게이트 갱신

- 다운로드 문서의 서식·내용 변경

## 4. 선택한 구조

### 4.1 계약 모듈

`app/contracts/report.py`를 새로 둔다. 이 모듈은 다음 공개 계약을 한곳에 정의한다.

- 리포트 목록 항목과 목록 응답
- 리포트 상세 응답
- 오류 응답의 공통 형태
- PDF 다운로드 성공 응답의 미디어 타입/스키마 메타데이터에 필요한 계약 정보

목록과 상세 DTO는 `extra="forbid"` 성격의 명시적 필드만 공개한다. 내부 `metadata`, `object_storage`, 저장소 URI, 원본 입력, 권한 판정용 내부 값은 DTO에 포함하지 않는다. 사람이 읽을 수 있도록 생성된 리포트 본문이 필요한 경우에도, 서비스가 허용한 안전한 리포트 표시 데이터만 포함한다.

PDF 응답도 같은 공개 경계를 따른다. 기존 다운로드 구현이 설정하던 `X-Report-Persistence`, `X-Report-Storage-Backend`, `X-Report-Storage-URI`, `X-Report-Object-Key`, `X-Report-Object-Policy` 헤더는 내부 구현·저장소 정보를 노출하므로 제거한다. 다운로드 계약에는 표준 `Content-Type`, `Content-Disposition`과 공개 실행 상태를 설명하는 필요한 헤더만 남긴다.

### 4.2 조회 서비스

`app/services/report_query_service.py`를 새로 둔다. 이 모듈은 저장소 레코드를 공개 DTO로 변환하는 유일한 경계다.

- 목록 서비스는 저장소의 목록 레코드를 공용 목록 DTO로 정규화한다.
- 상세 서비스는 저장소 레코드에서 명시적으로 허용한 표시 필드만 공용 상세 DTO로 정규화한다.
- 뷰는 HTTP 입력·인증·권한 오류 처리와 서비스 호출만 담당한다.
- 저장소는 조회/렌더링/영속화만 담당하며, HTTP 응답 모양을 알지 않는다.

이 경계로 인해 새로운 필드를 응답에 추가할 때도 뷰의 임시 딕셔너리나 경로별 하드코딩을 늘리지 않고, DTO와 변환 서비스에서 의도를 검토할 수 있다.

### 4.3 라우팅과 OpenAPI

`app/contracts/api_route_specs.py`에서 다음 세 GET 경로만 `API_ROUTE_SPECS`로 옮긴다.

- `GET /api/reports/`
- `GET /api/reports/{report_id}/`
- `GET /api/reports/{report_id}/download/`

`POST /api/reports/`는 기존대로 `DEFERRED_ROUTE_SPECS`에 남기며, 현재의 작업자 전용 409 동작을 바꾸지 않는다.

`RouteSpec`에는 특정 리포트 경로를 조건문으로 처리하지 않는 일반적인 성공 응답 콘텐츠 표현을 추가한다. JSON DTO가 아닌 성공 응답도 미디어 타입과 스키마를 선언할 수 있어야 하며, OpenAPI 생성기는 이 선언을 사용한다. PDF 다운로드는 `application/pdf`와 `type: string`, `format: binary`로 표현한다.

### 4.4 권한과 오류 계약

| 상황 | 기대 결과 | 핵심 원칙 |
| --- | --- | --- |
| malformed/expired Bearer | 401의 공통 인증 오류와 `WWW-Authenticate` | 토큰 오류를 익명 403으로 뭉개지 않음 |
| 익명 목록/상세/다운로드 요청 | 현재 인증 계층의 안전한 인증 오류 | 본문·PDF·저장소 정보에 접근하기 전에 차단 |
| 타 사용자 리포트 상세/다운로드 | 403 | 존재하는 리포트를 다른 사용자에게 노출하지 않음 |
| 존재하지 않는 리포트 | 404 | 공통 API 오류 형태 사용 |
| 아직 생성 준비가 끝나지 않은 PDF | 409 `report_not_ready` | 일반 서버 오류나 빈 PDF로 바꾸지 않음 |
| 목록의 `owner_id` 같은 요청 파라미터 | 공개 계약에 노출하지 않음 | 소유자는 인증된 요청 주체에서만 결정 |
| `session_id` 필터 | 로그인한 사용자가 접근 가능한 세션으로만 좁힘 | 필터가 다른 사용자의 리포트를 선택하는 수단이 되지 않음 |

상세와 다운로드는 기존처럼 접근 메타데이터와 소유권을 먼저 확인하고, 이후에만 상세 조회·PDF 렌더링을 수행한다. 권한이 없는 요청이 렌더링 또는 스토리지 해석을 유발해서는 안 된다.

## 5. 대안 검토

### 대안 A: 기존 뷰의 딕셔너리를 그대로 OpenAPI에 등록

변경량은 작지만, 저장소 반환값과 공개 응답의 경계가 계속 섞인다. 내부 메타데이터 노출 여부를 경로별로 추적하기 어렵고, DTO 계약도 테스트하기 어렵다. 채택하지 않는다.

### 대안 B: 계약 모듈 + 조회 서비스 + 일반화한 응답 콘텐츠 명세

공개 필드와 내부 저장소 필드를 분리하고, JSON/PDF 응답을 동일한 라우트 명세 체계로 표현한다. 현재 구조를 유지하면서도 재사용 가능하고 하드코딩을 피할 수 있어 채택한다.

### 대안 C: 리포트 모델/생성 파이프라인을 전면 재설계

장기적으로는 가능하지만 #226의 API 계약 목표를 넘고, 이미 동작하는 생성·문서 렌더링 경로에 불필요한 회귀 위험을 만든다. 이번 범위에서는 채택하지 않는다.

## 6. 검증 계획

### 기능·보안 회귀 테스트

- 목록은 인증된 요청 주체의 리포트만 반환하고, 다른 소유자의 리포트를 반환하지 않는다.
- 상세는 공개 DTO 허용 목록만 반환하며 내부 저장소/메타데이터를 누출하지 않는다.
- 목록 → 상세 → 다운로드가 실제 Django HTTP 요청으로 성공한다.
- PDF 응답 헤더에 저장소 URI, 객체 키, 저장소 백엔드·정책 같은 내부 정보가 포함되지 않는다.
- 타 사용자 상세/다운로드는 PDF 렌더링 전에 403으로 끝난다.
- 없는 리포트는 404, 준비되지 않은 리포트 다운로드는 409을 유지한다.
- 생성 POST는 기존처럼 작업자 전용 409 계약을 유지한다.
- OpenAPI 생성 결과는 세 GET 경로, 오류 응답, PDF 바이너리 미디어 타입을 포함하고 POST는 deferred 상태로 남는다.

### 모든 구현 PR의 필수 품질 게이트

작업 완료 전 아래 항목을 모두 확인하고 PR 설명에 결과를 남긴다.

1. 변경 파일 목록을 확인한다.
2. 의도하지 않은 파일 수정이 없는지 확인한다.
3. 변경 범위에 맞는 테스트와 관련 회귀 테스트를 실행한다.
4. 타입 체크 또는 린트를 실행한다. 이 저장소에서는 CI와 동일한 `ruff check --select E9,F63,F7,F82 .` 및 프런트엔드 `npm run build`를 기본으로 한다.
5. 핵심 기능을 직접 실행한다. #226에서는 Django HTTP E2E 목록 → 상세 → PDF 다운로드가 이에 해당한다.
6. 인증·권한·개인정보·저장소 메타데이터 등 보안 경계를 재확인한다.
7. 경로별 문자열/응답 조립 하드코딩을 추가하지 않고, 정책·DTO·서비스 모듈에 책임을 분리한다.

## 7. 완료 기준

- 세 GET 리포트 API가 OpenAPI v1의 정식 계약으로 생성된다.
- 기존 프런트엔드 호출과 호환되는 목록·상세·PDF 다운로드가 동작한다.
- 공개 JSON에 내부 저장소 또는 비공개 메타데이터가 포함되지 않는다.
- 인증·소유권·준비 상태 실패가 5xx가 아닌 의도한 안전한 오류 계약으로 반환된다.
- 범위 내 테스트, 정적 검사, 프런트엔드 빌드, Django HTTP E2E, 보안 검토가 모두 통과한다.
- #226 이외의 생성 흐름·DB 스키마·UI 재설계 변경이 포함되지 않는다.
