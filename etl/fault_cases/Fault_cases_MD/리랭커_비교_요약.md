# 리랭커 비교 — 상세 대화 및 검증 기록

## 목적
- 서로 다른 검색(리트리버) 방법(BM25, pgvector, Elasticsearch vector, hybrid 등)을 공통된 기준으로 비교하기 위한 근거와 실제 구현·검증 결과를 대화 흐름 기준으로 상세히 정리합니다.

## 배경(초기 질문)
- 사용자 첫 질문: "리랭커 점수 비교 근거가 정확히 뭐였어??" — 이 질문을 시작으로 관련 문서와 코드를 탐색하며 논의가 이어졌습니다.

## 대화 및 조사 과정(시계열 요약)

1) 초기 분석
	- 목표: 왜 raw retriever scores를 비교할 수 없는지, 그리고 어떤 공통 지표를 사용했는지 확인.
	- 수행: 저장소 내 Markdown 문서(특히 A/B 평가 계획 문서)를 검색하여 원칙을 확인.

2) 문서 확인
	- 발견: A/B 평가 계획 문서(판례/심의사례 관련 문서들)에 "raw retriever scores는 비교 불가 → 로컬 리랭커로 공통 점수 산출" 원칙이 명확히 기재되어 있음을 확인.

3) 코드·아티팩트 탐색
	- 주요 코드: `etl/fault_cases/src/review_case/search/evaluation/run_local_reranker.py` — 후보(제네레이트된 JSONL)를 읽고, 필요 시 DB에서 `chunk_text`를 가져와 `(query, chunk_text)` 쌍을 만들어 `CrossEncoder`로 점수를 예측한 뒤 sigmoid로 `local_reranker_score`를 생성.
	- 보고서: `build_reranker_reports.py` — `local_reranker_score`를 기준으로 retriever별 요약(metric 집계)을 수행.
	- 아티팩트: `etl/fault_cases/artifacts/review_case_output/retrieval_ab_exports/review_case_retrieval_ab_candidates.jsonl` (각 retriever 별 후보 세트 포함), `review_case_retrieval_ab_reranker_run_report.json` (리랭커 실행 메타데이터).

4) 실증적 검증
	- 후보 파일(`..._candidates.jsonl`)을 열어 확인한 결과, 동일 `query_id`/`query`에 대해 retriever별로 동일 `chunk_id`/`chunk_preview`(chunk_text)가 등장함을 확인 — 즉 비교가 동일 청크 기준으로 수행되도록 후보가 생성됨.
	- 예시(파일에서 발췌): 동일 `query_id: review_q001`에 대해 `pgvector_cosine`, `elasticsearch_bm25_nori`, `elasticsearch_vector_cosine`, `elasticsearch_hybrid_bm25_vector_rrf` 등 여러 `retriever` 행에서 동일 `chunk_id: review_case_2017_032889_case_overview`가 반복됨.

5) 결론(이 시점)
	- 프로젝트는 서로 다른 리트리버의 raw score를 직접 비교하지 않았음.
	- 대신 동일 후보(같은 `(query, chunk_text)` 쌍)에 대해 동일한 리랭커를 적용해 `local_reranker_score`를 산출하고, 이를 공통 지표로 하여 A/B 비교를 수행함.

## 상세 기술(코드·프로세스 설명)

1) 후보 생성
	- 각 retriever는 후보 chunk들을 생성/내보냄. 후보 레코드는 다음 필드를 포함: `query_id`, `query`, `retriever`, `rank`, `review_case_id`, `chunk_id`, `chunk_preview`(또는 `chunk_text`), `retriever_score`, `score_type` 등.

2) 리랭커 실행(`run_local_reranker.py`) 핵심 흐름
	- 후보 JSONL 로드.
	- `chunk_text`가 없는 경우 DB(postgres 등)에서 `chunk_id`를 키로 `chunk_text`를 조회해 보완.
	- `(query, chunk_text)` 쌍 리스트를 빌드.(pair 수 = 후보 수)
	- `sentence_transformers.CrossEncoder`(모델: 예: `models/bge-reranker-v2-m3`)를 사용해 쌍별 raw score 예측.
	- raw score에 `sigmoid`를 적용해 `local_reranker_score` (0..1)로 변환.
	- 원 레코드에 `local_reranker_score` 필드를 추가하여 JSONL로 출력.
	- 메타 리포트(`reranker_run_report.json`)를 작성(모델 정보, candidate_count, run_time 등).

3) 리포트 생성(`build_reranker_reports.py`)
	- `local_reranker_score`가 포함된 후보 데이터를 불러옴.
	- `(query_id, query, retriever)`로 그룹화 후 metric 계산(예: top1, avg@5, max@5, min@5, std@5 등).
	- retriever별 요약 표/CSV/리포트를 생성.

4) 평가 지표의 의미
	- `local_reranker_score`는 리랭커가 판단한 쿼리-청크 관련성의 추정치이며, retriever 비교는 이 스코어의 분포·상위 랭킹 일치도 등을 통해 수행됩니다.

## Q&A(대화에서 오간 핵심 포인트와 답변 요지)

Q: "리랭커 점수 비교 근거가 정확히 뭐였어??"
A: 원점수는 스케일/의미가 다르므로 직접 비교할 근거가 되지 못한다. 대신 동일 `(query, chunk_text)` 쌍에 대해 공통 리랭커로 점수를 재산출해 비교한다.

Q: "query + chunk_text가 BM25와 임베딩 기반 검색을 같이 비교할 근거가 되나?"
A: 네 — `query + chunk_text`는 리랭커가 쿼리-문맥 관련성을 평가할 수 있는 일관된 입력 포맷을 제공합니다. BM25는 텍스트 기반 점수, 임베딩은 벡터 기반 점수를 제공하지만 리랭커는 둘 모두 동일한 입력(텍스트)을 받아 일관된 스코어를 출력합니다.

Q: "같은 query면 같은 chunk가 되는가?"
A: 원칙적으로는 아니다. 그러나 이번 프로젝트의 후보 생성/아티팩트에서는 동일 `query_id`/`query`에 대해 retriever별로 동일 `chunk_id`/text를 제공하여 같은 청크로 비교가 가능하도록 구성되어 있었습니다.

Q: "그럼 리트리버 점수(raw)는 비교 근거가 되는가?"
A: 아니다. 서로 다른 리트리버의 raw score는 스케일과 의미가 달라 직접 비교에 적합하지 않습니다. 대신 `local_reranker_score`가 비교 근거가 됩니다.

Q: "이번 평가가 서치 방법을 비교하는 근거가 되냐?"
A: 예 — `local_reranker_score`를 공통 기준으로 사용하면 retriever별 후보들의 품질을 비교할 수 있습니다. 단, 그 비교는 리랭커의 판단에 의존하므로 리랭커의 품질·편향·calibration을 함께 고려해야 합니다.

## 제약·위험 요소(반드시 기록할 것)

1) 리랭커 의존성 위험
	- 리랭커 모델이 특정 유형의 텍스트(예: 판례 전문 용어)에 편향되거나 오분류하면, retriever 비교 결과가 실제 검색 효용성과 어긋날 수 있음.

2) 후보셋 생성 버그 가능성
	- 후보를 생성할 때 retriever마다 다른 전처리·필터링 규칙이 적용되면 동일 청크 보장이 깨질 수 있음. 현재 아티팩트에서는 동일 청크가 확인되었지만 파이프라인 전체에서 항상 보장되는지 확인 필요.

3) 평가 지표의 외적 타당도
	- 리랭커 점수가 실제 사용자 만족·다운스트림 응답 품질과 얼마나 일치하는지 추가 검증 필요.

## 추천 검증 절차(구체적 단계)

1) 샘플 기반 휴먼 라벨링
	- 각 retriever에서 상위 K개(예: K=5) 후보를 샘플링하여 인력 평가자에게 관련성 라벨을 부여.
	- 라벨과 `local_reranker_score`의 상관을 확인.

2) 리랭커 캘리브레이션 점검
	- 예측 점수 분포와 실제 라벨(또는 휴먼 라벨)의 정밀도-재현율을 비교하여 score threshold가 의미 있는지 검토.

3) 다운스트림 A/B 테스트
	- 리트리버별로 전체 RAG 파이프라인을 운영(또는 시뮬레이션)하여 실제 응답 품질·속도·비용 측면에서 비교.

4) 후보셋 생성 파이프라인 감사
	- 후보 생성의 전처리·정렬·필터 규칙을 점검해 모든 retriever에서 동일한 candidate pool이 보장되는지 검증.

## 필요한 추가 산출물(원하면 바로 생성 가능)

- `reranker` 점수 히스토그램 비교 플롯 (retriever별 분포)
- 상위 N개에 대한 휴먼 라벨링 엑셀 파일 템플릿
- reranker calibration 리포트(precision@k, recall@k 등)

## 결론(요지)

- 이번 프로젝트의 A/B 비교는 "리트리버 raw score 직접 비교"가 아니라 "동일 `(query, chunk_text)`에 대해 재산출한 `local_reranker_score`로 비교"하는 방식으로 설계·실행되었습니다.
- 따라서 서치 방법(리트리버) 비교의 근거로서는 `local_reranker_score`가 적절하나, 이 근거는 리랭커의 품질·편향에 의존하기 때문에 추가적인 검증(휴먼 라벨, downstream A/B 등)을 권장합니다.
