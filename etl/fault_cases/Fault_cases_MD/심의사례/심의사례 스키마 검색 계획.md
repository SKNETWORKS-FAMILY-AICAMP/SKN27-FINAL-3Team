# `text_ml_case_search` Agent Input Full Optional Fields 테스트 계획

## 0. 수정 목적

이 문서는 `text_ml_case_search` Agent 테스트 입력을 다시 정리한 것입니다.

기존 수정본에서는 다음 필드들이 모두 `null`로 들어가 있었습니다.

```json
{
  "vision_evidence": null,
  "ocr_evidence": null,
  "insurer_claim": null,
  "required_outputs": null
}
```

하지만 이번 테스트 목적은 **선택 필드가 모두 들어온 상황에서도 동일한 input schema로 Agent/RAG가 정상 동작하는지 확인**하는 것입니다.

따라서 이번 수정본에서는 각 케이스마다 다음 필드를 모두 채웠습니다.

```text
vision_evidence
ocr_evidence
insurer_claim
required_outputs
```

---

## 1. 핵심 원칙

```text
1. query_id 같은 평가용 wrapper는 넣지 않는다.
2. source_scope는 넣지 않는다.
3. source_group도 넣지 않는다.
4. eval_origin도 넣지 않는다.
5. JSONL 한 줄은 agent_input 하나만 포함한다.
6. 판례/심의사례 선택은 input에서 하지 않는다.
7. Agent/RAG는 같은 agent_input을 기준으로 검색하고, 결과에서 source_type으로 출처를 구분한다.
```

## 3. 왜 이렇게 바꾸는가

선택 이유:

```text
1. 실제 서비스에서는 Vision, OCR, 보험사 주장이 함께 들어올 수 있다.
2. 이 값들이 들어와도 Agent input schema는 변하지 않아야 한다.
3. null 입력만 테스트하면 optional 필드 처리 로직을 검증할 수 없다.
4. RAG 검색 입력을 만들 때 query_text뿐 아니라 Vision/OCR/보험사 주장 정보를 보강 정보로 사용할 수 있다.
5. 단, 판례/심의사례를 선택하는 source_scope 같은 필드는 여전히 사용하지 않는다.
```

---

## 4. 예상 결과

```text
1. Agent는 query_text를 중심으로 사고 설명을 정규화한다.
2. vision_evidence가 있으면 사고 장면 보강 정보로 활용할 수 있다.
3. ocr_evidence가 있으면 사고 일시, 장소, 유형, 원인, 설명을 보강 정보로 활용할 수 있다.
4. insurer_claim이 있으면 insurer_claim_review 생성 경로로 들어갈 수 있다.
5. required_outputs가 있으면 Supervisor가 필요한 반환 범위를 확인할 수 있다.
6. RAG 결과는 evidence[].source_type으로 판례/심의사례 출처를 구분한다.
```

---

## 5. 주의사항

이번 JSONL의 Vision/OCR/보험사 주장 값은 실제 데이터가 아니라 테스트용으로 창작한 예시입니다.

따라서 검색 품질 평가 시에는 다음을 구분해야 합니다.

```text
query_text 기반 검색 성능
Vision/OCR 보강 정보가 들어간 schema 입력 처리 안정성
보험사 주장 비교 출력 생성 가능 여부
```

즉, 이번 파일은 실제 판정 정답셋이 아니라 **full input schema 흐름 검증용 테스트 입력**입니다.

## 6. 스키마 검색 테스트와 검색 방식 A/B 비교

이번 스키마 검색 테스트는 단순히 `agent_input` 구조가 JSONL로 잘 들어오는지만 보는 테스트가 아니다.  
`text_ml_case_search` Agent가 실제로 사용할 RAG 검색 입력을 어떤 형태로 만들고, 어떤 검색 방식이 더 안정적인 후보를 가져오는지도 함께 확인한다.

따라서 이 테스트에서는 같은 `agent_input`에서 검색 입력을 만들고, 다음 검색 방식을 비교한다.

```text
1. PostgreSQL pgvector
2. Elasticsearch BM25/Nori
3. Elasticsearch hybrid = BM25/Nori + vector
```

### 6.1 왜 스키마 검색 계획에 A/B 비교를 포함하는가

이유는 다음과 같다.

```text
1. Agent는 검색기를 직접 대체하지 않는다.
2. Agent는 RAG 검색 결과를 받아 evidence, similar_cases, ratio_range_label, insurer_claim_review로 가공한다.
3. 따라서 Agent 구현 전에 RAG 검색 입력 형태와 검색 방식을 먼저 고정해야 한다.
4. optional field가 채워진 agent_input에서는 query_text만 쓸 때와 검색 결과가 달라질 수 있다.
5. query_text / full_optional_context 입력 차이를 검색 방식별로 확인해야 한다.
```

즉, 이 계획의 목적은 다음 두 가지를 함께 검증하는 것이다.

```text
입력 스키마 검증:
  vision_evidence, ocr_evidence, insurer_claim, required_outputs가 들어와도 agent_input 구조가 유지되는지 확인

검색 품질 검증:
  같은 agent_input에서 만든 검색 입력을 pgvector / BM25+Nori / hybrid에 넣었을 때 어떤 후보가 나오는지 확인
```

---

## 7. 검색 입력 Variant

이번 테스트에서는 같은 `agent_input`에서 최소 두 가지 검색 입력을 만든다.

```text
1. query_text
   - 사용자가 묻는 핵심 사고 설명
   - 가장 기본적인 검색 입력

2. full_optional_context
   - query_text
   - raw_user_text
   - vision_evidence
   - ocr_evidence
   - insurer_claim
   를 합친 보강 검색 입력
```

예상 차이는 다음과 같다.

```text
query_text:
  짧고 명확하다.
  검색 노이즈가 적다.
  다만 OCR/영상/보험사 주장에만 들어 있는 단서는 반영되지 않는다.

full_optional_context:
  사고 정황이 풍부해진다.
  OCR의 사고유형, 사고원인, 보험사 주장 근거까지 검색에 반영할 수 있다.
  다만 너무 많은 단서가 들어가면 BM25 검색에서는 특정 단어가 과도하게 영향을 줄 수 있다.
```

따라서 최종적으로는 다음 조합을 본다.

```text
query_text x pgvector
query_text x BM25/Nori
query_text x hybrid

full_optional_context x pgvector
full_optional_context x BM25/Nori
full_optional_context x hybrid
```

## 8. 검색기 raw score 직접 비교 금지

검색 방식별 원점수는 서로 의미와 범위가 다르다.

```text
pgvector:
  cosine_similarity

BM25/Nori:
  bm25_score

hybrid:
  RRF 기반 hybrid_score
```

이 값들은 같은 점수 체계가 아니다.

예를 들어 다음처럼 비교하면 안 된다.

```text
BM25 score = 74
pgvector cosine_similarity = 0.56
hybrid_score = 0.03

따라서 BM25가 가장 좋다.
```

이 비교는 잘못된 비교다.  
BM25 점수는 키워드 매칭 기반 점수이고, cosine similarity는 벡터 각도 기반 유사도이며, hybrid score는 순위 융합 점수이기 때문이다.

따라서 raw score는 다음 용도로만 사용한다.

```text
1. 각 검색기 내부에서 rank를 정하는 참고값
2. 검색기별 결과가 정상적으로 생성되었는지 확인하는 디버깅 값
3. 보고서에서 검색기 내부 상태를 설명하는 보조 지표
```

## 9. 공통 비교 기준: 로컬 reranker 점수

최종 검색 방식 비교는 `심의사례 검색 A-B 평가 및 로컬 리랭커 계획.md`의 원칙을 그대로 따른다.

핵심 원칙은 다음과 같다.

```text
검색기별 raw score를 직접 비교하지 않는다.
pgvector / BM25+Nori / hybrid가 가져온 top_k 후보 전체를 같은 로컬 reranker로 다시 채점한다.
그 공통 점수로 검색 방식을 비교한다.
```

사용 모델은 1차 기준으로 다음을 사용한다.

```text
models/bge-reranker-v2-m3
```

평가 입력은 다음 쌍이다.

```text
query + chunk_text
```

또는 필요 시 다음 fallback을 사용한다.

```text
query + search_text
query + chunk_preview
```

최종 후보별 공통 점수 컬럼은 다음 이름으로 둔다.

```text
common_reranker_score
```

또는 기존 A/B 평가 코드와 맞출 경우:

```text
local_reranker_score
```

### 9.1 공통 reranker 평가 방식

평가 방식은 다음과 같다.

```text
1. pgvector top5 후보를 가져온다.
2. BM25/Nori top5 후보를 가져온다.
3. hybrid top5 후보를 가져온다.
4. 세 검색기의 후보를 하나의 candidates JSONL로 합친다.
5. 모든 후보에 대해 같은 local reranker를 적용한다.
6. 검색기별 avg_common_reranker_score@5, top1_common_reranker_score, max_common_reranker_score@5를 계산한다.
```

즉, 다음처럼 되어야 한다.

```text
pgvector 후보 100개
BM25/Nori 후보 100개
hybrid 후보 100개

총 300개 후보 전체에 common_reranker_score 부여
```

BM25 후보에만 reranker 점수를 붙이고 pgvector/hybrid 후보에는 점수가 없는 상태는 최종 비교로 보지 않는다.

## 10. 스키마 검색 테스트 결과 보고서 기준

스키마 검색 테스트 결과 보고서는 다음 기준으로 작성한다.

### 10.1 반드시 포함할 값

```text
active_test_case_count
input_variant_count
retriever_count
candidate_count
top_k
candidate_k
reranker_model
reranker_pair_count
error_count
```

### 10.2 검색기별 비교 표

검색기별 비교 표에는 다음을 포함한다.

```text
input_variant
retriever
query_count
candidate_count
avg_top1_internal_score
avg_at_5_internal_score
avg_common_reranker_score
chunk_type_counts
```

단, 최종 우열 판단은 다음 값으로 한다.

```text
avg_common_reranker_score
top1_common_reranker_score
max_common_reranker_score@5
```

`avg_top1_internal_score`, `avg_at_5_internal_score`는 검색기 내부 점수 기반 참고값으로만 사용한다.

### 10.3 해석 원칙

```text
1. BM25/Nori가 높은 BM25 score를 보인다고 무조건 더 좋은 검색기는 아니다.
2. pgvector cosine similarity와 BM25 score는 직접 비교하지 않는다.
3. hybrid RRF score와 BM25 score도 직접 비교하지 않는다.
4. 검색 방식 간 최종 비교는 common_reranker_score로 한다.
5. 단, reranker 점수만으로 최종 운영 방식을 결정하지 않고 사람이 일부 샘플을 확인한다.
```

## 11. 현재 테스트 코드에서 주의할 점

현재 스키마 검색 테스트 코드는 다음 조건을 만족해야 한다.

```text
1. JSONL에서 // 로 시작하는 줄은 비활성 케이스로 건너뛴다.
2. 활성 agent_input만 테스트한다.
3. query_text와 full_optional_context를 모두 만들 수 있어야 한다.
4. pgvector / BM25+Nori / hybrid 결과를 같은 candidates JSONL로 저장한다.
5. candidates 전체에 local reranker 점수를 부여한다.
6. 결과 MD는 다음 경로에 생성한다.
```

```text
etl/fault_cases/Fault_cases_MD/심의사례/심의사례 스키마 검색 테스트 결과 스코어 및 보고서.md
```

이번 테스트에서 11~25번 케이스를 `//`로 비활성화하면 실제 active input은 10개가 된다.

예상 후보 수는 다음과 같다.

```text
10 active cases
x 2 input variants
x 3 retrievers
x top5
= 300 candidates
```

따라서 정상 결과는 다음과 비슷해야 한다.

```text
active_test_case_count = 10
input_variant_count = 2
retriever_count = 3
candidate_count = 300
```

이후 전체 후보 300개에 대해 `common_reranker_score`가 모두 존재해야 최종 비교가 가능하다.

## 12. 코드 수정 상세 계획

현재 스키마 검색 테스트 코드는 검색 후보 생성까지는 수행할 수 있지만, 최종 비교 기준인 `common_reranker_score`가 모든 후보에 붙지 않으면 계획 기준을 만족하지 못한다.

따라서 `run_full_optional_input_test.py`는 다음 구조로 수정한다.

```text
대상 파일:
etl/fault_cases/src/review_case/search/schema_search/run_full_optional_input_test.py
```

### 12.1 입력 로딩 단계

JSONL 입력은 다음 파일을 사용한다.

```text
etl/fault_cases/artifacts/review_case_output/schema_search_test/text_ml_case_search_agent_input_full_optional_fields.jsonl
```

로딩 규칙은 다음과 같다.

```text
1. 빈 줄은 건너뛴다.
2. // 로 시작하는 줄은 비활성 테스트 케이스로 보고 건너뛴다.
3. 각 활성 줄은 {"agent_input": {...}} 구조로 읽는다.
4. message_id가 있으면 query_id는 full_optional_{message_id}로 만든다.
```

현재 11~25번 케이스를 `//`로 비활성화했으므로 active input은 10개다.

### 12.2 검색 입력 생성 단계

각 `agent_input`에서 두 가지 검색 입력을 만든다.

```text
query_text:
  agent_input.query_text 그대로 사용

full_optional_context:
  query_text
  raw_user_text
  vision_evidence.description
  vision_evidence.observations
  ocr_evidence.accident_type
  ocr_evidence.accident_cause
  ocr_evidence.accident_description
  ocr_evidence.accident_location
  ocr_evidence.extracted_fields
  insurer_claim.claimed_ratio
  insurer_claim.reason_text
  insurer_claim.source_text
  를 검색용 텍스트로 결합
```

따라서 10개 활성 케이스 기준 검색 입력 수는 다음과 같다.

```text
10 active cases x 2 input variants = 20 search inputs
```

### 12.3 검색 실행 단계

각 검색 입력에 대해 다음 3개 검색 방식을 모두 실행한다.

```text
1. pgvector_cosine
2. bm25_nori
3. hybrid
```

각 검색 방식은 top5를 반환한다.

```text
20 search inputs x 3 retrievers x top5 = 300 candidates
```

각 candidate row에는 최소 다음 필드를 포함한다.

```text
query_id
message_id
input_variant
query
retriever
rank
review_case_id
review_no
chunk_id
chunk_type
case_title
reference_chart_key
retriever_score
score_type
chunk_preview
search_preview
```

retriever별 내부 점수는 다음처럼 보존한다.

```text
pgvector_cosine:
  cosine_similarity
  cosine_distance

bm25_nori:
  bm25_score

hybrid:
  hybrid_score
  bm25_rank
  bm25_score
  vector_rank
  vector_score
```

단, 이 내부 점수들은 직접 비교용이 아니다.

### 12.4 공통 reranker 평가 단계

검색 후보 300개를 모두 만든 뒤, 모든 candidate에 대해 같은 local reranker를 적용한다.

```text
reranker_model = models/bge-reranker-v2-m3
input_pair = query + chunk_text
fallback = query + search_preview 또는 query + chunk_preview
```

중요한 점은 reranker를 BM25 후보에만 적용하면 안 된다는 것이다.

```text
잘못된 상태:
  BM25 후보에만 common_reranker_score 존재
  pgvector 후보는 common_reranker_score 없음
  hybrid 후보는 common_reranker_score 없음

올바른 상태:
  pgvector 후보 전체에 common_reranker_score 존재
  BM25 후보 전체에 common_reranker_score 존재
  hybrid 후보 전체에 common_reranker_score 존재
```

따라서 10개 active input 기준으로 다음이 성립해야 한다.

```text
candidate_count = 300
reranker_pair_count = 300
common_reranker_score_not_null = 300
```

성능상 reranker는 후보 하나씩 호출하지 않고 batch로 처리한다.

```text
1. candidates 전체를 먼저 메모리에 모은다.
2. (query, candidate_text) pair 300개를 만든다.
3. CrossEncoder.predict를 batch_size 단위로 실행한다.
4. 예측 점수를 각 candidate row에 common_reranker_score로 저장한다.
```

### 12.6 보고서 계산 기준

보고서는 검색기 내부 점수와 공통 reranker 점수를 분리해서 보여준다.

검색기 내부 점수:

```text
avg_top1_internal_score
avg_at_5_internal_score
```

공통 비교 점수:

```text
avg_common_reranker_score
top1_common_reranker_score
max_common_reranker_score@5
min_common_reranker_score@5
```

최종 우열 판단은 공통 비교 점수로만 한다.

```text
최종 비교 기준:
  avg_common_reranker_score
  top1_common_reranker_score
  max_common_reranker_score@5
```

검색기 내부 점수는 다음 용도로만 사용한다.

```text
1. 검색기 내부 rank가 정상인지 확인
2. BM25, pgvector, hybrid가 각각 어떤 후보를 올렸는지 확인
3. 디버깅 및 설명용 참고 지표
```

### 12.7 정상 실행 후 기대 결과

10개 active input 기준 정상 실행 결과는 다음과 비슷해야 한다.

```text
active_test_case_count = 10
input_variant_count = 2
retriever_count = 3
candidate_count = 300
reranker_pair_count = 300
error_count = 0
```

retriever별 후보 수는 다음과 같아야 한다.

```text
pgvector_cosine = 100
bm25_nori = 100
hybrid = 100
```

input variant별 후보 수는 다음과 같아야 한다.

```text
query_text = 150
full_optional_context = 150
```

그리고 최종적으로 모든 후보에 다음 필드가 있어야 한다.

```text
common_reranker_score
```

이 조건을 만족해야 스키마 검색 테스트 결과를 검색 방식 비교 결과로 사용할 수 있다.
