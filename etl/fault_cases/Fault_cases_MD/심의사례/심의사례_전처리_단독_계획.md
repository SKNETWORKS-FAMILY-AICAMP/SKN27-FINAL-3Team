# 심의사례 전처리 단독 계획서

## 0. 정정

이번 계획의 대상은 **인정기준 전처리**가 아니라 **심의사례 전처리**다.

인정기준 ZIP은 참고용일 뿐이다.  
참고할 것은 인정기준의 데이터 내용이 아니라 아래 구조 철학이다.

```text
1. 원천 청크를 남긴다.
2. 구조화 결과를 따로 만든다.
3. 품질검증 리포트를 만든다.
```

따라서 이 문서에서는 인정기준 전처리는 제외하고, **심의사례 PDF를 어떻게 전처리할지**만 정리한다.

---

# 1. 우리가 계획하고 싶었던 것

우리가 계획하고 싶었던 것은 다음이다.

```text
자동차사고 과실비율분쟁 심의사례 PDF를
심의번호 기준으로 226개 사례로 나누고,
각 사례에서 사고상황, 주장, 증거, 쟁점, 결정근거, 결정이유, 과실비율을 뽑아
RAG/DB에 넣을 수 있는 구조화 데이터로 만드는 것
```

즉, 핵심 대상은 **심의사례**다.

---

# 2. 심의사례 전처리의 중심 키

심의사례의 중심 키는 **심의번호**다.

예시:

```text
심의번호 2018-051544
심의번호 2017-032889
```

따라서 사례 1건은 `review_no`를 기준으로 관리한다.

```json
{
  "review_case_id": "review_case_2018_051544",
  "review_no": "2018-051544"
}
```

---

# 3. 심의사례 1건에서 뽑아야 하는 순서

PDF 화면에 보이는 순서 그대로 파싱한다.

```text
[1] 상단 사고 분류
[2] 상단 기준 박스
[3] 사례 개요
    [3-1] 심의번호
    [3-2] 결정비율
    [3-3] 사고내용
[4] 참고 인정기준 설명
[5] 주장 내용
    [5-1] 청구인 주장
    [5-2] 피청구인 주장
[6] 입증 자료
[7] 주요 쟁점
[8] 결정 근거
[9] 결정 이유
[10] 최종 과실비율 문장
```

중요한 기준:

```text
참고 인정기준 설명 전에 반드시
심의번호 → 결정비율 → 사고내용
3개가 먼저 나온다.
```

또한:

```text
주장 내용은 청구인과 피청구인이 나뉜다.
청구인 주장과 피청구인 주장은 서로 다른 내용이다.
절대 하나로 합치면 안 된다.
```

# 4. [1] 상단 사고 분류

상단 사고 분류는 사례의 큰 유형이다.

예시:

```text
차대차 직진 대 직진 사고 - 사거리 교차로(상대 차량이 측면 방향에서 진입)
```

추출 필드:

| 필드 | 의미 | 예시 |
|---|---|---|
| party_type | 사고 당사자 유형 | 차대차 |
| header_title_raw | 상단 제목 원문 | 차대차 직진 대 직진 사고 - 사거리 교차로(...) |
| header_accident_group | 큰 사고유형 | 직진 대 직진 사고 |
| header_road_context | 도로/상황 맥락 | 사거리 교차로(상대 차량이 측면 방향에서 진입) |
| header_parse_method | 파싱 방식 | hyphen_split |

다른 형태:

```text
차대차 기타 도로유형 사고
```

이 경우:

```json
{
  "party_type": "차대차",
  "header_accident_group": "기타 도로유형 사고",
  "header_road_context": null,
  "header_parse_method": "single_group"
}
```

주의:

```text
header_road_context는 모든 사례에 있는 값이 아니다.
없다고 실패 처리하지 않는다.
```

# 5. [2] 상단 기준 박스

사용자가 빨간색으로 표시한 영역이다.

이 영역은 단순 참고기준만 있는 것이 아니라 아래 3개가 같이 있다.

```text
왼쪽: 사례 제목
가운데: 사고상황 키워드
오른쪽: 참고기준 도표번호
```

예시:

```text
이륜차 비보호 좌회전 사고 (수정과실)
신호등 있음
삼거리 교차로
비보호좌회전
녹색직진
참고기준 319
```

추출 필드:

| 필드 | 의미 | 예시 |
|---|---|---|
| case_title | 실제 사례 제목 | 이륜차 비보호 좌회전 사고 |
| case_condition | 세부 조건 | 없으면 null |
| fault_type | 기본/수정/준용 여부 | 수정과실 |
| reference_chart_key | 참고 도표번호 | 319 |
| reference_chart_no | 숫자 도표번호 | 319 |
| reference_chart_sub_no | 세부번호 | 없으면 null |
| standard_scenario_raw | 기준 박스 원문 | 신호등 있음 삼거리 교차로 비보호좌회전 녹색직진 |
| standard_scenario_keywords | 사고상황 키워드 배열 | ["신호등 있음", "삼거리 교차로", "비보호좌회전", "녹색직진"] |
| signal_condition | 신호 조건 | 신호등 있음 |
| road_feature | 도로 특징 | 삼거리 교차로 |
| standard_a_behavior | 도표상 A 행동 | 비보호좌회전 |
| standard_b_behavior | 도표상 B 행동 | 녹색직진 |

주의:

```text
상단 기준 박스 키워드를 accident_type에 억지로 넣지 않는다.
검색 핵심 필드인 standard_scenario_keywords로 따로 보존한다.
```

# 6. [3] 사례 개요

사례 개요는 본문 핵심 정보다.

반드시 아래 3개를 순서대로 뽑는다.

```text
심의번호
결정비율
사고내용
```

## 6-1. 심의번호

예시:

```text
심의번호 2018-051544
```

추출 필드:

```json
{
  "review_no": "2018-051544",
  "review_case_id": "review_case_2018_051544"
}
```

## 6-2. 결정비율

예시:

```text
결정비율 A(청구) : B(피청구) = 0 : 100
```

추출 필드:

| 필드 | 의미 |
|---|---|
| decision_fault_ratio | 원문 결정비율 |
| a_role | A가 청구인지 피청구인지 |
| b_role | B가 청구인지 피청구인지 |
| a_ratio | A 과실비율 |
| b_ratio | B 과실비율 |
| claimant_final_ratio | 청구인 최종 과실비율 |
| respondent_final_ratio | 피청구인 최종 과실비율 |

주의:

```text
A(청구) : B(피청구)인 사례도 있고,
A(피청구) : B(청구)인 사례도 있다.

따라서 A=청구로 고정하면 안 된다.
괄호 안의 청구/피청구를 읽어서 매핑한다.
```

## 6-3. 사고내용

예시:

```text
사고내용
신호기 있는 사거리 교차로에서 적색신호에 직진하던 피청구차량과 녹색신호에 직진하던 청구차량간의 충돌사고
```

추출 필드:

```json
{
  "accident_content": "신호기 있는 사거리 교차로에서 적색신호에 직진하던 피청구차량과 녹색신호에 직진하던 청구차량간의 충돌사고"
}
```

# 7. [4] 참고 인정기준 설명

사례 개요 다음에 나오는 설명이다.

예시:

```text
참고 인정기준 201
신호기가 있는 교차로에서 신호는 양 차량 운전자가 신뢰하는 것으로...
기본비율 A : B = 0 : 100
```

추출 필드:

| 필드 | 의미 |
|---|---|
| reference_standard_no | 참고 인정기준 번호 |
| reference_standard_text | 기준 설명 원문 |
| base_fault_ratio_text | 기본비율 문장 |

주의:

```text
참고 인정기준 설명은 사례 개요 뒤에 온다.
따라서 심의번호, 결정비율, 사고내용보다 먼저 파싱하면 안 된다.
```

# 8. [5] 주장 내용

주장 내용은 반드시 청구인과 피청구인으로 나눈다.

PDF에서는 2단 표 형태로 나온다.

```text
주장 내용

청구인
- 청구인 주장 내용

피청구인
- 피청구인 주장 내용
```

추출 필드:

| 필드 | 의미 |
|---|---|
| claimant_argument | 청구인 주장 |
| respondent_argument | 피청구인 주장 |

검증 기준:

```text
claimant_argument 없음 = fatal
respondent_argument 없음 = fatal
claimant_argument와 respondent_argument가 완전히 같음 = fatal 또는 강한 warning
```

처리 방법:

```text
1. 좌표 기반 분리 우선
2. 왼쪽 컬럼을 청구인으로 본다.
3. 오른쪽 컬럼을 피청구인으로 본다.
4. 좌표 정보가 없으면 라벨 기반 분리로 fallback한다.
```

# 9. [6] 입증 자료

입증 자료는 판단 근거의 출처가 되는 자료다.

예시:

```text

차량 파손 사진
블랙박스 영상
```

추출 필드:

```json
{
  "evidence_text": "교통사고사실확인원, 차량 파손 사진, 블랙박스 영상 ..."
}
```

# 10. [7] 주요 쟁점

주요 쟁점은 심의에서 다툰 핵심이다.

예시:

```text

추출 필드:

```json

  "main_issue": "피청구차량이 적색신호에 신호기 있는 교차로를 진입하였는지 여부"
}
```

# 11. [8] 결정 근거

결정 근거는 위원회가 사실관계를 인정한 근거다.

예시:

```text
결정 근거

```

추출 필드:

```json
{

}
```

# 12. [9] 결정 이유

결정 이유는 최종 판단 설명이다.

예시:

```text
결정 이유
교통사고사실확인원상 신호기 있는 사거리 교차로에서 피청구차량이 적색신호에 교차로를 직진하였고...
청구차량 0% / 피청구차량 100%
```

추출 필드:

| 필드 | 의미 |
|---|---|
| decision_reason | 결정 이유 |
| final_ratio_text | 마지막 과실비율 문장 |

# 14. 심의사례 전처리 파일 구조

인정기준 전처리는 제외한다.  
심의사례만 기준으로 하되, `review_case` 루트의 공통 파일과 이번 전처리 직접 대상 파일을 구분한다.

중요한 정정:

```text
review_case/__init__.py
review_case/config.py
review_case/paths.py
review_case/models.py
review_case/run_pipeline.py
```

위 파일들은 이미 `review_case` 패키지의 수집/공통 실행 기반으로 쓰이는 파일이다.  
따라서 “심의사례 전처리 신규 파일 구조”에는 포함하지 않고, 필요 시 설정값·모델·라우터를 보강하는 공통 파일로만 본다.

## 14-1. 산출물 구조

```text
etl/fault_cases/
├── artifacts/
│   └── review_case_output/
│       ├── crawled/
│       │   └── (최종)과실비율심의사례_(54MB).pdf
│       └── preprocessed/
│           ├── review_case_documents.jsonl
│           ├── review_case_chunks.jsonl
│           ├── quality_report.jsonl
│           ├── preprocessing_summary.json
│           ├── loader_report.json
│           ├── page_coverage.json
│           ├── cases_json/
│           └── toc/
│               ├── review_case_toc_items.jsonl
│               └── review_case_toc_case_links.jsonl
```

## 14-2. 기존/공통 파일

아래 파일들은 전처리 전용 parser가 아니라 패키지 공통 기반이다.

```text
etl/fault_cases/src/review_case/
├── __init__.py          # 패키지 인식
├── config.py            # 수집/전처리 공통 설정, 환경변수 override
├── paths.py             # 산출물 경로/파일명 관리
├── models.py            # 수집/전처리 공통 dataclass 모델
└── run_pipeline.py      # crawl/preprocess stage router
```

정리 기준:

```text
신규 전처리 구조 설명에서는 제외
단, 이번 수정에서 필드/설정이 필요하면 보강 대상은 될 수 있음
```

## 14-3. 심의사례 전처리 직접 대상 파일

현재 전처리 로직의 중심은 `preprocessing/` 아래 파일들이다.

```text
etl/fault_cases/src/review_case/preprocessing/
├── __init__.py
├── pdf_loader.py                  # PDF 페이지 텍스트/좌표 추출
├── cleaner.py                     # 텍스트 정리, 라벨 복구
├── toc_parser.py                  # 목차 도표 item 추출

## 14-4. 수집 파일은 전처리 구조와 분리

`crawling/` 폴더는 심의사례 PDF 수집 단계다. 전처리 파일 구조 설명에서는 별도 범주로만 둔다.

```text
etl/fault_cases/src/review_case/crawling/
└── ... PDF 수집/검증 관련 파일
```

전처리 실행은 수집 결과 PDF를 입력으로 받아 아래 명령으로 수행한다.

```bash
python -m src.review_case.run_pipeline --stage preprocess --write-case-json-files
```

# 19. 최종 한 줄 정리

```text
이번 계획은 인정기준이 아니라 심의사례 전처리 계획이다.
심의번호 기준으로 사례를 나누고,
상단 사고 분류 → 상단 기준 박스 → 사례 개요 → 참고 인정기준 → 주장 → 입증자료 → 쟁점 → 결정근거 → 결정이유 순서대로 뽑는다.
