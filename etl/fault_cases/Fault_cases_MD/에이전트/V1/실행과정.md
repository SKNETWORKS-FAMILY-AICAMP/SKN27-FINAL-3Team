# text_ml_case_search Agent / RAG V1 실행과정

생성일: 2026-07-04

## 0. 기록 목적

이 문서는 `text_ml_case_search` Agent / RAG V1 구현 과정에서 실제로 진행한 작업, 생성/수정한 파일, 실행한 명령, 확인된 결과를 누적 기록한다.

질문이나 개념 설명만 한 내용은 원칙적으로 기록하지 않는다.  
코드 생성, 코드 수정, MD 수정, 테스트 실행, 검증 결과처럼 나중에 다시 추적해야 하는 작업만 기록한다.

## 13단계. active 10개 실행 결과 JSON/MD 리포트 생성

### 진행 이유

12단계에서 `full optional input` active 10개를 실제 Elasticsearch BM25+Nori RAG가 연결된 Agent로 실행했다.

그 결과는 JSONL 원본으로는 매우 길고, 사람이 바로 판단하기 어렵다. 그래서 13단계에서는 기존 실행 결과를 다시 검색하거나 Agent를 다시 돌리지 않고, 이미 생성된 산출물을 읽어서 아래 내용을 정리한다.

```text
1. active input 10개가 모두 success인지
2. 각 입력마다 evidence가 붙었는지
3. similar_cases와 display_evidence가 생성됐는지
4. ratio_range_label이 채워졌는지
5. 사람이 확인해야 할 encoding/display warning이 있는지
```

이 단계의 목적은 검색 성능 최종 평가가 아니라, Agent V1 출력 구조가 Supervisor에게 넘길 수 있는 형태로 안정적으로 생성되는지 확인하는 것이다.

## 14단계. Supervisor 연동용 Agent 입출력 계약 최종 정리

### 진행 이유

13단계까지는 Agent가 실제 active 10개 입력을 받아 RAG evidence를 붙이고 JSON/MD 리포트를 만들 수 있는지 확인했다.

그 다음 단계에서는 새 검색 기능을 더 붙이기보다, Supervisor가 이 Agent 결과를 어떻게 받아야 하는지 계약을 고정해야 한다.

이 작업이 필요한 이유:

```text
1. Supervisor가 어떤 필드를 사용자 답변에 써야 하는지 명확히 해야 한다.
2. evidence 원문과 사용자 표시용 display_evidence를 구분해야 한다.
3. search_text/rag_debug 같은 개발용 필드를 사용자 출력용 필드와 구분해야 한다.
4. 나중에 판례/인정기준 검색을 붙여도 V1 계약이 흔들리지 않게 해야 한다.
5. output schema가 바뀌었을 때 contract_version으로 구분할 수 있어야 한다.
```

## 22. 11단계: 흐름도 기준 케이스 0~4 테스트

### 진행한 이유

10단계까지는 BM25 검색 정책과 Agent 검색 정책이 같은지 확인하는 단계였다.
11단계는 검색 정책 자체가 아니라, Agent가 실제 흐름도에서 정의한 상황별 분기에서 안전한 output을 반환하는지 확인하는 단계다.

흐름도 기준 분기는 다음 5개다.

```text
케이스 0:
  query_text 없음

케이스 1:
  보험사 주장 없음 + RAG 근거 없음

케이스 2:
  보험사 주장 없음 + RAG 근거 있음

케이스 3:
  보험사 주장 있음 + RAG 근거 없음

케이스 4:
  보험사 주장 있음 + RAG 근거 있음
```

이 테스트를 하는 이유는 다음과 같다.

```text
1. Supervisor는 항상 안전한 JSON을 받아야 한다.
2. RAG 근거가 없어도 Agent가 터지면 안 된다.
3. 보험사 주장이 있어도 RAG 근거가 없으면 비교 불가 상태를 명확히 표현해야 한다.
4. RAG 근거가 있으면 evidence, similar_cases, ratio_range_label, display_evidence가 함께 채워져야 한다.
5. 케이스별 status, evidence, insurer_claim_review 상태가 의도와 맞는지 고정해야 한다.
```

### 흐름도와 현재 구현의 차이

흐름도에는 케이스 0이 `partial`로 표현되어 있지만,
현재 V1 구현은 필수 입력인 `query_text`가 없으면 `failed`를 반환한다.

이유:

```text
query_text가 없으면 사고 설명, 검색문 생성, RAG 검색이 모두 불가능하다.
따라서 V1에서는 partial보다 failed가 더 명확한 계약이다.
```

또한 흐름도에는 케이스 3에서 `insurer_claim_review: null`처럼 표현되어 있지만,
현재 V1 구현은 보험사 주장이 있으면 RAG 근거가 없어도 `insurer_claim_review`를 만든다.

이유:

```text
보험사 주장 자체를 정리하고,
reference_evidence_count = 0,
limitations = No RAG evidence...
형태로 비교 불가 상태를 명확히 남기기 위해서다.
```

즉 11단계 테스트는 흐름도를 그대로 기계적으로 복사한 것이 아니라,
현재 구현 계약을 반영한 흐름도 기반 안전성 테스트다.

## 20. 9-1단계: 사용자 표시용 evidence 텍스트 정리

### 진행한 이유

9단계까지 진행하면서 실제 BM25+Nori RAG 결과가 Agent output의 `evidence`에 들어오게 됐다.
하지만 `evidence`는 원천 근거 보존용에 가깝다.

원천 evidence에는 다음 값들이 섞일 수 있다.

```text
chunk_text:
  원문에 가까운 긴 근거 텍스트

metadata.highlight:
  Elasticsearch가 검색어 매칭 부분에 붙이는 <em> 태그 포함 가능

metadata.score / metadata.index:
  내부 검색 점수와 index 정보
```

이 값을 그대로 사용자 또는 Supervisor 표시용으로 쓰면 다음 문제가 생긴다.

```text
1. 사용자 화면에 너무 긴 원문이 그대로 노출될 수 있다.
2. <em> 태그가 최종 응답에 섞일 수 있다.
3. BM25 score를 사용자에게 보여주면 관련성 점수로 오해할 수 있다.
4. 원천 근거와 표시용 근거의 역할이 섞인다.
```

그래서 원본 `evidence`는 유지하고,
Supervisor/UI가 보기 쉬운 `display_evidence`를 별도로 만들기로 했다.

### 구현한 파일


### 구현 내용

```text

build_display_evidence_item()

```

표시용 근거에는 다음 값을 넣는다.

```text

title

reference_chart_key
ratio_label
```

### 처리 규칙


## 12. 단계별 이유/근거 보강 정리

일시: 2026-07-04

### 12.1 계획 문서 정렬을 먼저 한 이유

처음부터 코드만 만들지 않고 RAG/Agent 계획 문서를 먼저 맞춘 이유는 다음과 같다.

```text
1. text_ml_case_search Agent는 단순 검색기가 아니라 Supervisor가 호출하는 업무 Agent다.
2. 심의사례, 판례, 인정기준까지 최종적으로 엮일 수 있으므로 폴더 구조와 역할 경계가 먼저 맞아야 한다.
3. 기존 review_case 검색 코드는 테스트/검증 산출물이고, Agent 코드는 운영 흐름에 들어갈 코드라 책임이 다르다.
4. 계획 문서와 실제 코드 구조가 다르면 이후 구현자가 어디를 고쳐야 하는지 혼란이 생긴다.
```

따라서 먼저 다음 결정을 문서에 반영했다.

```text
V1:
  review_case BM25+Nori 기반 RAG부터 구현

V1.1:
  local reranker 후보

V2:
  review_case + precedent + fault_standard 통합 가능성 확장
```

이 결정의 핵심은 “처음부터 모든 source를 붙이지 않고, 심의사례부터 안정화한다”는 것이다.

### 12.2 `agents/text_ml_case_search` 폴더를 새로 만든 이유

`review_case` 폴더 안에 Agent 코드를 넣지 않은 이유는 다음과 같다.

```text
review_case:
  심의사례 전처리, DB 적재, 검색 실험, 인덱싱 코드의 영역

agents/text_ml_case_search:
  Supervisor가 호출하는 업무 Agent 영역
```

`text_ml_case_search`는 심의사례만 검색하는 모듈이 아니라, 사용자 입력을 받아 사고 설명 정규화, 쟁점 태깅, 근거 검색, 보험사 주장 검토, 추가 증거자료 추천까지 조립하는 Agent다.

그래서 다음처럼 분리했다.

```text
input/
  입력 검증, context 정리, 사고 정규화, 쟁점 태깅

rag/
  검색문 생성, BM25 검색, hit mapping, evidence 검증

builders/
  최종 output의 부분 구조 생성

agent.py
  전체 흐름 조립
```

예상 효과:

```text
1. review_case 전처리/검색 실험 코드와 Agent 운영 코드가 섞이지 않는다.
2. 나중에 판례/인정기준 retriever를 붙여도 agents 폴더 안에서 확장 가능하다.
3. Supervisor가 호출할 진입점이 명확해진다.
```

### 12.3 skeleton을 먼저 만든 이유

RAG 검색을 바로 붙이지 않고 skeleton을 먼저 만든 이유는 다음과 같다.

```text
1. RAG는 실패할 수 있다.
2. Elasticsearch가 꺼져 있을 수 있다.
3. 검색 결과가 0건일 수 있다.
4. 그래도 Agent는 Supervisor에게 안정적인 JSON을 반환해야 한다.
```

그래서 먼저 다음 상태를 확인했다.

```text
query_text 있음 + RAG 없음:
  status = partial
  evidence = []
  similar_cases = []
  limitations 포함

query_text 없음:
  status = failed
  missing_fields 포함
```

이유:

```text
Agent의 기본 안전성을 먼저 보장해야 이후 RAG 연결이 실패해도 전체 LangGraph/Supervisor 흐름이 깨지지 않는다.
```

### 12.4 normalizer / issue_tagger를 먼저 만든 이유

검색 전에 사고유형 후보와 쟁점 태그를 먼저 만드는 이유는 다음과 같다.

```text
1. 사용자의 자연어 입력은 길고 불안정하다.
2. BM25+Nori는 검색어에 포함된 명사/구문 영향을 많이 받는다.
3. 사고유형과 쟁점을 정리해두면 schema_search_text를 만들 때 검색 품질을 높일 수 있다.
4. 같은 쟁점 태그를 recommended_evidence, insurer_claim_review에서도 재사용할 수 있다.
```

즉 `issue_tags`는 단순 표시용이 아니라 다음 모듈들의 공통 재료다.

```text
search_text_builder
recommended_evidence_builder
insurer_claim_review_builder
future evidence_validator
future similar_case_builder
```

남은 보완점:

```text
현재 일부 샘플에서 "신호 없는 교차로"보다 "차로 변경"이 우선 잡히는 문제가 있다.
이건 normalizer 규칙 우선순위 조정 대상이다.
```

### 12.5 `recommended_evidence_builder.py`를 분리한 이유

추가 증거자료 추천을 `agent.py` 안에 넣지 않고 별도 builder로 뺀 이유는 다음과 같다.

```text
1. Agent.py는 전체 흐름 조립만 담당해야 한다.
2. 증거자료 추천 규칙은 계속 바뀔 가능성이 높다.
3. issue_tags와 evidence 상태에 따라 추천 항목이 달라지므로 별도 테스트가 필요하다.
4. Supervisor/UI가 읽을 수 있는 구조로 추천 항목을 만들려면 출력 스키마가 커진다.
```

그래서 `recommended_evidence`는 다음 구조로 확장했다.

```text
type:
  내부 코드/필터용

title:
  UI 또는 Supervisor가 제목처럼 쓸 수 있는 짧은 이름

description:
  사용자에게 보여줄 수 있는 설명

related_issue:
  어떤 쟁점 때문에 필요한 자료인지

priority:
  high / medium / low

based_on:
  어떤 입력 또는 분석 결과에서 추천됐는지
```

예상 효과:

```text
1. Supervisor가 사용자에게 "어떤 자료를 더 준비해야 하는지" 설명하기 쉬워진다.
2. 나중에 UI에서 증거자료 체크리스트로 바꾸기 쉽다.
3. 추천 기준만 바꾸고 싶을 때 Agent 전체를 건드리지 않아도 된다.
```

### 12.6 `source_ref` alias 처리를 넣은 이유

`source_reference`를 표준으로 정했지만 `source_ref`도 입력에서 허용한 이유는 다음과 같다.

```text
1. 외부 모듈이나 이전 테스트셋에서 source_ref라는 이름을 쓸 수 있다.
2. 이런 입력 하나 때문에 Agent가 실패하면 운영 안정성이 떨어진다.
3. 다만 최종 output 필드명은 하나로 통일해야 한다.
```

정책:

```text
입력:
  source_ref 허용

내부 context:
  source_reference로 변환

최종 output:
  source_ref 미사용
```

이유:

```text
입력 호환성은 넓게 가져가고, 출력 계약은 좁고 명확하게 유지하기 위해서다.
```

### 12.7 `search_text_builder.py`를 먼저 만든 이유

BM25 검색을 바로 붙이지 않고 검색문 생성기를 먼저 만든 이유는 다음과 같다.

```text
1. Agent input은 query_text 하나만 있는 것이 아니다.
2. raw_user_text, vision_evidence, ocr_evidence, insurer_claim이 검색 품질에 영향을 줄 수 있다.
3. 하지만 이 모든 값을 그대로 검색기에 넘기면 검색문이 불안정해진다.
4. 검색 전에 어떤 문자열을 검색기에 넣을지 고정해야 BM25 결과를 재현할 수 있다.
```

그래서 `search_text`를 세 가지로 나눴다.

```text
natural_query_text:
  사용자의 핵심 query_text

schema_search_text:
  사고유형, 쟁점, 사고설명, OCR, 보험사 주장을 한 줄 검색문으로 정리한 문자열

full_optional_context:
  섹션 구조를 유지한 긴 검색 context
```

예상 효과:

```text
1. BM25 retriever가 어떤 입력을 받는지 명확해진다.
2. 나중에 query_text vs full_optional_context A/B 테스트가 가능하다.
3. 검색 결과가 이상할 때 검색문 자체를 보고 원인을 찾을 수 있다.
```

### 12.8 `__init__.py` eager import를 제거한 이유

`python -m etl.fault_cases.src.agents.text_ml_case_search.agent --sample` 실행 시 RuntimeWarning이 발생했다.

원인:

```text
패키지 __init__.py에서 agent.py를 먼저 import했다.
그 상태에서 다시 python -m으로 agent.py를 실행하면 같은 모듈이 중복 로딩될 수 있다는 경고가 나온다.
```

조치:

```text
__init__.py에서 run_text_ml_case_search eager import 제거
```

이유:

```text
1. 패키지 초기화는 가볍게 유지한다.
2. CLI 실행 로그가 지저분해지는 것을 막는다.
3. 실제 Agent import는 필요한 위치에서 명시적으로 하도록 한다.
```

### 12.9 Agent 전용 BM25+Nori retriever를 만든 이유

기존 `review_case/search/elasticsearch/bm25_retriever.py`를 호출하지 않고 Agent 폴더에 새 `bm25_nori_retriever.py`를 만든 이유는 다음과 같다.

```text
1. 기존 review_case BM25 코드는 검색 실험/검증용 성격이 강하다.
2. Agent V1 운영 흐름에서는 agents/text_ml_case_search/rag 아래 코드가 기준이 되어야 한다.
3. 그래야 이후 Agent 검색 정책을 수정할 때 Agent 폴더만 보면 된다.
4. 기존 실험 코드와 운영 코드가 서로 다른 목적으로 진화할 수 있다.
```

중요한 기준:

```text
기존 retriever를 호출하지 않는다.
기존 BM25 검색 조건만 Agent retriever로 이관한다.
```

이관한 조건:

```text
BM25_SEARCH_FIELDS
operator = or
highlight.search_text
highlight.chunk_text
type = best_fields
```

예상 효과:

```text
1. Agent V1 검색 정책이 Agent 폴더 안에 고정된다.
2. 기존 검증 코드와 Agent 운영 코드의 책임이 분리된다.
3. top_k chunk_id 일치 검증으로 이관이 제대로 되었는지 확인할 수 있다.
```

### 12.10 `operator="or"`를 유지한 이유

BM25 query에서 `operator="or"`를 유지한 이유는 다음과 같다.

```text
1. 교통사고 검색문은 길고 여러 쟁점이 섞일 수 있다.
2. operator="and"를 쓰면 모든 토큰이 맞아야 해서 후보가 과도하게 줄어든다.
3. V1 목표는 완벽한 정답 하나가 아니라 안정적인 후보 evidence 확보이다.
```

예상 효과:

```text
검색 결과가 0건으로 떨어지는 위험을 줄인다.
다만 약한 후보도 들어올 수 있으므로 evidence_validator 또는 reranker로 보정할 수 있다.
```

### 12.11 highlight를 유지한 이유

Elasticsearch highlight를 유지한 이유는 다음과 같다.

```text
1. 어떤 문장 또는 필드가 검색어와 맞았는지 확인할 수 있다.
2. 디버깅에 도움이 된다.
3. 추후 matched_facts 생성의 보조 재료로 쓸 수 있다.
```

단, V1에서는 highlight를 사용자에게 그대로 보여주지 않는다.

```text
V1:
  metadata 내부 참고값

향후:
  matched_facts 보강 재료
```

### 12.12 `evidence_mapper.py`를 만든 이유

BM25 raw hit을 그대로 Agent output에 넣지 않고 mapper를 만든 이유는 다음과 같다.

```text
1. Elasticsearch hit은 검색엔진 결과 형식이다.
2. Supervisor가 필요한 것은 source_type, source_reference, metadata, chunk_text가 정리된 evidence 구조다.
3. 검색엔진별 점수 필드나 highlight 구조를 그대로 노출하면 output schema가 흔들린다.
```

mapper가 하는 일:

```text
BM25 raw hit
-> review_case evidence
-> source_reference 생성
-> metadata.standard_context 구성
-> decision_fault_ratio / reference_chart_key 보존
```

예상 효과:

```text
1. Agent output의 evidence 구조가 source별로 통일된다.
2. 추후 precedent mapper를 추가해도 같은 evidence schema로 합칠 수 있다.
3. Supervisor는 검색엔진 내부 구조를 몰라도 근거를 사용할 수 있다.
```

### 12.13 `source_reference.py`를 분리한 이유

`source_reference` 생성 로직을 evidence_mapper 내부에 직접 넣지 않고 분리한 이유는 다음과 같다.

```text
1. source_reference는 evidence뿐 아니라 similar_cases, citation, debug log에서도 다시 쓸 수 있다.
2. review_case_id가 없을 때 review_no로 fallback하는 규칙을 한 곳에 두는 것이 안전하다.
3. source_reference 형식이 바뀌면 한 파일만 고치면 된다.
```

현재 규칙:

```text
review_case_db:{review_case_id or review_no or unknown_review_case}#{chunk_id or unknown_chunk}
```

### 12.14 테스트를 fake client 중심으로 만든 이유

BM25 retriever와 mapper 테스트를 실제 Elasticsearch 없이 fake client로 만든 이유는 다음과 같다.

```text
1. 단위 테스트는 빠르게 돌아야 한다.
2. Docker/Elasticsearch 상태에 따라 실패하면 코드 문제인지 환경 문제인지 구분하기 어렵다.
3. 지금 단계의 목적은 query body와 hit parsing이 맞는지 확인하는 것이다.
```

따라서 실제 ES 연결 검증은 다음 단계에서 별도 통합 테스트로 한다.

```text
단위 테스트:
  fake client

통합 테스트:
  실제 Elasticsearch
```

다음 작업들이 남아 있다.

```text

   이유:

6. 실제 Elasticsearch 통합 확인
```

### 12.16 현재까지의 설계 원칙

현재까지의 구현 원칙은 다음과 같다.

```text
1. Agent는 최종 사용자 답변을 만들지 않는다.
2. Agent는 Supervisor가 사용할 구조화 결과를 만든다.
3. review_case V1부터 안정화한다.
4. 기존 review_case 검색 실험 코드는 호출하지 않고, 검증된 조건만 Agent 폴더로 이관한다.
5. 검색 실패/무결과 상황에서도 JSON output은 안정적으로 반환한다.
6. 입력 호환성은 넓게, 출력 schema는 좁고 명확하게 유지한다.
7. PowerShell 실행이 필요한 단계는 사용자가 직접 실행한다.
```

## 13. 6단계 일부: evidence_validator.py 작성

일시: 2026-07-04

### 목적

BM25+Nori 검색 결과를 evidence로 변환한 뒤, Supervisor에게 넘기기 전에 최소 품질 기준을 통과한 근거만 남기기 위해 `evidence_validator.py`를 작성했다.

### 왜 이 단계를 진행하는가

검색 결과는 항상 좋은 근거라는 보장이 없다.

예상 가능한 문제:

```text
1. source_type이 비어 있어 어떤 출처의 근거인지 알 수 없음
2. source_reference가 없어 나중에 인용/추적이 불가능함
3. metadata가 없어 점수, 기준표, 심의번호 같은 정보를 붙일 수 없음
4. chunk_text가 너무 짧아 실제 답변 근거로 쓰기 어려움
```

이런 값을 그대로 Supervisor에게 넘기면 다음 문제가 생긴다.

```text
1. 최종 답변에서 근거 출처를 설명하기 어렵다.
2. similar_cases를 만들 때 빈약한 사례가 섞인다.
3. 보험사 주장 비교나 ratio_range_label 생성 근거가 약해진다.
4. RAG는 성공한 것처럼 보이지만 실제 답변 품질은 떨어진다.
```

따라서 검색 직후가 아니라, `BM25 raw hit -> evidence` 변환 이후에 validator를 둔다.

```text
BM25 raw hit
-> evidence_mapper
```

## 14. retrieval_pipeline.py 작성

### 진행한 작업

다음 파일을 추가했다.

```text

etl/fault_cases/src/agents/text_ml_case_search/tests/test_retrieval_pipeline.py
```

### 왜 진행했는지

6단계에서 BM25+Nori 검색기, evidence mapper, evidence validator를 각각 만들었지만,
이 상태 그대로 두면 `agent.py`가 검색 세부 절차를 직접 알아야 한다.

그렇게 되면 Agent 본문에 아래 로직이 섞인다.

```text
1. 어떤 search_text variant를 쓸지 선택
2. BM25+Nori 검색 실행
3. raw hit을 Agent evidence 구조로 변환
4. 너무 짧거나 source_reference가 부족한 evidence 제거
5. 검색 결과 개수와 검증 결과를 디버그용으로 남김
```

그래서 이 흐름을 `retrieval_pipeline.py`로 분리했다.

목적은 다음과 같다.

```text
agent.py:
  입력 검증, 정규화, 최종 응답 조립에 집중

retrieval_pipeline.py:
  RAG 검색 흐름 조립에 집중
```

### 구현한 흐름

```text
search_text_builder 출력
  -> retrieval_pipeline.select_search_text()
  -> bm25_nori_retriever.search_bm25_nori()
  -> evidence_mapper.map_review_case_hits_to_evidence()
  -> evidence_validator.validate_evidence()
  -> evidence + validation_report 반환
```

### 주요 함수

```text
select_search_text(search_text, search_variant)
run_review_case_bm25_pipeline(es, search_text, search_variant, index_names, top_k, min_text_len)
```

### search_text variant 선택 규칙

요청한 variant가 있으면 우선 사용한다.

예:

```text
search_variant = schema_search_text
```

요청한 값이 비어 있으면 아래 순서로 fallback한다.

```text
1. schema_search_text
2. full_optional_context
3. normalized_description
4. natural_query_text
```

이유:

```text
실제 Supervisor/Agent 입력에서 일부 필드가 비어 있어도 검색이 완전히 죽지 않게 하기 위해서다.
다만 어떤 variant가 실제로 사용됐는지는 결과에 search_variant로 남긴다.
```

이유:

```text
Agent 응답에는 최종 evidence만 쓰면 되지만,
개발/검증 단계에서는 raw hit 수, 매핑 수, 검증 통과 수가 필요하다.
검색 결과가 부족할 때 검색 문제인지, mapping 문제인지, validation 문제인지 분리해서 볼 수 있다.
```

### 비밀번호 fallback 제거

초기 구현에서는 Docker 개발 기본값에 맞춰 `"change-me"` fallback을 둘 수 있었지만,

```text

따라서 Elasticsearch 비밀번호는 .env에 명시하고, 코드에는 환경변수 이름만 남긴다.
```

### 왜 기록했는지

따라서 테스트 코드의 목적과 보안 기준을 문서에 명확히 남겼다.

### 테스트 폴더의 의미

`etl/fault_cases/src/agents/text_ml_case_search/tests/`는 운영 실행용 코드가 아니다.

운영 실행은 아래 코드가 담당한다.

```text
agent.py
rag/es_client.py
rag/retrieval_pipeline.py
rag/bm25_nori_retriever.py
rag/evidence_mapper.py
rag/evidence_validator.py
```

`tests/`는 위 코드가 계획한 규칙을 지키는지 확인하는 검증 코드다.

### test_es_client.py의 목적

`test_es_client.py`는 실제 Elasticsearch에 접속하지 않는다.

검증하는 것은 다음 세 가지다.

```text
1. username + password가 있으면 basic_auth를 만든다.
2. username이 없으면 인증 없이 client kwargs를 만든다.
3. username은 있는데 password가 없으면 ValueError를 낸다.
```

### 테스트용 password 문자열의 의미

테스트 안의 `test-password` 같은 문자열은 실제 비밀번호가 아니다.

이 값은 다음 동작을 확인하기 위한 더미 입력이다.

```text
입력:
  username = elastic
  password = test-password

기대:
  basic_auth = ("elastic", "test-password")
```

즉 목적은 비밀번호 자체가 아니라, 입력된 password가 client kwargs에 올바르게 전달되는지 확인하는 것이다.

### 보안 기준

실제 Elasticsearch 비밀번호는 `.py` 파일에 넣지 않는다.

반드시 `.env`에서 주입한다.

```env
TEXT_ML_CASE_SEARCH_ELASTICSEARCH_PASSWORD=...
```

또는 기존 공통 값을 사용한다.

```env
ELASTIC_PASSWORD=...
```

### 왜 필요한가

이 기준을 둔 이유는 다음과 같다.

```text
1. 코드에 실제 비밀번호가 남는 것을 막는다.
2. 개발 기본값을 실수로 운영에 가져가는 일을 막는다.
3. ES 인증 설정 누락을 조용히 넘기지 않고 즉시 드러낸다.
4. Agent/RAG 검색 정책 변경 시 테스트로 회귀 여부를 확인한다.
```

### 계획 문서 반영

같은 기준을 아래 계획 문서에도 추가했다.

```text

etl/fault_cases/Fault_cases_MD/에이전트/에이전트_V1_구현_계획_실코드정렬_수정본.md
```

## 번외. Elasticsearch 비밀번호 변경 시 처리 절차

### 왜 기록했는지

`run_agent_sample.py` 실행 중 아래 문제가 발생할 수 있다.

```text
AuthenticationException(401)
unable to authenticate user [elastic]
```

이 경우 `.env`에 `ELASTIC_PASSWORD`가 있어도, 현재 떠 있는 Elasticsearch 컨테이너의 실제 `elastic` 계정 비밀번호와 다를 수 있다.

### 원인

Elasticsearch의 `ELASTIC_PASSWORD`는 보통 컨테이너의 데이터 볼륨이 처음 초기화될 때 적용된다.

따라서 아래처럼 `.env`만 바꾸는 것으로는 기존 계정 비밀번호가 자동 변경되지 않을 수 있다.

```text
이미 elasticsearch_data 볼륨 존재
-> .env의 ELASTIC_PASSWORD 변경
-> docker compose up -d
-> 기존 Elasticsearch 내부 elastic 계정 비밀번호는 그대로 유지될 수 있음
```

그래서 Python client에서는 다음처럼 인증 실패가 날 수 있다.

```text
.env의 ELASTIC_PASSWORD 값 != Elasticsearch 내부 elastic 계정 비밀번호
```

### 추천 방식 A: 데이터 유지하고 비밀번호만 재설정

기존 Elasticsearch index를 유지하려면 이 방식을 우선 사용한다.

PowerShell에서 실행:

```powershell
docker compose exec elasticsearch bin/elasticsearch-reset-password -u elastic -i
```

실행 후 새 비밀번호를 입력한다.

그 다음 `.env`의 값을 동일하게 맞춘다.

```env
ELASTIC_PASSWORD=방금_설정한_비밀번호
```

이후 Agent sample runner를 다시 실행한다.

```powershell
.\.venv\Scripts\python.exe -B -m etl.fault_cases.src.agents.text_ml_case_search.run_agent_sample
```

예상 결과:

```text
1. Elasticsearch 인증 성공
2. BM25+Nori 검색 실행
3. Agent output에 evidence와 rag_debug가 포함됨
```

### 방식 B: 데이터 볼륨까지 초기화

이 방식은 Elasticsearch index가 삭제될 수 있으므로 기본 추천은 아니다.

```powershell
docker compose down
docker volume rm <elasticsearch_data_volume_name>
docker compose up -d elasticsearch kibana
```

주의:

```text
이 방식은 BM25/Nori index, vector/hybrid index를 다시 만들어야 할 수 있다.
따라서 단순 비밀번호 변경이면 방식 A를 우선한다.
```

### 결론

```text
비밀번호만 바꿨다면 방식 A:
  docker compose exec elasticsearch bin/elasticsearch-reset-password -u elastic -i

데이터를 완전히 초기화해야 할 때만 방식 B:
  docker compose down + volume 삭제
```
