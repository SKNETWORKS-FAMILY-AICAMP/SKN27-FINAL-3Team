# `text_ml_case_search` Agent V1 구현 계획 - 실제 코드베이스 정렬 수정본

생성일시: 2026-07-04T12:33:24

## 0. 문서 목적

이 문서는 `text_ml_case_search` Agent V1을 실제 코드베이스 기준으로 구현하기 위한 상세 계획서다.

핵심 전제는 다음이다.

```text
우리는 딱 Supervisor에게 output을 돌려주는 5번까지 담당한다.
최종 사용자 답변은 우리 Agent가 만들지 않는다.
```

담당 흐름은 아래 5단계다.

```text
1. Supervisor가 사용자 입력을 보고 text_ml_case_search를 호출한다.
2. Supervisor는 우리가 정한 agent_input schema를 우리에게 보낸다.
3. 우리는 BM25+Nori 기반 RAG로 유사 근거를 찾는다.
4. 우리는 최종 답변을 만들지 않고 evidence / similar_cases / ratio_range_label / insurer_claim_review를 만든다.
5. 그 output을 Supervisor에게 돌려준다.
```

---

## 1. 현재 코드베이스 기준

현재 실제 `etl/fault_cases/src/` 아래에는 아래 source 계층만 있다.

```text
etl/fault_cases/src/
  fault_standard/
  review_case/
  traffic_precedents/
```

따라서 아래 Agent 계층은 신규 생성할 구조다.

```text
etl/fault_cases/src/agents/text_ml_case_search/
```

이 위치로 새로 만드는 이유는 다음과 같다.

```text
1. text_ml_case_search는 review_case 전용 코드가 아니다.
2. 향후 판례, 인정기준, OCR, Vision, 보험사 주장까지 함께 다루는 업무 Agent다.
3. review_case / traffic_precedents는 데이터 적재, 전처리, 색인, 검색 실험 계층이다.
4. agents/text_ml_case_search는 Supervisor가 호출하는 Agent 계층이다.
```

---

## 2. Agent의 정체성

`text_ml_case_search`는 RAG 챗봇이 아니다.

```text
RAG 챗봇:
  검색한 뒤 사용자에게 최종 답변까지 생성

text_ml_case_search Agent:
  검색한 뒤 Supervisor가 사용할 구조화 결과 생성
```

Agent의 핵심 목적은 다음이다.

```text
사고 설명, Vision 결과, OCR 결과, 보험사 주장 정보를 받아
유사 심의사례 근거를 먼저 찾고,
Supervisor가 최종 답변을 만들 수 있도록
정규화된 사고 설명, 쟁점, evidence, similar_cases,
ratio_range_label, insurer_claim_review를 반환한다.
```

## 3. V1 범위와 고도화 범위

```text
V1:
  review_case BM25+Nori 기반 Agent skeleton + RAG 연결

V1.1:
  review_case BM25 후보 + local reranker

V1.5:
  traffic_precedent 또는 fault_ratio_precedent adapter 1차 추가 검토

V2:
  review_case + traffic_precedent + fault_ratio_precedent 통합 검색
```

중요한 점은 다음이다.

```text
Input schema는 여전히 하나다.
V1에서 내부적으로 review_case 검색기부터 연결하는 것일 뿐,
사용자/Supervisor에게 심의사례 전용 input을 요구하지 않는다.
source_scope 같은 입력 필드는 만들지 않는다.
```

흐름도 문서 기준으로는 RAG 검색 대상이 아래처럼 넓게 표현되어 있다.

```text
검색 대상:
  과실비율 인정기준
  심의사례
  판례
```

하지만 이것은 최종 목표 구조다. 실제 구현은 한 번에 세 source를 모두 붙이지 않고 단계적으로 진행한다.

```text
V1 실제 구현:
  심의사례 review_case만 연결

V1.5:
  판례 adapter 일부 연결 검토

V2:
  심의사례 + 판례 + 인정기준 통합 RAG
```

이렇게 나누는 이유는 source별 원천 필드가 다르기 때문이다.

```text
review_case:
  review_no
  reference_chart_key
  decision_fault_ratio
  claimant_final_ratio
  respondent_final_ratio
  signal_condition
  road_feature

precedent:
  case_number
  court_name
  judgment_date
  case_name
  holding_summary
  law_reference
```

최종 output schema는 동일하게 맞출 수 있지만, source별 hit를 evidence로 변환하는 mapper는 다르다.
따라서 V1에서는 review_case mapper부터 안정화하고, V2에서 precedent mapper를 추가한다.

예상 결과:

```text
1. V1에서는 source_type이 대부분 review_case로 나온다.
2. Supervisor output schema는 V2까지 고려해 precedent도 수용 가능하게 유지한다.
3. V2에서 판례를 붙일 때 input schema를 바꾸지 않고 retriever/mapper만 확장한다.
```

## 4. V1에서 하지 않는 것 / 하는 것

### 하지 않는 것

```text
1. 최종 사용자 답변 생성
2. 확정 과실비율 판단
3. 보험사 주장 반박 단정
4. 법률 자문
5. 과태료 판단
6. 판례 통합 검색
7. source_scope input 추가
8. local reranker 운영 반영
```

### 하는 것

```text
1. Supervisor agent_input 수신
2. 필수 입력 검증
3. Context 통합
4. 사고 설명 정규화
5. issue_tags 생성
6. full_optional_context 검색문 생성
7. review_case BM25+Nori 검색
8. review_case hit → evidence 변환
9. evidence 검증
10. similar_cases 생성
11. ratio_range_label 생성
12. insurer_claim_review 생성
13. recommended_evidence / limitations / next_actions 생성
14. Supervisor 반환 output JSON 조립
```

## 7. 전체 흐름

```text
agent_input
↓
Input Validator
↓
Context Builder
↓
Accident Normalizer
↓
Issue Tagger
↓
RAG Pipeline
  - full_optional_context 생성
  - review_case BM25+Nori 검색
  - review_case hit → evidence mapping
  - evidence validation
↓
Similar Case Builder
↓
Ratio Range Builder
↓
Insurer Claim Review Builder
↓
Recommended Evidence Builder
↓
Output Builder
↓
Supervisor 반환
```

흐름도 문서의 케이스 분기는 Agent V1에서도 그대로 유지한다.
다만 V1에서는 RAG source가 review_case로 제한된다.

```text
케이스 0:
  query_text가 없거나 분석 가능한 사고 설명이 부족함
  → status: failed 또는 partial
  → evidence: []
  → missing_fields 또는 limitations 반환

케이스 1:
  보험사 주장 없음 + 유효 RAG 근거 없음
  → similar_cases: []
  → ratio_range_label: ""
  → insurer_claim_review: null
  → recommended_evidence와 limitations 중심 반환

케이스 2:
  보험사 주장 없음 + 유효 RAG 근거 있음
  → evidence 생성
  → similar_cases 생성
  → ratio_range_label 생성 가능
  → insurer_claim_review: null

케이스 3:
  보험사 주장 있음 + 유효 RAG 근거 없음
  → 보험사 주장 쟁점 후보만 정리
  → RAG 근거 부족으로 비교 분석은 제한
  → insurer_claim_review는 null 또는 limitations 포함 구조

케이스 4:
  보험사 주장 있음 + 유효 RAG 근거 있음
  → evidence 생성
  → similar_cases 생성
  → ratio_range_label 생성
  → insurer_claim_review 생성
```

이 분기를 명시하는 이유는 검색 결과가 항상 존재한다고 가정하면 Agent가 쉽게 깨지기 때문이다.
V1 Agent는 검색 성공뿐 아니라 무결과/입력 부족 상황도 Supervisor에게 안전한 JSON으로 반환해야 한다.

## 9-1. Evidence Display Formatter 구현 계획

### 왜 추가하는가

9단계 전후로 실제 BM25+Nori RAG evidence가 Agent output에 들어오면,
`evidence`에는 원천 chunk와 metadata가 그대로 들어간다.

이 원천 evidence는 추적과 검증에는 필요하지만,
Supervisor 또는 UI가 사용자에게 보여줄 문장 재료로 쓰기에는 거칠다.

특히 다음 문제가 있다.

```text
1. chunk_text가 길다.
2. Elasticsearch highlight에는 <em> 태그가 포함될 수 있다.
3. BM25 score는 내부 검색 점수라 사용자에게 직접 보여주면 안 된다.
4. 원천 evidence와 사용자 표시용 근거는 역할이 다르다.
```

그래서 `evidence`는 보존하고,
별도로 `display_evidence`를 만든다.

### 구현 파일

```text
etl/fault_cases/src/agents/text_ml_case_search/builders/evidence_display_builder.py
```

### Agent 연결 위치

```text
agent.py
  -> RAG evidence 생성
  -> similar_cases 생성
  -> ratio_range_label 생성
  -> display_evidence 생성
  -> output_builder로 전달
```

`display_evidence`는 최종 사용자 답변 자체가 아니다.
Supervisor가 최종 답변을 만들 때 참고하기 쉬운 근거 표시용 구조다.

### output_builder 변경

`structured_result`에 아래 필드를 추가한다.

```json
{
  "display_evidence": []
}
```

예상 예시는 다음과 같다.

```json
{
  "source_type": "review_case",
  "title": "신호 없는 교차로 사고 심의사례",
  "source_reference": "review_case_db:123#chunk-1",
  "reference_chart_key": "249",
  "ratio_label": "청구인 70 : 피청구인 30",
  "summary": "신호 없는 교차로에서 직진 차량과 우측 진입 차량의 진입 순서와 충돌 위치를 중심으로 판단한 사례입니다.",
  "matched_snippets": ["신호 없는 교차로", "우측 진입 차량"],
  "display_warnings": []
}
```

### 처리 규칙

```text
1. source_reference는 반드시 유지한다.
2. highlight의 <em> 태그는 제거한다.
3. chunk_text는 너무 길면 preview 길이로 줄인다.
4. 비율 metadata가 있으면 ratio_label로 정리한다.
5. BM25 score/index/raw highlight는 표시용 필드에 직접 넣지 않는다.
6. 텍스트 인코딩 깨짐이 의심되면 display_warnings에 표시한다.
```

### 테스트 계획

```text
test_evidence_display_builder.py
  - highlight <em> 태그 제거
  - source_reference 유지
  - 긴 chunk_text preview 처리
  - ratio_label 생성
  - display_warnings 생성 조건 확인
```

예상 결과:

```text
Agent output:
  structured_result.display_evidence 존재
  evidence 원본은 그대로 유지
  display_evidence에는 사용자/Supervisor 표시용 요약만 들어감
```

## 10. Config 설계

```python
import os

BM25_TOP_K = 5
BM25_CANDIDATE_K = 10

REVIEW_CASE_INDEX = os.getenv(
    "REVIEW_CASE_ES_BM25_INDEX",
    "review_case_chunks_bm25_nori_v1",
)

EVIDENCE_INDEX_NAMES = [
    REVIEW_CASE_INDEX,
]

BM25_SEARCH_FIELDS = [
    "search_text^4",
    "chunk_text^2",
    "case_title^2",
    "header_road_context^1.5",
    "search_text_standard",
    "chunk_text_standard",
]

MIN_CHUNK_TEXT_LEN = 50

ENABLE_PRECEDENT_RETRIEVER = False
ENABLE_METADATA_CONTEXT_ENRICHER = False
ENABLE_RERANKER = False
```

이 설정은 서버 내부 설정이다. Supervisor input schema에 검색 대상 선택 필드를 추가하지 않는다.

`REVIEW_CASE_INDEX`는 PostgreSQL 테이블명이 아니라 Elasticsearch 검색 색인명이다.
DB에 원본 데이터가 적재되어 있어도 BM25+Nori 검색은 Elasticsearch index를 대상으로 수행한다.

```text
PostgreSQL:
  review_case_chunks
  → 원본 chunk 저장

Elasticsearch:
  review_case_chunks_bm25_nori_v1
  → BM25+Nori 검색용 색인
```

예상 결과:

```text
1. V1 기본값은 review_case_chunks_bm25_nori_v1이다.
2. index 버전이 바뀌면 .env의 REVIEW_CASE_ES_BM25_INDEX만 수정한다.
3. Supervisor input에는 source_scope 또는 index_name을 넣지 않는다.
```

### 11.3 Normalizer / Issue Tagger

V1은 규칙 기반으로 시작한다. 이유는 검색 문제와 정규화 문제를 분리하기 위해서다. LLM 기반 보정은 V1.1 이후 검토한다.

### 11.4 RAG Pipeline

```text
full_optional_context 생성
→ review_case BM25+Nori 검색
→ review_case hit evidence 변환
→ evidence validation
→ 필요 시 metadata_context_enricher
```

BM25+Nori 검색 구현은 기존 실험 코드에서 검증한 조건을 Agent 운영 코드로 이관한다.
이때 기존 검색 조건 중 아래 설정도 함께 가져온다.

```text
operator="or":
  검색어 토큰 중 일부가 맞아도 후보로 가져오는 설정.
  full_optional_context가 길어져도 검색 후보가 과하게 사라지는 것을 막는다.

highlight:
  search_text/chunk_text에서 어떤 부분이 매칭됐는지 확인하는 설정.
  사용자에게 직접 노출하기보다는 디버깅, 근거 확인, 추후 matched_facts 보조에 사용한다.
```

예상 결과:

```text
1. 기존 BM25 실험과 Agent BM25 검색 조건이 일치한다.
2. 검색 결과가 없을 가능성을 낮춘다.
3. highlight를 통해 왜 검색됐는지 점검할 수 있다.
```

### 11.5 Evidence Mapper

실제 review_case hit 필드 기준으로 매핑한다.

```text
case_title → evidence.title
review_case_id / review_no / chunk_id → source_reference
reference_chart_key → metadata.reference_chart_key
decision_fault_ratio → metadata.decision_fault_ratio
claimant_final_ratio → metadata.claimant_final_ratio
respondent_final_ratio → metadata.respondent_final_ratio
signal_condition / road_feature / standard_* → metadata.standard_context
chunk_text → evidence.chunk_text
```

`issue_tags`는 ES hit에서 받지 않고 Agent issue_tagger가 만든 값을 기준으로 쓴다.

### 11.6 Ratio Range Builder

```text
1. decision_fault_ratio 우선
2. claimant_final_ratio / respondent_final_ratio 확인
3. 없으면 chunk_text regex fallback
4. 그래도 없으면 ""
```

중요:

```text
계산하지 않는다.
확정하지 않는다.
문서에 있는 비율 정보를 참고 라벨로만 정리한다.
```

## 12. `agent.py` 실행 흐름

```python
def run_text_ml_case_search(agent_input: dict, es) -> dict:
    validation = validate_input(agent_input)

    if not validation.ok:
        return build_failed_output(validation)

    context = build_context(agent_input)
    normalized = normalize_accident(context)
    issue_tags = extract_issue_tags(context, normalized)

    rag_result = run_rag_pipeline(
        es=es,
        agent_input=agent_input,
        issue_tags=issue_tags,
    )

    evidence = rag_result["evidence"]
    similar_cases = build_similar_cases(evidence)
    ratio_range_label = build_ratio_range_label(evidence)

    insurer_claim_review = build_insurer_claim_review(
        insurer_claim=context.get("insurer_claim"),
        issue_tags=issue_tags,
        evidence=evidence,
        ratio_range_label=ratio_range_label,
    )

    recommended_evidence = build_recommended_evidence(
        context=context,
        issue_tags=issue_tags,
        evidence=evidence,
    )

    limitations = build_limitations(evidence=evidence, context=context)
    next_actions = build_next_actions(recommended_evidence)

    return build_output(
        status="success" if evidence else "partial",
        normalized=normalized,
        issue_tags=issue_tags,
        evidence_tags=[item["title"] for item in recommended_evidence],
        recommended_evidence=recommended_evidence,
        insurer_claim_review=insurer_claim_review,
        similar_cases=similar_cases,
        ratio_range_label=ratio_range_label,
        evidence=evidence,
        next_actions=next_actions,
        limitations=limitations,
        missing_fields=[],
    )
```

## 테스트 코드 운영 기준과 존재 이유

### 테스트 폴더의 역할

`etl/fault_cases/src/agents/text_ml_case_search/tests/`는 Agent 실행용 폴더가 아니라 구현 검증용 폴더다.

서비스 실행은 `agent.py`와 `rag/`, `input/`, `builders/` 아래 운영 코드가 담당하고, `tests/`는 그 운영 코드가 계약을 지키는지 확인한다.

### 왜 필요한가

`text_ml_case_search` Agent는 다음처럼 여러 단계가 연결된다.

```text
input validation
-> context_builder
-> normalizer / issue_tagger
-> search_text_builder
-> BM25+Nori retriever
-> evidence_mapper
-> evidence_validator
-> output_builder
```

각 단계는 따로 보면 작지만, 중간 규칙 하나가 바뀌면 최종 Agent output이 달라진다.

예:

```text
source_ref alias 처리 누락
-> source_reference 누락
-> evidence_validator에서 근거 제거
-> Agent output evidence 감소
```

또는:

```text
BM25 field boost 변경
-> 검색 순위 변경
-> similar_cases/evidence 변화
-> 보험사 주장 비교 결과 변화
```

테스트는 이런 변화를 의도한 변경인지, 실수인지 구분하기 위해 필요하다.

### test_es_client.py의 목적

`test_es_client.py`는 실제 Elasticsearch 접속 테스트가 아니다.

목적은 Elasticsearch client 생성 규칙을 검증하는 것이다.

검증 항목:

```text
1. username/password가 있으면 basic_auth를 만든다.
2. username이 없으면 인증 없이 client kwargs를 만든다.
3. username은 있는데 password가 없으면 에러를 낸다.
```

테스트 안에 들어가는 `test-password`류 문자열은 실제 비밀번호가 아니라 더미 값이다.

이 더미 값은 다음 계약을 확인하기 위한 입력이다.

```text
입력 password가 주어졌을 때 basic_auth에 그대로 전달되는가?
```

### 실제 비밀번호 처리 기준

실제 비밀번호는 `.py` 파일에 넣지 않는다.

반드시 `.env`에 둔다.

```env
TEXT_ML_CASE_SEARCH_ELASTICSEARCH_PASSWORD=...
```

또는 기존 공통 값을 사용한다.

```env
ELASTIC_PASSWORD=...
```

password가 없는데 username이 있는 경우는 에러로 처리한다.

이유:

```text
개발용 기본 비밀번호 fallback이 코드에 남아 있으면 운영 전환 시 위험하다.
따라서 접속 실패를 조용히 넘기지 않고 설정 누락을 즉시 드러낸다.
```

### 유지 기준

테스트 파일은 아래 기준으로 유지한다.

```text
1. 실제 외부 서버 접속은 하지 않는다.
2. 비밀번호/토큰/키 같은 실값은 넣지 않는다.
3. fake client 또는 dummy 값으로 정책만 검증한다.
4. 운영 코드의 검색 정책, mapping 정책, validation 정책이 바뀌면 테스트도 함께 갱신한다.
```
