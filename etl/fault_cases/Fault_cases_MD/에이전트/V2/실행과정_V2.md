# text_ml_case_search V2 실행과정

작성 기준일: 2026-07-05

---

## 0. V2 진행 목적

V1 `text_ml_case_search` Agent는 `review_case` 심의사례만 BM25+Nori로 검색해서 Supervisor가 사용할 수 있는 `evidence`, `similar_cases`, `display_evidence`, `ratio_range_label`을 반환했다.

V2의 목적은 V1 구조를 최대한 유지하면서 `fault_ratio_precedent` 과실비율 판례를 추가 source로 붙이는 것이다.

최종 목표:

```text
사용자/슈퍼바이저 입력
→ text_ml_case_search Agent
→ review_case + fault_ratio_precedent 검색
→ 공통 evidence schema로 변환
→ source_summary 포함
→ Supervisor가 바로 사용할 수 있는 output 반환
```

이번 V2에서는 `traffic_precedent`와 `standard/인정기준`은 active evidence에 넣지 않는다.

## 0-1. V2 전체 구현 로드맵

두 계획 문서 기준으로 V2의 최종 목적은 아래와 같다.

```text
사용자/슈퍼바이저 입력
→ text_ml_case_search Agent
→ review_case + fault_ratio_precedent RAG 검색
→ evidence / similar_cases / ratio_range_label / display_evidence 정리
→ Supervisor가 바로 받을 수 있는 output schema 반환
```

이 목적에 도달하기 위한 전체 단계는 아래 순서로 진행한다.


```text

source_reference 기준 중복 제거
BM25 raw score를 source 간 직접 비교하지 않음
```

5+5로 변경한 이유:

```text
처음에는 review_case 4개 + fault_ratio_precedent 4개, final_top_k 8로 잡았다.
하지만 V2의 목적은 심의사례와 판례를 함께 output에 노출하는 것이다.
4+4는 가볍지만 source별 근거 다양성을 확인하기에는 조금 좁을 수 있다.

review_case는 심의사례 기반 과실비율 근거에 강하고,
fault_ratio_precedent는 판례상 과실상계/책임 제한 판단 근거에 강하다.
두 source의 역할이 다르므로 초기 V2에서는 동일하게 5개씩 보장한다.

5+5 = 총 10개는 Supervisor가 후처리할 수 있는 범위 안에서
두 source의 근거 다양성을 확인하기 위한 초기 균형값이다.
V2 active 10개 실행 결과를 보고 6+4, 4+6, 3+3 등으로 다시 조정할 수 있다.
```

왜 진행했는가:

```text
review_case와 fault_ratio_precedent는 서로 다른 Elasticsearch index에서 검색된다.
서로 다른 index의 BM25 점수는 corpus, 문서 길이, field 구성, analyzer 결과가 달라 직접 비교하기 어렵다.
따라서 점수 하나로 전체 정렬하지 않고 source별 quota를 적용해 안정적으로 병합한다.
```

근거:

```text
1. RAG_V2 계획에서 merge_strategy는 source_quota로 확정했다.
2. V2 active source는 review_case + fault_ratio_precedent 두 개다.
3. Supervisor는 심의사례 근거와 판례 근거를 모두 받아야 하므로 한 source가 다른 source를 완전히 밀어내면 안 된다.
4. source_reference가 같은 evidence는 중복 근거로 볼 수 있으므로 제거한다.
```

## 14단계. Supervisor 계약 V2 정리

추가 파일:

진행한 수정:

```text
output_builder.py:
  build_output에 contract_version 인자를 추가
  build_failed_output에도 contract_version 인자를 추가
  기본값은 기존 V1 계약을 유지

agent.py:
  es_client가 주입되어 실제 V2 RAG 경로를 타는 경우 contract_version을 text_ml_case_search_v2로 반환하도록 수정
  mock/no-es 경로는 기존 V1 성격을 유지

text_ml_case_search_Supervisor_입출력_계약_V2.md:
  V2 목적과 active source 범위 정리
  review_case + fault_ratio_precedent evidence 계약 정리
  source_summary 계약 정리
  display_evidence / similar_cases / ratio_range_label 사용 기준 정리
  5+5 source quota 병합 이유 정리
  Supervisor 사용 우선순위와 출력 문구 가이드 정리
```

왜 진행했는가:

```text
12~13단계에서 실제 active 10개 실행 결과는 V2 구조로 정상 동작했다.

특히 V2는 V1과 달리 review_case와 fault_ratio_precedent가 함께 반환된다.
따라서 source_type, source_summary, display_evidence, evidence.metadata를 어떻게 해석할지 명확히 해야 한다.
```

근거:

```text
1. active 10개 실행에서 모든 run이 success였다.
2. 모든 run에서 review_case 5개 + fault_ratio_precedent 5개가 반환됐다.
3. total_evidence_count = 100, total_review_case_evidence_count = 50, total_fault_ratio_precedent_evidence_count = 50으로 확인됐다.
4. Supervisor는 심의사례와 판례를 같은 방식으로 문장화하면 안 되고, source_type별로 표현을 구분해야 한다.
```

계약 V2 핵심:

```text
contract_version = text_ml_case_search_v2
active_sources = ["review_case", "fault_ratio_precedent"]
standby_sources = ["traffic_precedent"]
excluded_sources = ["standard"]
merge_strategy = source_quota
review_case quota = 5
fault_ratio_precedent quota = 5
final_top_k = 10
```
