# `text_ml_case_search` Agent Schema Contract

## 1. 목적

`text_ml_case_search` Agent는 사고 설명, Vision 분석 결과, OCR 결과, 보험사 주장 정보를 바탕으로 유사 과실비율 사례와 참고 근거를 검색하고, Supervisor가 최종 사용자 응답을 만들 수 있도록 구조화된 분석 결과를 반환한다.

본 문서는 `text_ml_case_search`의 input/output schema와 RAG 근거 metadata 계약을 정리한다.

---

## 2. Agent 책임 범위

### 담당

- 사고 설명 정규화
- 사고 유형 후보 도출
- 주요 쟁점 태그 추출
- 유사 사례/인정기준/RAG 근거 검색
- 참고 과실비율 범위 정리
- 보험사 주장 비교 검토용 정보 정리
- 추가 확인 자료 추천

### 비담당

- 최종 과실비율 확정
- 법률 판단 또는 법률 자문
- 보험사 주장 반박 단정
- 사용자 최종 자연어 답변 생성

> 최종 사용자 응답은 개별 Agent가 아니라 Supervisor가 통합 생성한다.

---

## 6. 필드명 통일 규칙

출처 참조 필드는 `source_reference`로 통일한다.

| 대상 | 최종 필드명 |
|---|---|
| `agent_input.vision_evidence[].source_ref` | `agent_input.vision_evidence[].source_reference` |
| `agent_input.insurer_claim.source_ref` | `agent_input.insurer_claim.source_reference` |
| `structured_result.similar_cases[].source_reference` | 유지 |
| `evidence[].source_reference` | 유지 |

> 기존 `source_ref`가 들어올 가능성이 있으므로 1차 구현에서는 deprecated alias로만 허용하고, 최종 output에는 `source_ref`를 반환하지 않는다.

## 7. 노출 기준

| 필드 | 처리 기준 |
|---|---|
| `evidence_tags` | 내부 분석용. 사용자에게 직접 노출하지 않음 |
| `recommended_evidence` | 사용자 화면용 문구로 가공해 노출 |
| `insurer_claim_review` | 보험사 주장 요약/쟁점/한계 중심으로 노출 |
| `reliability_score` | raw score 직접 노출 지양 |
| `evidence[].confidence` | 내부 ranking/guardrail용 |
| `law` 타입 evidence | 법률 Agent 참조 근거로만 사용 |

## 8. OpenAPI 반영 기준

- `insurer_claim_review`는 `nullable: true`
- `similar_cases`는 빈 배열 허용
- `evidence`는 빈 배열 허용
- `missing_fields`는 빈 배열 허용
- `next_actions`는 빈 배열 허용
- `ratio_range_label`은 빈 문자열 허용
- 조건부 필수 필드는 description에 조건 명시
- 사용자 노출용 문구와 내부 분석용 태그 분리
- 출처 참조 필드는 `source_reference` 사용
- `source_ref`는 표준 필드로 사용하지 않음

---

## 9. 최종 정리

`text_ml_case_search`는 과실비율을 확정하지 않고, Supervisor가 사용할 수 있는 사고 유형, 주요 쟁점, 유사 사례, 참고 근거, 추가 확인 자료를 구조화해서 반환한다.

최종 사용자 응답은 Supervisor가 다른 Agent 결과와 함께 통합 생성한다.

## 10. 2026-07-04 스키마 정렬 결정 사항

### 10.1 `vision_evidence` 필수 여부

`vision_evidence`는 필수가 아니다.

이유:

```text
text_ml_case_search는 사용자 텍스트만으로도 호출될 수 있다.
Vision Agent 결과는 있으면 검색 품질을 높이는 보조 입력이지만, 없다고 Agent가 실패하면 안 된다.
```

처리 기준:

```text
입력 없음/null      -> []
배열 입력          -> 배열 유지
배열 내부 source_ref -> source_reference로 변환
```

### 10.2 `evidence_tags`와 `recommended_evidence` 분리 이유

두 필드는 서로 겹칠 수 있지만 역할이 다르다.

| 필드 | 역할 | 사용자 노출 |
|---|---|---|
| `evidence_tags` | 내부 분석용 짧은 태그 | 원칙적으로 직접 노출하지 않음 |
| `recommended_evidence` | 사용자/Supervisor에게 전달할 증거자료 요청 문구 | 노출 가능 |

예시:

```json
{
  "evidence_tags": ["lane_change_video", "rear_vehicle_distance"],
  "recommended_evidence": [
    {
      "type": "lane_change_video",
      "title": "차로 변경 시작 시점 영상",
      "description": "방향지시등 작동 여부, 차로 변경 시작 시점, 후행 차량과의 거리가 함께 보이는 영상이 필요합니다.",
      "related_issue": "진로변경 주의의무",
      "priority": "high",
      "based_on": ["issue_tags", "vision_evidence"]
    }
  ]
}
```

정리:

```text
evidence_tags와 recommended_evidence[].type은 값이 겹쳐도 된다.
다만 evidence_tags는 분류/필터/후속 로직용이고,
recommended_evidence는 사람이 읽는 요청 항목이다.
```

### 10.3 `recommended_evidence` 최종 구조

`recommended_evidence`는 다음 구조를 기준으로 한다.

```json
{
  "type": "lane_change_video",
  "title": "차로 변경 시작 시점 영상",
  "description": "방향지시등 작동 여부, 차로 변경 시작 시점, 후행 차량과의 거리가 함께 보이는 영상이 필요합니다.",
  "related_issue": "진로변경 주의의무",
  "priority": "high",
  "based_on": ["issue_tags", "vision_evidence"]
}
```

필드 의미:

| 필드 | 의미 |
|---|---|
| `type` | 내부 증거자료 유형 코드 |
| `title` | Supervisor 또는 UI가 제목처럼 쓸 수 있는 짧은 이름 |
| `description` | 사용자에게 보여줄 수 있는 설명 |
| `related_issue` | 어떤 쟁점 때문에 필요한 자료인지 |
| `priority` | `high`, `medium`, `low` |
| `based_on` | 어떤 입력/분석 결과에서 추천됐는지 |

### 10.4 `source_ref` alias 처리

`source_ref`는 과거 또는 외부 모듈에서 들어올 수 있는 옛 필드명이다.

정책:

```text
입력에서는 source_ref를 허용한다.
내부 context 생성 시 source_reference로 변환한다.
최종 output에는 source_ref를 반환하지 않는다.
```

여기서 `deprecated alias`의 의미:

```text
deprecated = 앞으로 표준으로 쓰지 않을 예정인 낡은 이름
alias = 같은 값을 가리키는 다른 이름
```

즉 `source_ref`는 당장 입력 호환을 위해 받아주지만, 표준 필드는 `source_reference`다.

### 10.5 evidence metadata schema

최상위 output schema를 크게 바꾸지 않고, `evidence[].metadata` 안에 공통 필드와 source별 세부 필드를 둔다.

공통 metadata:

```json
{
  "case_id": "review_case_000123",
  "chunk_id": "review_case_000123:case_overview",
  "score": 14.2,
  "score_type": "bm25_nori",
  "matched_facts": ["신호 없는 교차로", "양 차량 교차로 진입"],
  "different_facts": ["진입 순서가 현재 입력만으로 불명확함"]
}
```

`review_case` 전용 metadata:

```json
{
  "review_no": "2017-032889",
  "reference_chart_key": "249",
  "case_title": "역주행사고",
  "decision_fault_ratio": "A 0 : B 100",
  "standard_context": {
    "signal_condition": "신호등 없음",
    "road_feature": "중앙선 설치된 도로",
    "standard_a_behavior": "직진",
    "standard_b_behavior": "중앙선 침범 역주행"
  }
}
```

예상 효과:

```text
Supervisor는 evidence 본문만 보지 않고도
어떤 사례인지, 어떤 기준표와 연결되는지, 어떤 쟁점이 맞고 다른지 빠르게 판단할 수 있다.
```
