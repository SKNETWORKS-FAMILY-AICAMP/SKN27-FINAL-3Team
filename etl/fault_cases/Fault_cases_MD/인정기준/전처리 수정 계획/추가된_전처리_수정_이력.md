# 추가된 전처리 수정 이력

이 문서는 기존 `README_기준정보_전처리_계획_및_수정이력.md`에 덧붙이지 않고, 이후 전처리 보정 과정만 별도로 정리한 추가 이력 문서이다.

정리 대상은 `etl/fault_cases/src/fault_standard/preprocessing` 아래의 기준정보 전처리 코드와, 그 결과로 생성되는 `etl/fault_cases/artifacts/fault_standard_output/preprocessed` 산출물이다.

## 수정 원칙

이번 수정의 가장 중요한 원칙은 특정 기준번호를 코드에 직접 박지 않는 것이었다.

예를 들어 아래와 같은 방식은 금지했다.

```python
if rule_id == "official_2023_차48-1":
    ...
```

대신 원문 구조에서 반복적으로 나타나는 일반 규칙을 사용했다.

- rule title, party raw_text, base_fault 영역, adjustment 영역을 구분한다.
- party 원문이 있으면 rule title보다 party 원문을 우선한다.
- `A100/B0`, `A70/B30`처럼 A/B가 모두 있는 값은 pair ratio로 본다.
- `+10`, `-10`, `10%까지 가산` 같은 값은 기본과실 variant가 아니라 수정요소로 본다.
- `__SHARED_EXPLANATION__`은 공유 해설 marker일 뿐 수정요소가 아니므로 adjustment table에서만 제외한다.
- diagram/image 전처리는 이번 범위에서 제외한다.

## 전체 수정 대상

주요 수정 대상 폴더는 다음과 같다.

```text
etl/fault_cases/src/fault_standard/preprocessing/
  nontypical/
  pm_auto/
  roundabout/
  official_2023/
```

가장 많은 수정이 들어간 곳은 `official_2023`이다.

```text
official_2023/
  rule_splitter.py
  extractors.py
  classifiers_clean.py
  builder.py
```

## 1. 2020 비정형 기준 전처리 보정

대상 산출물:

```text
2020_nontypical_accident_rulebook/
```

### 발견된 문제

초기 점검에서 다음 문제가 있었다.

- summary table의 멀티라인 row 일부가 다음 rule 제목과 섞였다.
- `road_context`, `accident_group`이 일부 rule에서 잘못 분류됐다.
- review case의 과실비율 파싱이 일부 누락됐다.
- movement vocabulary가 부족해 일부 party movement가 비어 있었다.
- validator가 너무 관대해 실제 문제를 `valid`로 통과시키는 문제가 있었다.

### 수정 방향

비정형 기준은 rule 수가 23개로 작지만, 특정 No.를 하드코딩하지 않고 다음 기준으로 수정했다.

- summary table은 번호 단위 row boundary를 우선한다.
- title 비교는 완전 일치만 보지 않고 정규화된 제목 기준으로 mismatch를 판단한다.
- road context는 수정요소 조건보다 rule title과 사고상황 block을 우선한다.
- review case 비율은 `청구차량 60%, 피청구차량 40%`처럼 `과실` 단어가 없는 패턴도 잡는다.
- movement는 `끼어들기`, `주차진행`, `횡단`, `우회전 대기`, `정차 후 출발` 같은 표현을 보강한다.

### 결과

수정 후 점검 기준으로 다음 항목이 안정화됐다.

```text
rules: 23개
parties: 46개
base_faults: 23개
adjustment_factors: 205개
movement 누락: 0건
adjustment target 누락: 0건
summary mismatch: 0건
```

최종 판단은 기본과실 조회, 수정요소 계산, Neo4j 적재용 핵심 데이터로 사용 가능한 상태에 가까운 것으로 정리했다.

## 2. 2021 PM 대 자동차 기준 전처리 보정

대상 산출물:

```text
2021_pm_vs_auto_nontypical_rulebook/
```

### 발견된 문제

초기 PM 전처리 결과에는 다음 문제가 있었다.

- adjustment factor의 `target_party_key`, `target_party_type`이 많이 비어 있었다.
- PM 기준에서 기본 사고상황과 수정요소 조건이 `road_context`에 섞였다.
- 공유 해설/법규를 사용하는 도표 묶음에서 앞 도표의 chunk/law_ref가 비어 있었다.
- 도표35, 도표37, 도표38처럼 다중 기본과실 시나리오가 있는 rule이 단일 base_fault로만 저장됐다.
- 도표33 제목이 도표34 제목과 섞였다.
- movement vocabulary가 부족했다.

### 수정 방향

PM 기준은 A가 PM, B가 자동차라는 방향성이 핵심이므로 이를 유지하면서 구조를 분리했다.

- A/B 방향은 rule 전체에서 `A=PM`, `B=자동차`로 유지한다.
- 수정요소 조건은 `adjustment_condition_contexts`로 분리한다.
- `road_contexts`는 기본 사고상황에서 나온 도로 조건만 담도록 한다.
- 공유 해설/법규는 `shared_rule_groups`, `shared_rule_group_*` 테이블로 분리한다.
- 도표35/37/38은 `rule_scenarios`로 분리하고, base_fault만 읽는 계산 로직이 실수하지 않도록 `scenario_required` 성격의 메타를 둔다.
- movement는 `통행`, `주차`, `정차`, `주행`, `후행`, `개문`, `문열림`, `피추돌` 등을 보강한다.

### 결과

수정 후 핵심 구조는 다음과 같이 안정화됐다.

```text
rules: 38개
parties: 76개
base_faults: 38개
adjustment_factors: 282개
rule_scenarios: 7개
shared_rule_groups: 5개
A=PM: 38개
B=자동차: 38개
adjustment target 누락: 0건
```

이후 추가 점검에서 `road_context` 오염과 shared chunk null 문제가 지적됐고, 이를 보정했다.

최종 판단은 PM 기준 역시 기본과실 조회, 수정요소 계산, Neo4j 적재에 사용할 수 있는 수준으로 정리했다.

## 3. 2025 2차로형 회전교차로 기준 전처리 보정

대상 산출물:

```text
2025_two_lane_roundabout_rulebook/
```

### 발견된 문제

초기 회전교차로 전처리 결과에는 다음 문제가 있었다.

- 회전-9부터 회전-15까지 `lane_path`가 비어 있었다.
- `entry_direction`, `exit_direction`이 잘못 들어간 rule이 있었다.
- 줄바꿈과 제어문자 때문에 party action 문장이 잘려 `차로변경`, `진출` 등이 누락됐다.
- `conflict_direction`이 대부분 `3시 방향`으로 들어가는 하드코딩성 문제가 있었다.
- `role_in_rule`이 실제 역할과 맞지 않았다.
- reference case 비율 파싱에서 사고 시각을 과실비율처럼 잡았다.

### 수정 방향

회전교차로는 기본과실보다 차로 경로가 중요하므로 `LanePath`와 `LaneStep` 중심으로 보정했다.

- party action을 제어문자 제거 후 줄바꿈 병합하여 파싱한다.
- 방향, 차로, 진입, 회전, 차로변경, 진출을 다단계 step으로 분리한다.
- 차량당 하나의 `lane_step`만 만들지 않고, 원문에 명시된 단계만큼 생성한다.
- `conflict_direction`, `conflict_lane`은 확정값이 아닌 추론값이면 derived 성격으로 관리한다.
- reference case 비율 파서는 `10:02`, `15:00` 같은 시간 패턴을 제외한다.

### 결과

최종 검증에서 핵심 수정이 반영됐다.

```text
lane_steps: 74개
party 조합: 30개
2개 이상 step 생성 party: 27개 / 30개
회전-9~15 path 빈값 문제 해결
```

대표 예시는 다음과 같다.

```text
회전-13 A
진입 / 12시 방향 / 진입1차로
회전 / 회전1차로
진출 / 3시 방향 / 진출1차로

회전-15 A
진입 / 12시 방향 / 진입1차로
회전 / 회전1차로
차로변경 / 회전2차로
진출 / 3시 방향
```

일부 party의 lane step이 1개인 경우는 원문 action 자체가 짧거나 차로가 명시되지 않은 경우로 보아, 억지 보정하지 않았다.

## 4. 2023 공식 인정기준 전처리 대규모 보정

대상 산출물:

```text
2023_official_auto_accident_rulebook/
```

2023 공식 인정기준은 201개 rule을 갖고 있고, 전처리 구조가 가장 복잡했다. 여러 차례 검증과 수정을 거치며 아래 문제들을 순차적으로 해결했다.

### 4.1 adjustment target 누락 문제

#### 문제

초기에는 `adjustment_factors.jsonl`에서 target이 비어 있는 row가 많았다.

```text
target_party_key null
target_party_type null
target_parse_status = unresolved
```

대표 원인은 다음과 같았다.

- 표 row에 A/B가 직접 없는 경우 해설 문장의 `보행자의 과실`, `B차량의 과실`을 연결하지 못했다.
- PDF 줄바꿈 때문에 `B진로변경 / 신호불이행· / 지연 / +10`이 하나의 수정요소로 합쳐지지 않았다.
- `__SHARED_EXPLANATION__` marker 안의 `거9-7` 같은 문자열을 `-7` 수정요소처럼 오인했다.

#### 수정 코드

주요 수정 파일:

```text
official_2023/extractors.py
```

수정한 핵심 로직:

- `merge_adjustment_lines()`
- `parse_adjustment_line()`
- `infer_adjustment_target_info()`
- `extract_adjustment_target_context()`
- `infer_adjustment_target_from_explanation()`
- `is_shared_adjustment_marker()`

#### 수정 방식

- raw row에 A/B/보/차가 있으면 가장 먼저 target으로 사용한다.
- 줄바꿈된 수정요소는 delta가 나올 때까지 앞줄을 누적해 하나의 row로 병합한다.
- 해설 문장에서 `보행자의 과실`, `B차량의 과실`, `차의 과실` 등을 읽어 target을 보강한다.
- 그래도 모호한 row는 자동계산에서 제외하도록 `exclude_from_auto_calculation`을 둔다.
- `__SHARED_EXPLANATION__`이 들어간 row는 adjustment factor로 만들지 않는다.

#### 결과

최종적으로 다음 상태가 됐다.

```text
adjustment target null: 0건
target_parse_status unresolved: 0건
__SHARED_EXPLANATION__ 가짜 adjustment: 0건
```

### 4.2 shared explanation 제거 범위 문제

#### 문제

한 번은 `__SHARED_EXPLANATION__` row를 제거하는 과정에서 rule 본문과 공유 해설 연결까지 함께 잘리는 회귀가 발생했다.

그 결과 다음 문제가 생겼다.

```text
rules: 201개에서 199개로 감소
parties 감소
base_fault unknown 증가
거43-2, 거43-3 누락
rule_blocks, chunks, law_refs 감소
```

#### 수정 코드

주요 수정 파일:

```text
official_2023/rule_splitter.py
official_2023/extractors.py
```

#### 수정 방식

- rule 본문을 자르는 `truncate_spillover_text()`에서 next rule header처럼 보이는 줄을 만나면 자르는 공격적 절단 로직을 제거했다.
- shared marker 제거는 `adjustment_factors` 생성 단계에만 남겼다.
- rule_blocks, law_refs, reference_cases, chunks에는 shared 본문이 유지되도록 했다.

#### 결과

다시 아래 상태로 회복됐다.

```text
rules: 201개
parties: 402개
base_faults: 201개
거43-1 / 거43-2 / 거43-3 존재
```

### 4.3 차47-3 / 차48-1 boundary 문제

#### 문제

차47-3 뒤에 차48-1 내용이 붙는 문제가 있었다.

문제 상태:

```text
차47-3 party 4개
- A 정차 후 출발 버스차량
- B 추월 진로변경
- A 후행
- B 선행(적재물 낙하)

- rule_title = 기준

- base_fault = 0:100
```

#### 수정 코드

주요 수정 파일:

```text
official_2023/rule_splitter.py
```

#### 수정 방식

- `차48-1 기준`처럼 참조 문구를 rule header로 오인하지 않도록 `기준` 단독 제목을 noise로 처리했다.
- rule id를 하드코딩하지 않고, `기준`만 제목인 경우는 실제 rule title로 보지 않는 일반 규칙을 사용했다.

### 4.4 차43-7 variant 처리 문제

#### 문제

차43-7은 `(가)`, `(나)` 시나리오가 있는 rule이다. 원문 표에는 다음 값이 있다.

```text
(가) A100 / B0
(나) A70 / B30
```

그런데 초기 처리에서는 이를 `single_party_ratio`처럼 보거나 single_party_key가 비어 있는 상태로 저장했다.

#### 수정 코드

주요 수정 파일:

```text
official_2023/extractors.py
```

수정한 핵심 로직:

- `extract_variants()`
- `extract_tabular_pair_variants()`
- `extract_party_ratio_values_from_table_area()`
- `enrich_variant_party_info()`

#### 수정 방식

- 기본 과실비율 표 안에서 `(가)/(나)` label과 A/B 숫자가 모두 있으면 pair ratio variant로 추출한다.
- `A100`, `A70`, `B0`, `B30`처럼 열 형태로 분리된 값을 label 순서에 맞게 묶는다.
- A/B 합계가 100인 경우만 pair variant로 인정한다.
- pair variant에는 `single_party_key`를 채우지 않는다.

#### 결과

최종 상태:

```text
차43-7 variants: 2개
(가): A100 / B0
(나): A70 / B30
ratio_interpretation = pair_fault_ratio
```

### 4.5 차61-3 variant 오인 문제

#### 문제

차61-3은 기본과실이 하나인 일반 rule이다.

```text
A30 : B70
```

그런데 해설의 `A이륜차의 과실을 10% 높여서 ... 30:70` 문장 때문에 `(나) 10%` single variant로 잘못 들어갔다.

#### 수정 코드

주요 수정 파일:

```text
official_2023/extractors.py
```

수정한 핵심 로직:

- `extract_variants()`
- `extract_labeled_single_ratio_variants()`
- `extract_inline_variant_ratios()`
- `is_adjustment_ratio_context()`
- `has_base_fault_ratio_context()`
- `has_pair_ratio_context()`

#### 수정 방식

- `+10`, `가산`, `감산`, `조정`이 있는 문맥은 variant로 보지 않는다.
- 같은 문맥에 `30:70` 같은 pair ratio가 있으면 앞의 `10%`를 single variant로 보지 않는다.
- variant 후보가 1개뿐이면 RuleScenario로 만들지 않는다.

#### 결과

최종 상태:

```text
차61-3
base_fault_type = pair_ratio
normalized_ratio = 30:70
variants = 0개
auto_calculation_eligible = true
```

### 4.6 보22 variant 복구

#### 문제

보22는 도로폭 조건별로 보행자 기본과실이 달라지는 rule이다.

기대 구조:

```text
(가) 소로 횡단: 보행자 10%
(나) 동일폭 횡단: 보행자 20%
(다) 대로 횡단: 보행자 30%
```

초기에는 base_fault가 unknown이거나 variant가 제대로 복구되지 않았다.

#### 수정 코드

주요 수정 파일:

```text
official_2023/extractors.py
```

수정한 핵심 로직:

- `extract_width_based_pedestrian_variants()`
- `infer_variant_single_party_info()`
- `apply_base_fault_calculation_policy()`는 builder 쪽에서 variant 우선 계산 정책을 적용한다.

#### 수정 방식

- title이나 본문에 도로폭, 소로, 동일폭, 대로 문맥이 있고 보행자 기본과실이 함께 있을 때 variant를 만든다.
- 보행자 rule의 single party ratio는 `single_party_key = 보`, `single_party_type = pedestrian`으로 보강한다.
- base_fault는 `variant_ratio`, `calculation_source = variants`로 표시한다.

#### 결과

최종 상태:

```text
보22 variants: 3개
single_party_key = 보
single_party_type = pedestrian
calculation_source = variants
```

### 4.7 movement / party_type 보정

#### 문제

대표 문제:

```text
movement = 보행
```

#### 수정 코드

주요 수정 파일:

```text
official_2023/extractors.py
```

수정한 핵심 로직:

- `build_party_row()`
- `infer_party_type()`
- `infer_party_movement()`
- `infer_movement()`
- `is_movement_allowed_for_party_type()`
- `is_generic_vehicle_action()`

#### 수정 방식

- party action/raw_key를 rule title보다 우선한다.
- rule title은 action에서 movement를 못 찾았을 때만 fallback으로 사용한다.
- party_type이 vehicle/motorcycle/bicycle/pm이면 `보행`, `보도 보행`, `차도 보행` 같은 보행자 movement를 선택하지 않는다.

# 상세 보강 이력

이 섹션은 위 요약만으로는 부족했던 부분을 보강하기 위해 추가한다.

초기 문서는 각 기준서별 최종 상태를 중심으로 정리했지만, 실제 작업은 한 번에 끝난 것이 아니라 여러 번의 검증 보고서와 재수정 과정을 거쳤다. 특히 2023 공식 인정기준은 수정요소 target을 고치다가 rule boundary와 shared explanation 연결이 흔들리는 회귀가 발생했고, 이후 해당 회귀를 다시 복구하는 순서로 진행되었다.

따라서 아래에는 다음 흐름을 기준으로 다시 정리한다.

```text
1. 처음 발견된 문제
2. 문제가 발생한 코드 계층
3. 잘못 수정했을 때 생긴 회귀
4. 최종적으로 적용한 수정 기준
5. 산출물에서 기대한 결과
```

## 공통 전처리 기준 재정의

이번 전처리 수정의 핵심은 PDF에서 추출된 텍스트를 그대로 JSONL로 나누는 것이 아니라, Neo4j 적재와 과실비율 계산에서 사용할 수 있는 의미 단위로 재구성하는 것이었다.

처음에는 다음과 같은 문제가 반복됐다.

```text
PDF 텍스트는 정상적으로 수집됨
하지만 표, 해설, 법규, 사례, 다음 rule 제목이 한 block 안에 섞임
그 결과 party, base_fault, adjustment, law_ref, reference_case가 서로 오염됨
```

그래서 전처리 기준을 다음처럼 다시 잡았다.

```text
rules.jsonl
  - rule_id, rule_title, accident_group, accident_subgroup 같은 rule 메타

parties.jsonl
  - A/B/보/차 등 사고 당사자
  - party_type
  - movement
  - raw_text

base_faults.jsonl
  - 기본과실
  - pair_ratio 또는 variant_ratio

variants.jsonl 또는 rule_scenarios.jsonl
  - 하나의 rule 안에 (가)/(나)/(다) 같은 시나리오가 있는 경우

adjustment_factors.jsonl
  - 수정요소
  - target_party_key
  - target_party_type
  - delta
  - auto_calculation_eligible

rule_blocks.jsonl
  - 원문 근거 block
  - base_fault, adjustment_explanation, law, reference, usage_note 등

chunks.jsonl
  - 검색/RAG용 텍스트 조각
```

이 기준을 잡은 이유는 단순하다.

기본과실 계산은 `base_faults`와 `variants`를 봐야 하고, 수정요소 계산은 `adjustment_factors`를 봐야 한다. 반면 법규와 사례는 계산값이 아니라 근거 설명용이다. 이 경계를 지키지 않으면 Neo4j에서 관계를 만들 때 수정요소가 아닌 문장이 수정요소로 들어가거나, 다음 rule의 party가 이전 rule에 붙는 문제가 생긴다.

## 하드코딩 금지 기준

사용자가 여러 번 강조한 조건은 특정 기준번호를 코드에 직접 박지 않는 것이었다.

금지한 방식은 다음과 같다.

```python
if rule_id == "official_2023_차48-1":
    ...
```

이런 방식은 당장 한 row는 고칠 수 있지만, PDF 개정판이나 다른 기준서에 같은 구조가 나오면 다시 깨진다. 그래서 최종 수정에서는 다음 기준을 사용했다.

```text
특정 rule_id 기준 수정 금지
문장 구조, party marker, ratio pattern, block_type, title pattern 기준으로 수정
```

예시는 다음과 같다.

```text
좋지 않은 방식:
  차48-1이면 party를 A 후행 / B 선행으로 강제한다.

최종 수정 방향:
  새 rule 제목 marker와 다음 기준번호 marker를 기준으로 boundary를 다시 나눈다.
  party raw_text 안의 (A), (B), 보, 차 marker를 우선한다.
  base_fault 표 안에서 0:100, 40:60 같은 pair ratio를 추출한다.
```

## 다이어그램 제외 기준

작업 도중 여러 검증 보고서에서 `diagrams.jsonl`, `diagram_image_path`, `diagram_bbox`가 언급되었다.

하지만 이번 프로젝트의 우선순위는 텍스트 기반 Neo4j 적재와 과실비율 계산이었다. 따라서 다이어그램 crop, bbox, 이미지 저장은 범위에서 제외했다.

정리 기준은 다음과 같다.

```text
포함:
  rule
  party
  base_fault
  variant
  adjustment_factor
  law_ref
  reference_case
  usage_note
  chunk

제외:
  diagram crop
  image path
  bbox
  page image
```

즉, 문서 안에 diagram 관련 row가 있더라도 이번 수정 이력에서는 품질 판단 기준으로 사용하지 않는다.

## 초기 문제

초기 문제는 다음과 같았다.

```text
회전-9~15 lane_path가 비어 있음
```

## 수정한 코드 계층

주요 수정 대상은 다음이다.

```text

  - party action text cleaning
```

## 수정 기준

기존에는 party action 하나에서 첫 번째 차로만 잡는 문제가 있었다.

예를 들어 다음 문장은 여러 step으로 쪼개져야 한다.

```text

```

수정 후 기대 구조는 다음이다.

```text
step 1: 진입 / 12시 방향 / 진입1차로
step 2: 회전 / 회전1차로
step 3: 진출 / 3시 방향 / 진출1차로
```

차로변경이 있는 경우도 별도 step으로 분해한다.

```text
step 1: 진입
step 2: 회전
step 3: 차로변경
step 4: 진출
```

또한 원문에 없는 차로/방향은 억지로 채우지 않도록 했다.

```text
원문에 명시됨:
  lane 또는 direction 확정값

원문에 명시되지 않음:
  None 유지
```


## 2023 official이 가장 어려웠던 이유

2023 공식 인정기준은 201개 rule, 600쪽 PDF 기반이라 다른 기준서보다 훨씬 복잡했다.

어려웠던 이유는 다음과 같다.

```text
1. rule 개수가 많음
2. 보행자/자동차/자전거/농기계 등 party type이 섞임
3. 기본과실이 pair_ratio와 variant_ratio로 나뉨
4. 수정요소 표가 여러 줄로 깨져 있음
5. shared explanation marker가 들어감
6. 다음 rule 제목과 이전 rule 본문이 붙는 boundary 문제가 있음
7. 법규/판례/활용참고가 다음 장 목차와 섞일 수 있음
```

## 1차 문제: adjustment target 누락

초기 2023 전처리에서 가장 큰 문제는 수정요소 target이었다.

문제 상태:

```text
adjustment_factors는 추출됨
하지만 target_party_key가 null인 row가 많음
target_party_type도 null
condition_text도 부족
factor_name이 비어 있는 row도 많음
```

이 상태에서는 다음 질문에 답할 수 없다.

```text
"야간 +5"가 보행자 과실을 올리는가?
"차의 현저한 과실 -10"이 자동차 과실을 낮추는가?
"B 진로변경 신호불이행 +10"이 B에게 붙는가?
```

## adjustment target 수정 기준

수정 대상 코드:

```text
official_2023/extractors.py
  - extract_adjustment_factors()
  - target 추론 함수
  - 표 row 병합 로직
```

수정 기준:

```text
1. raw_text에 A/B/보/차가 있으면 우선 target으로 사용
2. 줄바꿈 때문에 target marker가 앞줄에만 있으면 다음 줄까지 문맥 유지
3. "B진로변경 / 신호불이행· / 지연 / +10" 같은 분리 row를 하나의 수정요소로 병합
4. adjustment_explanation의 "보행자의 과실", "B차량의 과실" 같은 문장을 target 보강 힌트로 사용
5. 그래도 불명확하면 억지로 붙이지 않고 auto_calculation_eligible=false 처리
```

이 수정 후 unresolved target은 크게 줄었고, 이후에는 target null 0건 상태까지 개선되었다.

## 2차 문제: shared explanation marker가 가짜 수정요소로 들어감

target 보강 이후 새 문제가 드러났다.

문제 row 예시:

```text
__SHARED_EXPLANATION__ 거9-7
※舊 424 기준 __SHARED_EXPLANATION__ 거9-7
```

이건 수정요소가 아니라 공유 해설 marker다.

하지만 숫자와 `-7`이 포함되어 있어 parser가 `delta=-7`인 수정요소처럼 잘못 인식했다.

문제점:

```text
raw_text = ※舊 424 기준 __SHARED_EXPLANATION__ 거9-7
target_party_key = A
delta = -7
auto_calculation_eligible = true
```

이 상태로 Neo4j에 넣으면 존재하지 않는 수정요소가 자동 계산에 포함된다.

## shared marker 수정 기준

수정 대상:

```text
official_2023/extractors.py
  - adjustment candidate filter
```

최종 기준:

```text
__SHARED_EXPLANATION__ marker는 adjustment_factors에서만 제외
rule_blocks, chunks, law_refs, reference_cases 연결은 유지
```

중요했던 점은 marker를 전역 삭제하면 안 된다는 것이다.

실제로 한 번은 marker 제거 범위를 넓게 잡으면서 다음 회귀가 발생했다.

```text
rules: 201개 -> 199개로 감소
parties: 402개 -> 344개로 감소
base_fault unknown 증가
거43-2, 거43-3 사라짐
law_refs/reference_cases/usage_notes 감소
```

이 회귀를 통해 marker는 adjustment 후보에서만 제외해야 한다는 기준이 확정되었다.

```text
고속도로, 자동차전용도로 문맥은 횡단보도/회전교차로가 아님
보행자와 자동차 party가 함께 있으면 자동차와 보행자 사고 계열로 분류
도로 문맥은 accident_subgroup 또는 road_context에 남긴다
```

기대 결과:

```text
accident_group = 자동차와 보행자
accident_subgroup = 고속도로 또는 자동차전용도로/기타
```

# 실제 수정 흐름 요약

전체 작업 흐름을 시간순으로 요약하면 다음과 같다.

```text
1. PDF 수집 코드와 경로 정리
2. crawling_settings.json / pipeline_settings.json 기반 경로 정리
3. Playwright 브라우저 설치 자동화 검토
4. 전처리 코드 이동 후 경로 문제 수정
5. output directory 생성 누락 수정
6. 2020 비정형 전처리 1차 감사
7. 2020 summary/road_context/review_case/movement 보정
8. 2021 PM 전처리 1차 감사
9. PM adjustment target, scenario, shared group, road_context 분리
10. 2025 roundabout 전처리 1차 감사
11. LanePath/LaneStep 다단계 구조 보정
12. 2023 official 전처리 1차 감사
13. adjustment target 대량 누락 보정
14. shared marker가 adjustment로 들어가는 문제 제거
15. shared marker 제거 중 rule/party/base_fault가 줄어드는 회귀 복구
16. 차47-3/차48-1 boundary 복구
17. 보22 variant 복구
18. 차43-7 pair variant 처리
19. 차61-3 일반 base_fault 처리
20. movement 추론 우선순위 보정
21. 보29-1/보29-2 party_type 보정
22. 보35/보36 movement 및 accident classification 보정
```

이 중 가장 중요한 교훈은 다음이다.

```text
수정요소 parser만 고치려다가 rule boundary나 shared block 연결을 건드리면 전체 row 수가 줄어드는 회귀가 발생한다.
따라서 adjustment_factors 후보 필터링, rule_blocks 보존, chunks 보존, law/reference 연결은 서로 분리해서 수정해야 한다.
```

# 최종 사용 기준

전처리 결과를 Neo4j에 넣을 때는 다음 순서로 사용하는 것이 안전하다.

```text
1. rules.jsonl로 Rule 노드 생성
2. parties.jsonl로 Party 노드 및 HAS_PARTY 관계 생성
3. base_faults.jsonl로 기본과실 관계 생성
4. variants.jsonl 또는 rule_scenarios.jsonl이 있으면 기본과실 계산에서 variants 우선
5. adjustment_factors.jsonl은 auto_calculation_eligible=true인 row만 자동 계산에 사용
6. auto_calculation_eligible=false인 row는 근거/검토용으로만 연결
7. law_refs/reference_cases/usage_notes/chunks는 설명 근거와 검색용으로 연결
8. diagram/image 관련 데이터는 이번 텍스트 전처리 범위에서 제외
```

이 기준을 지키면 다음 문제를 피할 수 있다.

```text
가짜 shared marker가 과실비율로 계산되는 문제
variant rule을 단일 base_fault로 계산하는 문제
target이 모호한 수정요소를 A/B에 억지로 붙이는 문제
다음 rule party가 이전 rule에 붙는 문제
보행자 도로 명칭을 party_type=pedestrian으로 오인하는 문제
```
