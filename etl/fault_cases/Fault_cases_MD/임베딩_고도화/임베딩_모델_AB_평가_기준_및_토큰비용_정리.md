# 임베딩 모델 A/B 테스트 평가 기준 정리

> 작성 목적  
> 판례, 인정기준, 심의사례 임베딩 모델 비교 계획에서 코사인 유사도와 평가 지표의 역할을 구분하고, 불필요하게 복잡한 평가 항목을 줄이기 위한 기준을 정리한다.

---

## 1. 핵심 결론

임베딩 검색 자체는 **코사인 유사도**를 사용하면 된다.

다만 여러 임베딩 모델의 성능을 비교할 때는 모델별 코사인 유사도 절대값을 직접 비교하면 안 된다.

```text
코사인 유사도
= 각 모델 안에서 문서 검색 순위를 정하는 기준

Hit@K, MRR
= 검색 결과에 실제 정답이 제대로 포함됐는지 평가하는 기준
```

따라서 이번 실험은 다음 구조로 진행한다.

```text
질문 임베딩 생성
→ 문서 임베딩과 cosine similarity 계산
→ Top-10 검색
→ 정답 ID 기준 Hit@1, Hit@5, MRR@10 계산
```

---

## 2. 코사인 유사도만으로 모델을 비교하면 안 되는 이유

모델마다 임베딩 공간과 점수 분포가 다르다.

예를 들어 다음과 같은 결과가 나올 수 있다.

### 모델 A

| 순위 | 검색 결과 | 코사인 유사도 |
|---:|---|---:|
| 1 | 오답 | 0.91 |
| 2 | 정답 | 0.88 |

### 모델 B

| 순위 | 검색 결과 | 코사인 유사도 |
|---:|---|---:|
| 1 | 정답 | 0.76 |
| 2 | 오답 | 0.73 |

모델 A의 최고 유사도는 0.91이고 모델 B는 0.76이지만, 실제 검색 성능은 정답을 1위에 올린 모델 B가 더 좋다.

따라서 다음 비교는 사용하지 않는다.

```text
모델 A 최고 유사도 0.91
모델 B 최고 유사도 0.76

→ 0.91이 더 높으므로 모델 A가 우수하다
```

모델 간 비교에서는 **정답 검색 순위**를 기준으로 판단해야 한다.

---

## 3. 1차 실험에 필요한 평가 지표

처음부터 모든 검색 평가 지표와 통계 검정을 적용할 필요는 없다.

1차 임베딩 모델 비교에서는 다음 세 가지면 충분하다.

### 3.1 Hit@1

```text
검색 결과 1위가 정답인가?
```

- 정답이면 1
- 오답이면 0

사용자 질문에 가장 정확한 문서를 바로 반환하는 능력을 평가한다.

### 3.2 Hit@5

```text
검색 결과 상위 5개 안에 정답이 포함됐는가?
```

최종 Agent나 RAG가 상위 여러 문서를 함께 참고한다면 Hit@5가 중요하다.

### 3.3 MRR@10

```text
정답이 상위 10개 중 몇 번째에 위치했는가?
```

| 정답 순위 | 점수 |
|---:|---:|
| 1위 | 1.00 |
| 2위 | 0.50 |
| 3위 | 0.33 |
| 5위 | 0.20 |
| 10위 밖 | 0 |

정답을 높은 순위에 배치할수록 점수가 높다.

---

## 4. nDCG는 언제 사용하는가

nDCG@10은 정답이 하나가 아니라 여러 개이고, 관련도 수준이 서로 다를 때 유용하다.

예를 들어 판례나 심의사례는 하나의 질문에 다음처럼 여러 관련 사례가 있을 수 있다.

```text
3점: 사고 구조와 핵심 쟁점이 거의 동일
2점: 사고 구조는 유사하지만 일부 조건이 다름
1점: 관련 주제이나 직접적인 정답은 아님
0점: 무관
```

이 경우 완전한 정답이 상위에 나오고 부분 관련 문서가 그 뒤에 배치되는지를 평가하기 위해 nDCG를 사용할 수 있다.

다만 1차 실험에서는 필수가 아니다.

```text
1차 필수:
- Hit@1
- Hit@5
- MRR@10

2차 선택:
- nDCG@10
- 세부 유형별 분석
- 통계적 유의성 검정
```

## 5. 데이터별 권장 평가 단위

### 5.1 인정기준

정답 단위가 명확한 `rule_id`이므로 가장 단순하게 평가할 수 있다.

```text
정답 기준:
rule_id

평가 지표:
- Rule Hit@1
- Rule Hit@5
- Rule MRR@10
```

정답 Rule이 하나인 경우 nDCG는 우선 제외해도 된다.

### 5.2 심의사례

한 사례에 여러 청크가 존재하므로 청크 자체보다 사례 단위가 우선이다.

```text
1차 정답:
review_case_id

2차 분석:
expected_chunk_type
```

권장 지표:

```text
- Case Hit@1
- Case Hit@5
- Case MRR@10
- 필요 시 Case nDCG@10
```

### 5.3 판례

판례도 하나의 사건에 `holding`, `summary`, `reasoning` 등 여러 청크가 존재한다.

같은 사건의 청크가 여러 개 검색될 수 있으므로 검색 후 `case_id` 기준으로 중복을 제거한 뒤 평가한다.

```text
1차 정답:
case_id

2차 분석:
chunk_id
chunk_type
```

권장 지표:

```text
- Case Hit@1
- Case Hit@5
- Case MRR@10
- 필요 시 Case nDCG@10
```

## 6. 평가 지표가 토큰을 추가로 소비하는가

Hit@1, Hit@5, MRR, nDCG 계산 자체는 임베딩 토큰을 추가로 사용하지 않는다.

문서와 질문을 한 번 임베딩하고 검색 결과를 저장하면, 같은 결과를 이용해 여러 평가 지표를 계산할 수 있다.

```text
문서 임베딩 1회
질문 임베딩 1회
Top-10 검색 1회
↓
Hit@1 계산
Hit@5 계산
MRR@10 계산
필요 시 nDCG@10 계산
```

평가 지표 계산은 Python이나 SQL로 처리되므로 별도의 API 토큰 비용이 발생하지 않는다.

---

## 7. 실제 토큰과 비용이 발생하는 지점

비용의 대부분은 평가 지표가 아니라 **문서 임베딩 생성**에서 발생한다.

### OpenAI API 모델

```text
- text-embedding-3-small
- text-embedding-3-large
```

두 모델은 입력 토큰 기준 API 비용이 발생한다.

### 로컬 실행 모델

```text
- BGE-M3
- Qwen3-Embedding
- multilingual-E5
```

로컬 모델은 OpenAI 토큰 비용이 발생하지 않는다.

대신 다음 비용이 발생한다.

```text
- RunPod GPU 사용시간
- 모델 다운로드 시간
- 스토리지 사용량
- 실행환경 구성 및 운영 관리
```

## 8. 판례 데이터의 예상 토큰 규모

판례 데이터는 약 8,334개 청크이며 전체 `embedding_text`는 약 696만 자다.

한국어 토크나이저별 차이를 고려하면 계획 단계에서는 다음 범위로 예상할 수 있다.

```text
약 696만 자
→ 약 400만~800만 input tokens 예상
```

OpenAI 모델 두 개를 각각 한 번 실행하면 대략 다음과 같다.

```text
text-embedding-3-small:
약 400만~800만 input tokens

text-embedding-3-large:
약 400만~800만 input tokens

두 모델 합계:
약 800만~1,600만 input tokens
```

정확한 토큰 수와 비용은 실행 전 `tiktoken` audit와 실제 API 응답의 `usage.total_tokens`로 확정한다.

## 9. 평가 Query 비용

평가 질문 수가 50개 또는 100개라면 query 임베딩 비용은 문서 임베딩에 비해 매우 작다.

예시:

```text
평가 Query 100개
Query당 평균 100 tokens 가정

100 × 100
= 약 10,000 tokens
```

모델별로 다시 임베딩해도 전체 문서 수백만 토큰에 비하면 작은 규모다.

따라서 비용 관리에서 우선 확인할 대상은 평가 질문 수보다 전체 문서 코퍼스 크기다.

---

## 10. 토큰과 비용이 불필요하게 증가하는 경우

다음 상황에서는 전체 문서를 다시 임베딩해야 할 수 있으므로 주의해야 한다.

```text
- 문서 embedding_text 구성을 변경
- 청크 크기나 overlap 변경
- 전체 문서를 다시 청킹
- 모델별 입력 prefix 또는 instruction을 계속 변경
- 동일 모델을 설정만 바꿔 반복 실행
- 평가 결과를 본 뒤 문서 템플릿을 수정
- 저장한 임베딩을 재사용하지 않고 매번 다시 생성
```

반대로 다음 변경은 문서 임베딩을 다시 만들 필요가 없다.

```text
- Hit@1에서 Hit@5 추가
- MRR@10 추가
- 결과표 형식 변경
- 비용 가중치 변경
- 모델 선정 기준 변경
- 기존 검색 결과를 이용한 오류 분석
```

## 11. 권장 실험 진행 순서

처음부터 판례 8,334청크를 모두 실행하기보다 작은 코퍼스부터 검증하는 것이 안전하다.

### 1단계: 인정기준

```text
문서:
rule_summary 277개

목적:
- 모델 adapter 정상 작동 확인
- 차원 1024 확인
- cosine 검색 확인
- 평가 코드 확인
- 비용 기록 방식 확인
```

### 2단계: 심의사례

```text
문서:
구조화 청크 904개

목적:
- 사례 단위 중복 제거 확인
- 여러 관련 사례 평가 확인
- 청크 유형별 검색 결과 확인
```

### 3단계: 판례

```text
문서:
8,334청크

목적:
- 최종 대규모 모델 비교
- case_id 단위 검색 성능 평가
- 실제 비용 및 생성시간 비교
```

작은 데이터에서 파이프라인 오류를 먼저 잡으면 판례 전체를 불필요하게 재임베딩하는 위험을 줄일 수 있다.

## 12. 최소 실행 기준

1차 임베딩 모델 비교는 다음 정도로 단순화한다.

```text
평가 Query:
- smoke 10개
- 정식 test 50~100개

검색:
- pgvector exact cosine
- Top-10 반환

정답 기준:
- 인정기준: rule_id
- 심의사례: review_case_id
- 판례: case_id

평가 지표:
- Hit@1
- Hit@5
- MRR@10

비용 및 운영 지표:
- 문서 임베딩 비용
- Query 임베딩 비용
- 임베딩 생성시간
- 평균 검색시간
- 저장 용량
- 운영 난이도
```

## 14. 최종 정리

```text
코사인 유사도:
각 모델 내부에서 문서 검색 순서를 정한다.

Hit@1:
정답을 바로 1위로 찾았는지 확인한다.

Hit@5:
정답이 상위 후보 안에 포함됐는지 확인한다.

MRR@10:
정답을 얼마나 높은 순위에 배치했는지 확인한다.

nDCG@10:
여러 관련 문서의 관련도 순서까지 평가할 때 선택적으로 사용한다.
```

이번 1차 실험은 복잡한 통계 검정보다 다음 기준에 집중한다.

```text
정답을 실제로 잘 찾는가?
비용은 얼마나 드는가?
실제 서비스에서 운영하기 쉬운가?
```

평가 지표를 많이 추가한다고 임베딩 토큰이 더 소비되는 것은 아니다. 토큰과 비용을 줄이려면 평가 지표를 줄이기보다 문서 임베딩 재생성을 방지하고, 작은 코퍼스에서 파이프라인을 먼저 검증해야 한다.
