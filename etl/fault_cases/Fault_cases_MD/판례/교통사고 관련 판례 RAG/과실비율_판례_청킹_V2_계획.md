# 과실비율 판례 전용 청킹 V2 계획

## 0. 이 문서의 범위

이 문서는 `traffic_precedents`에서 분류한 **과실비율 판례 데이터만** 다룬다.

- 대상 source type: `fault_ratio_precedent`
- 대상 검색 방식: pgvector dense retrieval
- 검색 query: `agent_input.query_text`
- 제외: 심의사례(`review_case`)
- 제외: 교통사고 일반판례(`traffic_precedent`) BM25/Nori
- 제외: Hybrid, BM25, Neo4j, reranker
- 차원 비교: 이번 단계가 아니라 임베딩 모델 A/B 다음 단계

`교통사고 관련 판례 RAG` 폴더의 기존 문서는 주로 `traffic_precedent`의
BM25/Nori 검색 결과를 다룬다. 검색 결과 표, `source_reference`, 사람 검수 흐름은
참고할 수 있지만 이번 코퍼스와 검색 방식의 직접 기준은 아니다.

### 1.1 완료된 단계

현재 최종 과실비율 판례 산출물은 다음 파일이다.

확인 결과는 다음과 같다.

| 항목 | 현재 값 |
|---|---:|
| 2차 과실비율 증거 검증 통과 | 1,006건 |
| RAG ready | 987건 |
| review flag 보유 | 779건 (ready 내부 부분집합) |

따라서 **규칙 기반 1차 교통사고 분류, 2차 과실비율 증거 검증, RAG 최종 적합성
게이트 및 ready 코퍼스 청킹까지 실행된 상태**다.

### 1.2 아직 완료로 보면 안 되는 단계

다음은 아직 운영 완료 상태로 보면 안 된다.

1. `rag_review_flags` 보유 779건의 표본 QA
2. 임베딩 생성
3. 1024차원 A/B 전용 pgvector 테이블과 인덱스 생성
4. 50개 query Ground Truth 기반 검색 평가

기존 DB loader는 `case_id`, `holding`, `summary`, `main_text` 같은 영문 필드를
읽는다. 최종 JSONL은 `_case_id`, `판시사항`, `판결요지`, `판례내용`, `이유` 같은
한글 필드이므로 현재 loader 앞에 명시적 매핑이 없으면 null 적재 위험이 있다.

### 1.3 "순도 100%" 표현을 쓰면 안 되는 이유

기존 1,006건 표본 확인에서 아래와 같은 비교통 사건이 포함된 것을 확인했다.

```text
case_id=605709
사건명=근로자지위확인등·근로자지위확인등
핵심 내용=근로자파견 및 직접고용 의무

case_id=239487
사건명=손해배상(의)
핵심 내용=의료과오 손해배상

case_id=172935
사건명=공제급여청구의소
핵심 내용=학교안전 공제급여
```

긴 판결문 어딘가에 `사고`, `도로`, `과실`, `손해배상`이 함께 등장하면 규칙 점수가
올라갈 수 있었다. 이 문제를 2차 검증 코드에 RAG 적합성 게이트로 통합하여 위 사례는
현재 사건명으로 확정할 수 있는 19건을 `fault_ratio_rag_excluded`로 분리했다.

나머지는 교통 표현이 약하거나 보험·연금·절차 등 부수 쟁점이 있더라도 자동 제외하지
않고 `rag_review_flags`를 붙인다. 이 플래그는 ready 코퍼스에서 빼는 라벨이 아니라
QA와 오류 분석을 위한 메타데이터다. 현재 987건 중 779건에 하나 이상의 플래그가 있다.

## 3. 기존 계획과 코드 평가

### 3.1 살릴 부분

다음 아이디어는 타당하다.

- 판례 필드를 먼저 분리한다.
- 긴 `이유`는 법률 목차와 문장 경계를 우선한다.
- 지나치게 긴 단락에만 길이 폴백을 적용한다.
- 잘린 본문에 최소한의 사건 문맥을 제공한다.
- 청크 ID와 원문 출처를 추적 가능하게 저장한다.

### 3.2 수정이 필요한 부분

| 기존 상태 | 문제 | V2 결정 |
|---|---|---|
| 계획서는 계층 청킹이라고 설명 | 실제 코드는 1,500자/250자 문자 창 | 목차 → 문장 → 문자 폴백 순서 구현 |
| `판례내용` 전체를 `main_text`로 청킹 | `이유`와 327건 중복 | `이유`가 없을 때만 `판례내용` 사용 |
| 별도 `fault_ratio_evidence` 청크 생성 | 같은 본문이 evidence/main에 중복되어 top-k 점유 | 본문은 한 번만 저장하고 metadata flag로 표시 |
| 각 키워드의 첫 출현만 evidence로 사용 | 뒤쪽의 실제 과실 판단을 놓칠 수 있음 | 모든 본문 청크에 비율 표현과 문맥 flag 추출 |
| `chunk_text=search_text` | RAG 원문과 임베딩 입력 역할이 섞임 | `chunk_text`와 `embedding_text` 분리 |
| 모든 청크에 긴 metadata 강제 주입 | 반복 텍스트가 의미 벡터를 지배할 수 있음 | 사건명·문서구역·사건종류만 짧게 주입 |
| 위치 기반 ID | 앞 청크 변경 시 뒤 ID가 전부 이동 | source type + content hash 기반 안정 ID |
| `len(text)//3` 토큰 추정 | 모델별 tokenizer 차이를 반영하지 못함 | 5개 모델 tokenizer preflight 별도 수행 |
| 분류 근거 키워드를 검색 본문에 포함 | 분류 규칙이 검색 정답을 누출할 수 있음 | 원 판례 필드만 embed, 분류 필드는 metadata만 저장 |
| DB 전체 DELETE 후 재생성 | 실패 시 기존 청크가 사라질 수 있음 | JSONL dry-run → 검수 → 별도 실험 테이블 적재 |

## 4. V2 청크 대상

### 4.1 포함 필드

| 순서 | chunk type | 원본 필드 | 역할 |
|---:|---|---|---|
| 1 | `holding` | `판시사항` | 법적 쟁점 |
| 2 | `summary` | `판결요지` | 사실관계와 판단 요약 |
| 3 | `reasoning` | `이유` | 사고 경위, 당사자 과실, 법원 판단 |
| 4 | `main_text_fallback` | `판례내용` | `이유`가 없을 때만 사용 |

### 4.2 초기 dense index에서 제외하는 필드

| 필드 | 제외 이유 |
|---|---|
| `주문` | 사고 유사도보다 인용/기각/비용 정보가 중심 |
| `참조조문` | 법령명 검색용이며 사고 사실 query와 목적이 다름 |
| `참조판례` | 사건번호 중심으로 dense 유사도 기여가 낮음 |
| `fault_ratio_*` 분류 필드 | 규칙 기반 파생값이며 검색 입력 누출 위험 |
| 별도 metadata 청크 | 짧은 라벨 청크가 top-k를 점유할 수 있음 |

제외 필드는 삭제하지 않고 case/chunk metadata에 보관한다. 이후 별도 법령 검색이나
필터가 필요할 때 사용한다.

## 5. V2 분할 규칙

### 5.1 분할 우선순위

```text
원본 필드 분리
→ 법률 목차 경계(1., 가., 1), (1), I.)
→ 한국어 문장 경계
→ 최대 길이 초과 시 문자 경계 폴백
→ 짧은 꼬리 청크를 인접 청크와 병합
→ 단독 목차 표지(예: "1.") 제거
```

날짜 `2022. 10. 13.`은 숫자 목차로 오인하지 않도록 예외 처리한다.

### 5.2 현재 후보 파라미터

```json
{
  "strategy": "fault_ratio_precedent_v2",
  "target_chars": 900,
  "max_chars": 1200,
  "overlap_units": 1
}
```

`overlap_units=1`은 고정 250자 overlap이 아니라 직전 법률 단락 또는 문장 단위
1개를 뜻한다.

이 값은 **현재 드라이런 후보값**이다. 모델 A/B 직전 5개 모델 tokenizer로
`embedding_text`를 측정하고, 한 모델이라도 truncation이 발생하면 `max_chars`를
낮춘 뒤 전 모델용 청크를 함께 재생성한다. 모델별로 서로 다른 청크를 쓰면 안 된다.

### 5.3 청크 텍스트 분리

```text
chunk_text:
  판결문 원문 근거. 최종 답변 evidence에 사용.

embedding_text:
  사건명 + 문서구역 + 사건종류 + chunk_text.
  5개 모델에 완전히 동일한 문자열을 입력.
```

예시:

```text
판례명: 구상금
문서구역: 이유
사건종류: 민사
2. 사고 경위 원고 차량은 직진하고 피고 차량은 좌회전하였다...
```

사건번호, 선고일, 법원명, 분류 점수, 분류 키워드는 metadata로만 저장한다.

### 5.4 ID 규칙

```text
{case_id}:fault_ratio_precedent_v2:{chunk_type}:{sha256 앞 12자리}
```

위치 번호만으로 ID를 만들지 않는다. 동일 본문은 같은 hash를 가져 Ground Truth와
검색 로그를 추적하기 쉽다.

## 8. 임베딩 모델 A/B 전에 통과할 게이트

### Gate 1. 코퍼스 검수

2차 검증의 `03_fault_ratio_review_flagged_cases.jsonl` 779건은 ready 987건에 포함된
부분집합이다. 임베딩 모델 A/B에서는 제외하지 않되, 플래그별 층화 표본을 사람이
확인하고 검색 실패 분석 시 해당 메타데이터를 사용한다.

```json
{
  "case_id": "sample_case_id",
  "decision": "keep|exclude|uncertain",
  "review_flags": ["suspected_non_traffic_issue:insurance_coverage_only"],
  "reason": "표본 검수 사유"
}
```

판정값은 `keep`, `exclude`, `uncertain`으로 고정한다. 두 사람이 일부를 교차 검수해
규칙을 맞춘 뒤 전체를 처리한다.

### Gate 2. 청크 품질

필수 조건:

- 입력 case 수와 처리 case 수 일치
- 빈 `chunk_text` 0건
- `max_chars` 초과 0건
- 동일 case/type/text hash 중복 0건
- 단독 목차 표지 0건
- `이유`와 `판례내용` 이중 색인 0건
- 모든 chunk에 원문 case와 source field 추적값 존재

### Gate 3. 모델별 tokenizer preflight

비교 대상 5개 모두 같은 `embedding_text`를 검사한다.

```text
text-embedding-3-small
text-embedding-3-large
BAAI/bge-m3
Qwen/Qwen3-Embedding-0.6B
intfloat/multilingual-e5-large
```

검사 결과에는 모델별 최대/중앙/P95 token 수와 truncation 건수를 남긴다.
truncation 허용값은 0건이다.

### Gate 4. 코퍼스 동결

최종 청크 JSONL의 SHA-256, row 수, chunk type 분포를 manifest에 기록한다. 5개 모델
모두 같은 manifest를 사용한다. 모델별 임베딩 실행 중 청크를 다시 만들지 않는다.

## 9. OpenAI와 RunPod 실행 경계

청킹은 CPU 작업이므로 로컬에서 수행한다.

```text
로컬:
  최종 판례 검수
  청킹
  tokenizer preflight
  corpus manifest 생성

OpenAI API:
  text-embedding-3-small
  text-embedding-3-large

RunPod GPU:
  BAAI/bge-m3
  Qwen/Qwen3-Embedding-0.6B
  intfloat/multilingual-e5-large

공통 pgvector:
  같은 chunk_id와 embedding_text로 적재
  같은 query_text, top_k, cosine distance로 비교
```

RunPod에는 원본 1,006건 전체가 아니라 최종 ready 987건에서 생성한 동결 청크 JSONL과 manifest를
전달한다. RunPod에서 임의로 재청킹하거나 모델별 전처리 문구를 섞지 않는다.
단, E5/Qwen/BGE가 공식적으로 요구하는 query/document prefix가 있으면 adapter에
명시하고 결과 보고서에 기록한다.

## 10. 실행 순서

```text
1. ready 987건과 청크 8,334개 manifest 동결
2. 5개 tokenizer preflight
3. 필요 시 max_chars 하향 후 전 청크 재생성
4. 청크 JSONL + manifest 재동결
5. OpenAI API 및 RunPod에서 모델별 임베딩 생성
6. A/B 전용 1024차원 pgvector 테이블에 모델별 적재
7. 동일한 50개 query Ground Truth로 Hit@K, MRR, nDCG, latency, cost 비교
```
