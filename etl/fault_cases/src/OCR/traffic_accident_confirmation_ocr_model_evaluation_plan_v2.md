# 교통사고사실확인원 OCR 모델 비교 평가 — 실전 테스트 가이드 v2

> **문서 목적**: OCR LangGraph에서 사용할 Vision/OCR 모델을 선정하기 위한 실험 설계, 실행 절차, 결과 해석 방법을 한 파일에 정리한다.  
> **이 문서를 읽으면**: 왜 이 구조로 테스트하는지, 어떻게 실행하는지, 결과를 보고 어떻게 판단하는지까지 이해할 수 있어야 한다.

---

## 1. 왜 이 테스트가 필요한가

### 1-1. 배경

교통사고사실확인원 OCR은 과실비율 분석 Agent의 **입력 데이터 생산 단계**다.  
OCR이 틀리면 그 뒤의 과실비율 분석 자체가 잘못된 근거 위에서 돌아간다.

따라서 "어떤 모델이 가장 비싸거나 최신인가"가 아니라,  
**"어떤 모델이 과실비율 Agent가 실제로 사용할 수 있는 OCR 결과를 안정적으로 만드는가"** 가 선택 기준이다.

### 1-2. 이 테스트로 결정하는 것

- **운영 기본 모델 확정** — `prompts.py`의 `DEFAULT_OCR_MODEL` 값
- **비용 예측** — 서비스 운영 시 월 처리 비용 추정 근거
- **품질 하한선 파악** — 어떤 이미지 조건에서 partial/failed가 발생하는지

### 1-3. 이 테스트로 결정하지 않는 것

- 프롬프트 최적화 (모델 선정 이후 별도 작업)
- 이미지 전처리 (해상도, 회전 보정 등)
- 2page/사고현장약도 분석 지원 여부

## 2. 비교 모델 5개 — 선택 이유

### 2-1. 최종 후보

| 모델 | 포지션 | Input (1M) | Output (1M) | 선택 이유 |
|---|---|---:|---:|---|
| `gpt-4o-mini` | 최저비용 가성비 | $0.15 | $0.60 | 입출력 모두 가장 저렴. OCR 품질이 충분하면 비용 관점에서 가장 강한 후보 |
| `gpt-5.4-nano` | 최신 초저비용 | $0.20 | $1.25 | 최신 5.4 계열 중 가장 저렴. nano 계열이 작은 한글 OCR에서 버티는지 확인 필요 |
| `gpt-5.4-mini` | 기본 후보 | $0.75 | $4.50 | 비용/성능 균형 후보. MVP 기본값 1순위로 가장 먼저 확인 |
| `gpt-4o` | 기존 Vision 기준선 | $2.50 | $10.00 | 최신이 아니지만 한글 OCR에서 검증된 Vision 모델. 기준선으로 비교 |
| `gpt-5.4` | 품질 승격 후보 | $2.50 | $15.00 | mini/nano가 Critical 필드를 자주 놓칠 때 올려볼 고품질 후보 |

### 2-2. 왜 이 5개인가

OCR 모델 비교의 축이 다음 5가지여야 하기 때문이다.

```
최저비용        → gpt-4o-mini
최신 초저비용   → gpt-5.4-nano
최신 기본형     → gpt-5.4-mini
기존 기준선     → gpt-4o
품질 승격       → gpt-5.4
```

이 5개를 비교하면 **비용-품질 트레이드오프 곡선** 전체를 커버할 수 있다.  
하나라도 빠지면 "비싸지만 더 나은지"나 "저렴해도 충분한지"를 검증할 비교군이 없어진다.

### 2-3. 제외한 모델과 이유

| 모델 | 제외 이유 |
|---|---|
| `gpt-5.5` | 교통사고사실확인원 OCR은 고난도 법률 추론이 아니라 정형 문서 필드 추출이다. 5.5의 고성능이 필요한 작업이 아닐 가능성이 높다. 5개 후보가 모두 Critical 추출률 80% 미달 시에만 추가 평가한다. |
| `gpt-5`, `gpt-5.2` | 포지션이 중복된다. 저비용은 `gpt-4o-mini`/`gpt-5.4-nano`가, 기본형은 `gpt-5.4-mini`가, 품질 승격은 `gpt-5.4`가 더 명확한 역할을 한다. |
| `gpt-5-pro` 계열 | OCR MVP 단계에서는 비용 과다. |

### 3-2. 왜 5장인가

- **3장(smoke test)**: 기본 동작 확인에는 충분하지만, 모델 선택 근거로는 약하다.
- **5장**: 정상 이미지 + 잘린 이미지 + 구양식 + 최신 양식 + 다른 지역을 한 번에 커버한다.  
  모델이 다양한 실제 문서에 대응하는지 검증하기에 충분한 최소 규모다.
- **10장 이상**: 이 단계에서는 과하다. 모델 선정 후 더 많은 샘플로 검증하는 것이 맞다.

### 3-3. 각 샘플의 역할

**샘플 1 (`17-10-16-서울노원구.png`)**  
정상 이미지. 모든 모델이 이 샘플에서 Critical 필드를 다 뽑아야 한다.  
못 뽑는다면 그 모델은 기본 OCR 성능 자체에 문제가 있다는 신호다.

**샘플 2 (`24-00-00-경기도부천시.jpg`)**  
날짜가 `24-00-00`으로 표기된 점이 특이하다. 잘린 이미지일 가능성이 있다.  
이 샘플에서 `partial` 또는 `failed`로 판정되는지 확인하는 것 자체가 목적이다.  
모델이 "잘린 이미지를 잘린 이미지라고 인식하는지" 테스트한다.

**샘플 3 (`15-07-18-광주광역시.jpg`)**  
2015년 양식. 당시 경찰서 발급 양식은 지금과 레이아웃이 다를 수 있다.  
구양식에서도 Critical 필드가 추출되는지 확인한다.

**샘플 4, 5**  
다른 연도/지역 조합으로 모델이 특정 레이아웃에 과도하게 맞춰진 건 아닌지 교차 확인한다.

## 4. 테스트 구조 — 왜 이렇게 나눠져 있는가

### 4-1. 폴더 구조

```
etl/fault_cases/src/OCR/
│
├── traffic_accident_confirmation_ocr/   ← 운영 파이프라인
│   ├── prompts.py      (DEFAULT_OCR_MODEL = "gpt-5.4-mini")
│   ├── masking.py      (개인정보 마스킹 — eval에서도 재사용)
│   ├── verification.py (문서 판별 — eval에서도 재사용)
│   ├── evaluator.py    (success/partial/failed 판정)
│   ├── agent.py        (OCR 노드)
│   ├── graph.py        (LangGraph 연결)
│   └── state.py, utils.py, constants.py
│
└── eval/                                ← 모델 비교 평가 전용
    ├── config.py       (가격표, 샘플 경로, Gate 기준값)
    ├── ocr_caller.py   (API 직접 호출 + timing + usage 수집)
    ├── scorer.py       (단건 채점 → Gate 집계 → 정규화 점수)
    ├── reporter.py     (결과 저장 + 콘솔 출력)
    └── run_eval.py     (CLI 진입점)
```

결과 저장:
```
etl/fault_cases/artifacts/eval_results/
└── {timestamp}_{model}.json   ← 모델 실행 시마다 생성
```

### 4-2. 왜 eval을 운영 파이프라인과 분리했는가

**운영 파이프라인(`agent.py`)에 usage 추적을 넣지 않은 이유**:
- `agent.py`는 실제 서비스에서 단건 처리에 집중한다. 토큰 수, 비용, 처리시간 기록은 테스트에서만 필요하다.
- 운영 코드에 테스트 로직이 섞이면 이후 코드 관리가 어려워진다.

**eval에서 Gate 집계를 처리하는 이유**:
- Gate 조건(5장 평균 Critical 80% 이상, 5장 중 4장 문서 판별 등)은 **여러 샘플을 집계해야** 판정할 수 있다.
- 운영 파이프라인은 단건 처리이므로 이런 집계 로직은 맞지 않는다.

**eval에서 masking, verification을 재사용하는 이유**:
- 운영에서 쓰는 것과 같은 마스킹/판별 로직을 써야 "운영 환경에서 이 모델이 어떻게 동작할지"를 정확히 평가할 수 있다.
- 별도로 만들면 결과가 달라질 수 있다.

### 4-3. 왜 eval 모듈을 4개로 나눴는가

`run_eval.py` 하나에 다 넣으면:
- 가격표를 바꾸려면 실행 로직 파일을 열어야 한다
- 채점 로직을 고치려면 출력 로직도 같은 파일에 있다
- 나중에 "결과를 CSV로도 저장하고 싶다"는 요청이 오면 전체 파일을 뒤져야 한다

모듈 분리 후:
| 모듈 | 역할 | 수정이 필요한 경우 |
|---|---|---|
| `config.py` | 설정 모음 | 모델 추가, 가격 변동, Gate 기준 조정 |
| `ocr_caller.py` | API 호출 + 데이터 수집 | API 파라미터 변경, 타임아웃 설정 |
| `scorer.py` | 채점/집계/정규화 | 점수 계산 방식 변경 |
| `reporter.py` | 출력/저장 | 출력 형식 변경, CSV 추가 등 |
| `run_eval.py` | CLI 조립 | 실행 흐름 변경 |

## 6. 실행 방법

### 6-1. 기본 실행 (모델 한 개씩)

**왜 한 모델씩인가**:  
한 번에 25회를 돌리면 결과가 나오기 전까지 비용이 얼마나 나오는지, 품질이 어떤지 중간에 확인할 수 없다.  
한 모델(5회)씩 돌리면 결과를 보고 "이 모델은 이미 충분한데 더 비싼 걸 돌릴 필요가 있나"를 실시간으로 판단할 수 있다.

```powershell
# 프로젝트 루트(SKN27-FINAL-3Team)에서 실행

# 1. 기본 후보 먼저 (5.4-mini를 기준으로 삼음)
python -m etl.fault_cases.src.OCR.eval.run_eval --model gpt-5.4-mini

# 2. 저렴한 쪽 비교
python -m etl.fault_cases.src.OCR.eval.run_eval --model gpt-4o-mini
python -m etl.fault_cases.src.OCR.eval.run_eval --model gpt-5.4-nano

# 3. 기준선 비교
python -m etl.fault_cases.src.OCR.eval.run_eval --model gpt-4o

# 4. 품질 상한선 확인 (필요 시)
python -m etl.fault_cases.src.OCR.eval.run_eval --model gpt-5.4

# 5. 최종 비교표 출력
python -m etl.fault_cases.src.OCR.eval.run_eval --report
```

```

  → "더 저렴한데 품질이 비슷한가"를 검증. 비슷하면 여기서 멈출 수 있다

gpt-4o 그 다음

  → 비용이 가장 높으므로 앞선 모델들이 충분하면 생략 가능
```

## 7. Gate 조건 — 1단계 필터

### 7-1. Gate 조건 목록

Gate를 통과하지 못한 모델은 최종 점수 계산에서 제외된다.

| Gate 항목 | 통과 기준 | 실패 시 처리 |
|---|---|---|
| **JSON 안정성** | 5장 전부 JSON 파싱 성공 | 탈락. 프롬프트 수정 후 재평가 가능 |
| **개인정보 누출** | 주민번호·전화번호·면허번호 노출 0건 | 탈락. `masking.py` 보완 후 재평가 |
| **치명적 환각** | Critical 필드에서 이미지에 없는 값 0건 | 탈락 |
| **Critical 최소 추출률** | 5장 평균 80% 이상 | 보류. 상위 모델로 승격 검토 |
| **문서 판별** | 5장 중 4장 이상 정상 판별 | 탈락 또는 보류 |

### 7-2. 왜 이 5개가 Gate인가

**JSON 안정성**:  
JSON 파싱이 실패하면 LangGraph 후속 노드가 실행되지 않는다. 운영 불가 수준.

**개인정보 누출**:  
저장 및 Supervisor 전달 과정에서 보안 문제가 생긴다. OCR 결과가 DB에 저장될 경우 법적 리스크.  
단, `masking.py`가 후처리로 잡아주므로 모델 자체가 개인정보를 뽑더라도 masking 통과 후 0건이면 허용.

**치명적 환각**:  
이미지에 없는 사고일시/사고장소를 만들어내면 과실비율 Agent가 잘못된 사실을 근거로 분석한다.  
단순 누락보다 훨씬 위험하다. 누락은 `missing_fields`로 처리할 수 있지만, 환각은 탐지가 어렵다.

**Critical 추출률 80%**:  
5장 평균 4개 Critical 필드 중 3.2개 이상을 뽑아야 한다는 의미다.  
이것도 못하면 Supervisor가 보완 질문을 너무 많이 해야 하고, 사용자 경험이 심각하게 저하된다.

**문서 판별**:  
교통사고사실확인원이 아닌 문서를 잘못 처리하면 그 뒤 전체가 오작동한다.  
5장 중 4장 이상은 "왠만한 교통사고사실확인원 1page는 판별 가능하다"는 최소 기준이다.

### 7-3. 자동/수동 구분

| 항목 | 자동 판별 여부 |
|---|---|
| JSON 안정성 | ✅ 자동 (`ocr_caller.py`) |
| 개인정보 누출 | ⚠️ 반자동 — masking.py 통과 후 수동 재확인 필요 |
| 치명적 환각 | ❌ 수동 — JSON 파일 열어서 직접 확인 필요 |
| Critical 추출률 | ✅ 자동 (`scorer.py`) |
| 문서 판별 | ✅ 자동 (`verification.py` 재사용) |

### 7-4. 수동 확인 방법

실행 완료 후 결과 JSON 파일을 열어서 추출된 값이 실제 이미지와 일치하는지 확인한다.

```powershell
# 결과 파일 열기 (VS Code 기준)
code etl\fault_cases\artifacts\eval_results\
```

JSON 구조:
```json
{
  "model": "gpt-5.4-mini",
  "timestamp": "20260708_153012",
  "gate": {
    "gate_pass": true,
    "avg_critical_rate": 0.85,
    "doc_detected": 5
  },
  "samples": [
    {
      "sample": "17-10-16-서울노원구.png",
      "score": {
        "critical_extracted": 4,
        "critical_rate": 1.0,
        "hallucination_count": 0,   ← 환각 발견 시 수동으로 1 이상으로 수정
        "privacy_leak": 0,          ← 누출 발견 시 수동으로 1 이상으로 수정
        ...
      },
      "metrics": {
        "input_tokens": 1204,
        "output_tokens": 487,
        "elapsed_ms": 1823,
        "cost_usd": 0.00412
      }
    }
  ]
}
```

수동 확인 체크:
```
각 샘플의 "parsed" 섹션에서 extracted_fields 확인:
  [ ] accident_datetime   → 이미지의 사고 일시와 일치하는가
  [ ] accident_location   → 이미지의 사고 장소와 일치하는가
  [ ] accident_type.value → 이미지의 사고 유형과 일치하는가
  [ ] accident_description → 이미지의 사고 내용과 일치하는가

환각 기준:
  - 이미지에 보이지 않는 날짜를 만들어낸 경우 → hallucination_count += 1
  - 이미지에 없는 지역명/경찰서명을 추측한 경우 → hallucination_count += 1
  - null이어야 할 필드에 임의의 값이 들어간 경우 → hallucination_count += 1

수동 수정 후 --report 재실행하면 Gate 재판정이 반영된다.
```

## 8. 점수 계산 방식 — 2단계

Gate를 통과한 모델에 한해 최종 점수를 계산한다.

### 8-1. 최종 점수 가중합

```
최종점수 =
  비용점수   × 0.40   (40%)
+ 성능점수   × 0.45   (45%)
+ 속도점수   × 0.10   (10%)
+ 안정성점수 × 0.05   (5%)
```

**왜 이 비율인가**:

| 영역 | 비율 | 이유 |
|---|---:|---|
| 성능 | 45% | OCR 품질이 나쁘면 뒤의 과실비율 분석 전체가 흔들린다. 비용보다 조금 더 높게 설정 |
| 비용 | 40% | 서비스 운영 비용은 장기적으로 매우 중요하다. 성능과 거의 동일한 비중 |
| 속도 | 10% | 실사용 가능한 수준이면 충분하다. 극단적으로 느리지 않으면 우선순위가 낮다 |
| 안정성 | 5% | Gate 조건이 이미 안정성의 핵심을 걸러낸다. Gate 통과 후 추가 점수는 보조 역할 |

### 8-2. 비용 점수

5장 평균 1장당 비용 기준. **가장 저렴한 모델 = 100점**.

```
비용점수 = (가장 저렴한 모델의 1장 비용) ÷ (해당 모델의 1장 비용) × 100
```

예시 (실제 값은 실행 후 채워진다):

| 모델 | 1장 평균 비용 | 비용 점수 |
|---|---:|---:|
| `gpt-4o-mini` | $0.0010 | 100.0점 |
| `gpt-5.4-nano` | $0.0014 | 71.4점 |
| `gpt-5.4-mini` | $0.0041 | 24.4점 |
| `gpt-4o` | $0.0120 | 8.3점 |
| `gpt-5.4` | $0.0180 | 5.6점 |

> 위 수치는 예시다. `input_tokens`, `output_tokens`는 이미지 크기와 해상도에 따라 달라지므로  
> 반드시 실제 API 응답의 `usage` 값을 사용한다. `ocr_caller.py`가 자동으로 수집한다.

### 8-3. 성능 점수 (100점 만점)

| 세부 항목 | 배점 | 대상 필드 |
|---|---:|---|
| Critical 필드 추출률 | 50점 | `accident_datetime`, `accident_location`, `accident_type.value`, `accident_description` |
| Important 필드 추출률 | 25점 | `receipt_number`, `issue_number`, `police_station`, `accident_cause`, `damage.raw_text`, `usage` |
| 문서 판별 정확도 | 15점 | 5장 중 교통사고사실확인원으로 정상 판별된 비율 |
| 상태 판정 적절성 | 10점 | `success/partial/failed` 판단이 사람이 기대한 결과와 일치하는 비율 |

**Critical 필드가 가장 높은 이유**:  
이 4개 필드가 없으면 과실비율 Agent가 "어디서, 언제, 어떤 유형의, 어떤 내용의 사고인지"를 모른 채 분석해야 한다.  
나머지 Important 필드(접수번호, 발급번호 등)는 빠져도 과실비율 분석 자체는 돌아간다.

**성능 점수 계산 예시**:

```
Critical 추출:
  5장 × 4필드 = 20개 평가 항목
  정확 17개 + 부분 1개 + 오류 2개
  → (17 + 0.5) / 20 × 100 = 87.5점
  → Critical 세부 점수 = 87.5 × 0.50 = 43.75점

Important 추출:
  5장 × 6필드 = 30개 평가 항목
  추출 22개 + 누락 8개
  → 22 / 30 × 100 = 73.3점
  → Important 세부 점수 = 73.3 × 0.25 = 18.33점

문서 판별:
  5장 중 5장 정상 판별
  → 5 / 5 × 100 = 100점
  → 문서 판별 세부 점수 = 100 × 0.15 = 15점

상태 판정:
  5장 중 4장이 기대값(success/partial)과 일치
  → 4 / 5 × 100 = 80점
  → 상태 판정 세부 점수 = 80 × 0.10 = 8점

성능 점수 합계 = 43.75 + 18.33 + 15 + 8 = 85.08점
```

> **현재 자동화 수준**:  
> 필드 추출 여부(null 여부)는 자동 집계.  
> 추출된 값이 이미지와 정확히 일치하는지는 현재 수동 검증이 필요하다.  
> `partial credit(0.5점)`은 현재 자동으로 부여하지 않으며, 수동 확인 후 JSON 직접 수정 방식으로 반영한다.

### 8-4. 속도 점수

**가장 빠른 모델 = 100점**.

```
속도점수 = (가장 빠른 모델의 평균 처리시간) ÷ (해당 모델의 평균 처리시간) × 100
```

예시:

| 모델 | 평균 처리시간 | 속도 점수 |
|---|---:|---:|
| `gpt-4o-mini` | 1,200ms | 100.0점 |
| `gpt-5.4-nano` | 1,400ms | 85.7점 |
| `gpt-5.4-mini` | 1,800ms | 66.7점 |
| `gpt-4o` | 2,100ms | 57.1점 |
| `gpt-5.4` | 2,600ms | 46.2점 |

### 8-5. 안정성 점수

| 조건 | 점수 |
|---|---:|
| JSON 100% 성공, 재시도 없음, 경고 없음 | 100점 |
| JSON 100% 성공, 일부 warnings 있음 | 80점 |
| JSON 100% 성공, 1회 재시도 발생 | 70점 |
| JSON 실패 1회 이상 | Gate 탈락 (이 단계까지 오지 않음) |

## 9. 최종 결과 해석 — 어떻게 모델을 선택할 것인가

### 9-1. --report 출력 형태

```
======================================================================
  ■ 최종 모델 비교표
======================================================================
  모델             Gate   비용40%  성능45%  속도10%  안정5%  최종
  ----------------------------------------------------------------
  gpt-4o-mini      ✅     100.0    72.3     100.0    100.0   84.5
  gpt-5.4-mini     ✅      24.4    91.2      66.7    100.0   67.5
  gpt-5.4-nano     ✅      71.4    68.1      85.7    100.0   74.3
  gpt-4o           ✅       8.3    89.8      57.1    100.0   65.6
  gpt-5.4          ✅       5.6    95.4      46.2    100.0   65.2
======================================================================
```

위 표는 예시 수치다. 실제 값은 실행 후 채워진다.

### 9-2. 결과 해석 기준

**Step 1: Gate 탈락 모델 제거**  
Gate 탈락 모델은 표에 나오지만 최종 후보에서 제외한다. 이유 불문.

**Step 2: 최종점수 1위 모델 확인**  
최종점수가 가장 높은 모델을 1차 후보로 선정.

**Step 3: 다음 조건으로 교차 검토**

| 조건 | 판단 |
|---|---|
| 1위와 2위 최종점수 차이가 5점 이상 | 1위 모델 선택 |
| 1위와 2위 최종점수 차이가 5점 미만 | 1장당 비용이 낮은 모델 선택 |
| 1위 모델의 Critical 추출률이 80% 미만 | 성능 상위 모델로 재검토 |
| 고가 모델이 1위이지만 성능 차이가 10점 미만 | 저가 모델 선택 |

**Step 4: 사나리오별 판단 기준**

| 시나리오 | 결과 해석 | 선택 |
|---|---|---|
| `gpt-4o-mini`가 Critical 85% 이상이고 최종점수 1위 | 저렴한 모델이 충분한 성능. 비용 우선 전략 성공 | `gpt-4o-mini` 채택 |
| `gpt-5.4-mini`가 Critical 90% 이상, `gpt-4o-mini`는 70% 미만 | 품질 차이가 명확. 비용보다 안정성 | `gpt-5.4-mini` 채택 |
| `gpt-5.4-nano`가 작은 글자에서 자주 null 반환 | nano는 한글 소형 폰트 OCR에 부족 | nano 탈락, mini 이상으로 확정 |
| `gpt-5.4`가 최고 성능이지만 2위와 성능 차이 5점 미만 | 비용 대비 품질 차이 불충분 | 2위 모델 선택 |
| 모든 모델이 `accident_description` 자주 누락 | 사고내용은 긴 자유 텍스트. 모든 mini 계열 한계 | `gpt-5.4` 또는 프롬프트 개선 |
| 5개 모두 Critical 80% 미달 | 예상 외 상황. 프롬프트 문제 가능성도 있음 | `gpt-5.5` 추가 평가 + 프롬프트 검토 |

### 9-3. 주의사항

**비용 점수가 높다고 무조건 채택하지 않는다**:  
`gpt-4o-mini`는 비용 점수 100점이지만, Critical 추출률이 60%라면 운영 기본 모델로 사용할 수 없다.  
비용 점수 40%는 성능이 충분한 모델들 사이에서 비교할 때 의미가 있다.

**환각이 발견된 모델은 성능 점수와 무관하게 Gate에서 탈락**:  
아무리 다른 필드를 잘 뽑아도, Critical 필드에서 이미지에 없는 값을 만들어낸 모델은 제외한다.

**`gpt-4o`가 최신 5.4 계열보다 나올 수 있다**:  
한글 OCR은 모델 버전보다 학습 데이터 구성이 중요하다.  
`gpt-4o`가 한글 문서에서 더 안정적인 결과를 낼 가능성이 있으므로 결과를 보고 판단한다.

## 12. 비용 계산 공식 (참고)

```
1장당 비용(USD) =
  (input_tokens  / 1,000,000 × input_token_price)
+ (output_tokens / 1,000,000 × output_token_price)
```

이미지 크기와 `detail` 설정에 따라 `input_tokens`가 달라지므로  
추정값이 아닌 실제 API 응답의 `usage` 값을 사용한다.  
`eval/ocr_caller.py`의 `call_ocr_with_metrics()`가 자동으로 수집한다.

월 운영 비용 추정 (참고용):
```
월 처리량 1,000건 기준:
  gpt-4o-mini:  $0.0010 × 1,000 = $1.00   (약 1,400원)
  gpt-5.4-mini: $0.0041 × 1,000 = $4.10   (약 5,740원)
  gpt-5.4:      $0.0180 × 1,000 = $18.00  (약 25,200원)

※ 위 수치는 예시. 실제 1장당 비용은 실행 결과로 확인한다.
```
