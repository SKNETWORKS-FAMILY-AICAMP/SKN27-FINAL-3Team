# 과실비율 판례 텍스트 청킹(Chunking) 전략

과실비율 2차 검증을 통과한 1,006건의 '순도 100% 과실비율 판례'를 바탕으로, RAG(검색 증강 생성) 시스템의 검색 품질을 극대화하기 위한 데이터 청킹(Chunking) 계획입니다.

## 1. 판례 구조의 이해 및 접근 방식

판례는 일반 줄글과 달리 고유의 목차 구조(사건명, 주문, 이유 등)를 가집니다. 이를 무시하고 글자 수(Token) 단위로 자르면 핵심 문맥이 파괴되므로, **법원 판결문 구조 기반 세부 청킹(Hierarchical Structural Chunking)**을 적용합니다.

### 1.1 구조 기반 1차 분리 (Preprocessed Fields 활용)
전처리 단계에서 이미 분리된 JSON 필드(사건명, 판시사항, 주문, 청구취지, 이유 등)를 1차적으로 활용합니다.
*   **짧은 텍스트 필드 (메타데이터화):** `사건명`, `사건번호` 등 짧고 명확한 필드는 검색 보조용 메타데이터로 원형을 유지합니다.
*   **긴 텍스트 필드 (세부 청킹 대상):** `이유`(Reasoning), `판시사항` 등 텍스트가 긴 필드들은 내부적으로 목차 기호를 포함하고 있을 확률이 높으므로, 아래 1.2의 '목차 기호 기반 세부 청킹'을 공통으로 적용합니다. (특히 '이유' 섹션은 사고 경위와 과실 산정 논리가 담겨 있어 계층이 가장 깊고 길게 나타납니다.)

### 1.2 법원 판결문 목차 기호 기반 세부 청킹 (범용 적용)
'이유'를 비롯한 주요 텍스트 필드들을 정규식(Regex)을 이용해 법원 특유의 목차 계층 순서대로 트리(Tree) 형태로 쪼갭니다. 다른 섹션들도 목차 깊이만 얕을 뿐(예: `1.`, `2.` 까지만 존재) 동일한 순서 규칙을 따릅니다.

**분할 기준 목차 계층 (Hierarchical Regex Splitting):**
1.  대분류: `1.`, `2.`, `3.` ...
2.  중분류: `가.`, `나.`, `다.` ...
3.  소분류: `1)`, `2)`, `3)` ...
4.  세분류: `가)`, `나)`, `다)` ...
5.  추가분류: `(1)`, `(2)`, `(가)`, `(나)` ...

이 순서대로 정규식을 적용해 의미가 끊어지지 않는 논리적 단락 단위로 Chunk를 생성합니다.

### 1.3 초과 길이 단락 폴백 (Fallback Sentence Splitting)
위의 계층 구조로 끝까지 쪼갰음에도 특정 단락(예: `가)` 항목)이 임베딩 모델의 최대 토큰 길이를 초과하거나 너무 길어질 수 있습니다.
*   **문장 단위 분할:** 이 경우에는 한국어 문장 분리 라이브러리(예: `kss`)를 사용하여 문장 단위로 나눕니다.
*   **오버랩 (Overlap):** 문맥 단절을 방지하기 위해 앞뒤로 약 1~2문장(10~20%)을 겹치게(Overlap) 자릅니다.

### 1.4 핵심: 메타데이터 주입 (Metadata Injection)
잘게 쪼개진 텍스트 조각(Chunk)만으로는 해당 조각이 어떤 사고에 대한 결론인지 알 수 없는 **문맥 소실(Context Loss)**이 발생합니다.
이를 방지하기 위해 생성된 **모든 Chunk의 맨 앞에 원본 판례의 핵심 메타데이터를 강제로 텍스트로 주입**합니다.

*   **주입 전 Chunk:** "위와 같은 사정을 종합하여 피고의 책임을 70%로 제한함이 타당하다."
*   **주입 후 Chunk:** `[사건명: 구상금] [사건번호: 2022나1234] [사고유형: 신호없는 교차로 사고]` 위와 같은 사정을 종합하여 피고의 책임을 70%로 제한함이 타당하다.

이를 통해 임베딩 모델이 조각 자체만으로도 사고의 전체 문맥을 이해할 수 있게 되어 검색(Hit) 성능이 비약적으로 상승합니다.
