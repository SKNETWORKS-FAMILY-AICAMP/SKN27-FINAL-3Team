# 하이브리드 RAG 후속 실험 상세 액션 플랜

과실비율 RAG 시스템의 검색 품질을 극대화하기 위해, 기존 운영 중인 BM25 기반 검색을 "하이브리드(Hybrid) 검색"으로 고도화하는 4단계 실험 계획입니다.

## 1. 하이브리드 실험 4단계 액션 플랜

"어떤 모델이 좋은가?", "하이브리드가 진짜 좋은가?"를 완벽하게 통제된 변인 하에서 증명하기 위한 4단계 구체적 실행 계획입니다.

### Step 1. 기준점(Baseline) 세우기
새로운 기술이 기존 기술보다 얼마나 좋아졌는지 증명하기 위한 '비교용 채점판'을 만듭니다.
*   **사용 데이터:** `schema_search_test` 폴더에 생성된 100개의 가상 질문(Query) - 정답 판례(Document) 쌍.
*   **검색 엔진:** 기존에 운영 중인 **Elasticsearch (BM25 + Nori)**.
*   **평가 방식:** ES에서 검색해 온 상위 후보들을 **BGE-Reranker**에 통과시켜 `local_reranker_score`를 계산합니다.
*   **목표 산출물:** 기존 시스템의 `Hit@5` 점수 및 `Avg Top1` 점수 기록 (예: "우리 기존 시스템은 65점이다.")

### Step 2. 최우수 임베딩 모델 선발 (1024 차원 통일)
가장 똑똑한 의미 검색 모델을 찾습니다. 단, 차원수(데이터량) 때문에 성능이 좋아 보이는 착시를 막기 위해 **모든 후보를 1024 차원으로 통일(Apples-to-Apples)**하여 링에 올립니다.
*   **검색 엔진:** PostgreSQL (`pgvector` 단독 사용)
*   **비교 후보군 (모든 벡터를 1024로 고정):**
    1.  `text-embedding-3-small` (1536 -> 1024 축소)
    2.  `text-embedding-3-large` (3072 -> 1024 축소)
    3.  `BAAI/bge-m3` (기본 1024)
    4.  `multilingual-e5-large` (기본 1024)
*   **평가 방식:** Step 1과 똑같은 질문 100개, 똑같은 BGE-Reranker를 사용하여 점수를 매깁니다.
*   **목표 산출물:** 차원급을 떼고 순수하게 아키텍처가 가장 뛰어난 **최종 승자 모델 1개** 선정. (예: "승자는 text-embedding-3-large다!")

### Step 3. 승자 모델의 차원(Dimensionality) 최적화
Step 2에서 1등을 한 모델(예: `text-embedding-3-large`)을 대상으로, DB 용량과 검색 속도를 어디까지 타협할 수 있는지 테스트합니다.
*   **테스트 대상:**
    1.  원본 차원 (3072차원) - 정확도 최고, 속도 최하, 비용 최고
    2.  기본 축소 (1024차원) - 밸런스형
    3.  극한 축소 (256차원) - 정확도 최하, 속도 최고, 비용 최저
*   **평가 방식:** 동일한 Reranker 점수 비교.
*   **목표 산출물:** "3072차원과 256차원의 정확도(Hit@5) 차이가 고작 2%밖에 안 난다. DB 비용을 아끼기 위해 **256차원으로 최종 확정**한다!"와 같은 엔지니어링 의사결정.

### Step 4. 드림팀 결성 및 3자 최종 비교 (Cross-store Hybrid)
기존 키워드 챔피언(Step 1)과 의미 검색 챔피언(Step 3)을 마침내 합치고, 세 가지 방식의 장단점을 최종 비교합니다.
*   **검색 엔진:** Elasticsearch(BM25) + PostgreSQL(pgvector 승자 모델) 동시 검색.
*   **결합 방식:** 두 DB에서 나온 순위(Rank)를 **RRF (Reciprocal Rank Fusion)** 공식으로 합쳐 최종 순위를 만듭니다.
*   **최종 평가:** RRF로 합쳐진 상위 후보들을 BGE-Reranker에 넣어 최종 점수를 냅니다.
*   **최종 결론 (3자 비교 표 생성):** 
    1. 순수 키워드 검색 점수 (Step 1 결과)
    2. 순수 의미 검색 점수 (Step 3 결과)
    3. 하이브리드 검색 점수 (Step 4 결과)
    이 세 가지를 한눈에 비교하여, "각각 단독으로 썼을 때의 한계점과 결합했을 때의 시너지(Hit@5 폭발적 상승)"를 최종 리포트로 도출합니다!

## 2. 평가지표 및 평가 방식 (다각도 비교)
검색 시스템은 단순 정확도뿐만 아니라 운영 효율성도 중요합니다. 따라서 **'정확도 지표'**와 **'엔지니어링 지표'**를 나누어 평가합니다.

**A. 정확도 지표 (Quality Metrics)**
1.  **Hit@5:** 최종 정렬된 상위 5개 안에 정답 판례가 존재하는가. (순수 포획 능력)
2.  **Avg Top1 / Avg@5 Reranker Score:** BM25든 Vector든, 가져온 문서가 얼마나 질문과 관련이 깊은가 (리랭커 모델이 채점한 0~1 사이의 절대 점수).
3.  **승리 횟수 (Winner Count):** 100개의 질문 중 BM25가 더 높은 점수를 낸 횟수 vs Vector가 더 높은 점수를 낸 횟수. (서로 상호보완적인지 확인)

**B. 엔지니어링 지표 (Engineering Metrics)**
1.  **검색 지연시간 (Search Latency):** BM25 검색 시간 vs pgvector(HNSW/IVFFlat) 거리 계산 시간 비교.
2.  **색인/API 비용 (Cost):** 임베딩 모델별 1M 토큰당 과금액 또는 자체 서버(GPU) 유지 비용.
3.  **저장 공간 (Index Size):** 차원수(1024 vs 256)에 따른 PostgreSQL Vector Index 크기 변화 및 메모리 점유율.
