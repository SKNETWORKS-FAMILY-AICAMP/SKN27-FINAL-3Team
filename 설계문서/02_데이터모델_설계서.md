## 1. 개요

본 문서는 판단 Agent의 데이터 구조, 판정 로직에 쓰이는 열거형, State 스키마, RG×MG 조합 매트릭스,
검증 규칙을 정의한다. OCR Agent가 출력하는 필드(`notice_stage`, `opinion_deadline` 등)를 입력으로
그대로 받으며, 필드 의미는 DATA-002 §4-2 매트릭스를 따른다.

## 2. 핵심 열거형 (Enum)

### 2-1. JudgmentStatus (v2.0에서 2개 값 제거, v3.0에서 되살리지 않음)

| 값 | 의미 | 후속 처리 |
|----|------|---------|
| `"success"` | 판정 완료 (`verdict_node` 통과) | `overall_possibility`·`risk_flag` 활용 |
| `"denied"` | 기한 경과로 판정 자체가 "불가" | 가이드만 반환, 판정 필드 없음 |
| `"input_required"` | `user_appeal_reason` 누락 | Supervisor 재질문 요청 |
| `"not_applicable"` | 범칙금 — 이의신청서 생성 대상 아님 | 절차 안내 전용 가이드 반환 |

> v1.0에 있던 `"law_code_unverified"`(재확인 1회 요청)와 `"unable_to_verify"`(재확인 실패, 판단
> 종료)는 v2.0에서 law_code 검증 하드블록 자체가 제거되며 함께 삭제됐다. **v3.0에서 law_code
> 검증을 경량 형태로 복원했지만, 이 두 상태값은 되살리지 않는다** — 검증 실패가 `judgment_status`
> 자체를 바꾸지 않고 `law_code_verified` 필드(§3)로만 반영되기 때문이다. Supervisor 재호출을
> 유발하지 않는다는 게 v9 하드블록과의 핵심 차이다.

### 2-2. MeritLevel (MG 출력) — 변경 없음

| 값 | 의미 |
|----|------|
| `"강함"` | 참조 법조문(시행규칙 제142조 등)에 명확히 해당 |
| `"보류"` | 열거 목록엔 없으나 귀책없음 취지 또는 정황요소(질서위반행위규제법 제14조) 해당 가능성 |
| `"낮음"` | 참조 법조문과 명백히 무관 |

### 2-3. RiskFlag (RG 출력) — 변경 없음

| 값 | 의미 | 트리거 |
|----|------|--------|
| `true` | 신원노출 위험 있음 | 1단계 키워드 매칭 또는 2단계 LLM confidence 높음/애매 |
| `false` | 신원노출 위험 없음 | 2단계 LLM이 명확히 무관 판정 (confidence 낮음) |

> `risk_flag`와 별개로, `residual_risk_notice`(RG로 사전에 걸러낼 수 없는 절차상 잔여 리스크)는
> `risk_flag` 값과 무관하게 **과태료 판정 결과 전체에 항상 포함**된다 (⑥번 disclaimer 고정 문구).

### 2-4. OverallPossibility (E 출력, `judgment_status=success`일 때만 존재) — 변경 없음

| 값 | 사용 조건 |
|----|----------|
| `"의견_제출시_인정가능"` | `notice_stage=사전통지` |
| `"이의제기_인용가능"` | `notice_stage=1차 고지서` |

### 2-5. (v1.0에서 제거) ~~IssuingAuthorityType~~

발부기관 유형(경찰/지자체) 판별 자체가 v2.0에서 삭제됐다. 접수채널 안내가 발부기관 구분 없이 단일
문구("서면 원칙 + 관할 기관 직접 확인")로 통일됐기 때문이다.

## 3. LangGraph State 스키마 (v3.0)

```python
from typing import Optional
from typing_extensions import TypedDict, Literal

JudgmentStatus = Literal[
    "success", "denied", "input_required", "not_applicable",
]
MeritLevel     = Literal["강함", "보류", "낮음"]


class AppealJudgmentState(TypedDict, total=False):
    # ── OCR Agent 결과 (structured_result 평탄화 재사용) ─────────────
    fine_type:                          Optional[str]   # "과태료" | "범칙금"
    notice_stage:                       Optional[str]   # "사전통지" | "1차 고지서" | "즉결심판"
    violation_text:                     Optional[str]
    opinion_deadline:                   Optional[str]   # YYYY-MM-DD
    payment_deadline_2nd:               Optional[str]
    issuing_authority:                  Optional[str]   # 가이드 ③에 그대로 노출만 함 (판별 안 함)
    law_code:                           Optional[str]   # 용도 2가지 (v3.6): ① LDB_CHECK 경량 검증 → ⑥ disclaimer
                                                          # 조건부 문구, ② MG의 위반유형(주정차/비주정차) 판별
                                                          # 라우팅 신호 (인용 근거로는 안 씀, §5 참고)

    # ── Supervisor 공급 (OCR 결과에 없는 값) ─────────────────────────
    user_appeal_reason:                 Optional[str]
    notice_received_date:               Optional[str]   # YYYY-MM-DD, (v3.4) 확정 — OCR에 발송일 계열
                                                          # 필드 자체가 없어 user_appeal_reason과 동일하게
                                                          # Supervisor가 사용자에게 물어 공급. 1차 고지서
                                                          # 기산일(수령일+60일) 계산에 사용. ARCH-001 §9-3 참고.

    # ── law_code_check_node (LDB_CHECK) 출력 (v3.0 복원) ─────────────
    law_code_verified:                  Optional[bool]   # 실패해도 파이프라인은 계속 진행

    # ── deadline_gate_node 출력 ───────────────────────────────────────
    computed_deadline:                  Optional[str]    # notice_stage별 계산된 실제 기한
    deadline_passed:                    Optional[bool]

    # ── risk_classification_node(RG) 출력 ────────────────────────────
    risk_flag:                          Optional[bool]
    risk_stage_matched:                 Optional[str]    # "keyword" | "llm" | None
    risk_confidence:                    Optional[float]
    risk_trigger_category:              Optional[str]    # (v18) "A_제3자운전주장" | "B_명시적전환요청" |
                                                          # "C_본인운전인정형" | None. 여러 카테고리가
                                                          # 동시에 매치되면 A/B(무조건 위험) 우선 —
                                                          # guide_generation_node가 이 값으로 disclaimer
                                                          # 조건부 프레이밍(카테고리 C 전용) 적용 여부를 판단

    # ── merit_classification_node(MG) 출력 ───────────────────────────
    merit:                              Optional[MeritLevel]
    merit_basis:                        Optional[str]    # LLM이 근거로 인용한 조문 요약

    # ── verdict_node(E) 출력 ──────────────────────────────────────────
    judgment_status:                    Optional[JudgmentStatus]
    overall_possibility:                Optional[str]

    # ── guide_generation_node 출력 ────────────────────────────────────
    guide:                              Optional[dict]   # ①~⑥ 키를 갖는 dict

    # ── Supervisor 수신 ───────────────────────────────────────────────
    agent_results:                      dict
```

### v1.0 대비 제거된 필드

| 제거된 필드 | 제거 사유 |
|---|---|
| `law_code_reverification_attempted` | law_code 하드블록 재확인 절차 자체가 삭제 |
| `law_code_normalized`, `law_code_valid`, `law_code_fail_stage` | law_code 정규화·조회·검증 로직 삭제 |

## 4. RG × MG 조합 매트릭스 (verdict_node 핵심 로직) — v18: 혼합 트리거 처리 규칙 추가

| | risk_flag = false | risk_flag = true |
|---|---|---|
| **merit = 강함** | 가능성 높음, 리스크 없음 → 안심하고 진행 | **(v3.3 갱신)** 142조 계열 인정사유는 조건부 리스크 — 도로교통법 제160조4항 1호(부득이한 사유)가 인정되면 과태료 자체가 면제돼 위험이 실현되지 않지만, 인정되지 않으면 이미 드러난 운전자 신원 때문에 3호(운전자가 밝혀진 경우)가 적용돼 범칙금으로 전환될 수 있음. "표현 조정 권고"가 아니라 "성공 시 무위험 / 실패 시 전환 위험"이라는 조건부 구조로 고지 |
| **merit = 보류** | 판단 애매, 위험 없음 → 증거 보강 권유 | 판단도 애매하고 위험도 있음 → 신중한 톤, 전문가 상담 권유 |
| **merit = 낮음** | 인정 어려움, 위험 없음 → 기대치 낮춰 안내 | 승산 낮고 위험까지 있음 → 진행 재고 권고 |

- 두 값은 별도 필드로 출력되며 하나의 점수로 합산하지 않는다.
- 출력 순서는 항상 `risk_flag`를 `merit`보다 먼저 노출한다.
- **(v3.2)** RG에 "본인 운전 인정형" 트리거가 추가되면서 "강함×위험" 조합은 더 이상 예외가
  아니라 142조 계열 이의제기의 기본 결과다. 상세는 §8 참고.
- **(v3.3)** 다만 이 조합의 risk는 **1호(부득이한 사유) 주장이 실패했을 때만 실현**된다 — 1호와
  3호(운전자가 밝혀진 경우)가 서로 다른 독립 근거이기 때문이다. "risk=true"를 무조건 위험으로
  읽으면 안 된다.
- **(v18) 다만 이 조건부 프레이밍은 `risk_trigger_category = "C_본인운전인정형"`일 때만 정확하다.**
  사유 텍스트에 카테고리 A(제3자 운전 주장)나 B(명시적 전환 요청)가 **함께** 매치된 혼합
  사례(예: "다른 사람이 응급환자를 이송하다가 위반했다")에서는, 그 위험이 1호 실패를 전제로 하지
  않고 곧바로 3호(제3자 특정)로 이어질 수 있어 "성공 시 무위험" 프레이밍이 부정확해진다.
  `guide_generation_node`는 `risk_trigger_category`에 A 또는 B가 포함되면 조건부 문구 대신
  무조건 위험 경고를 우선 적용하고, C만 단독으로 매치됐을 때만 조건부 구조를 쓴다.

## 5. notice_stage별 판단 기준 매핑 (MG 컨텍스트 주입 규칙) — v3.8: 도난 사유 반영

| notice_stage | 위반유형 | 판단 성격 | MG가 LLM에 주입하는 법조문 |
|---|---|---|---|
| 사전통지 | 주정차 위반 (`law_code`가 도로교통법 제32~34조) | 의견제출 (질서위반행위규제법 제16조) | **도로교통법 제160조4항1호 본문**(v3.8 추가, "차를 도난당하였거나") + 시행규칙 제142조 열거 목록 원문 |
| 사전통지 | **비주정차 위반 (그 외, v3.6 신설)** | 의견제출 (질서위반행위규제법 제16조) | **질서위반행위규제법 제7조**(고의 또는 과실이 없는 질서위반행위는 과태료를 부과하지 아니한다 — 도난도 이 원칙에 포함) |
| 1차 고지서 | 주정차 위반 | 정식 이의제기 (비송사건절차) | 제160조4항1호 본문 + 시행규칙 제142조 + 질서위반행위규제법 제14조(동기·목적·방법·결과, 태도와 정황, 연령·재산상태·환경) |
| 1차 고지서 | **비주정차 위반 (v3.6 신설)** | 정식 이의제기 (비송사건절차) | **질서위반행위규제법 제7조** + 제14조(정황요소는 위반유형과 무관하게 동일 적용) |

**(v3.8 추가) 도난은 142조 목록이 아니라 제160조4항1호 본문에 있다**: "차를 도난당하였거나 그
밖의 부득이한 사유"에서 "도난"과 "부득이한 사유"는 병렬 규정이다. 142조는 "부득이한 사유" 6개
항목만 정의하므로, 142조 목록만 주입하면 도난 사례를 놓칠 수 있다. 주정차 위반 케이스에는
제160조4항1호 본문 자체도 함께 주입해야 "차를 도둑맞아서 도둑이 운전했다"류 사유를 `merit=강함`
으로 정확히 잡는다. 비주정차 위반은 제7조가 이미 도난을 포함하는 일반 원칙이라 별도 조치가
필요 없다.

**(v3.6 해소) 시행규칙 제142조 적용범위 문제**: 제142조는 도로교통법 제160조 제3항(제32조~
제34조, 주정차·정차 위반)에서 위임된 조항이라 **주정차 위반 과태료에 한정**된다. 비주정차
위반(과속·신호위반 등 무인단속)에 대한 사전통지 단계 근거로는 **질서위반행위규제법 제7조**를
쓴다 — 위반유형과 무관하게 모든 과태료(질서위반행위)에 보편 적용되는 일반 원칙("고의·과실이
없으면 과태료를 부과하지 않는다")이라, 도로교통법에 해당 위반유형별 특칙(142조 같은)이 없는
경우 이 일반법 조항이 보충 적용된다. 제7조는 이미 §9 법령DB 참조 조항 목록에 "MG 2차 참고"로
동기화 대상에 있었으나 이 매핑표에는 연결이 안 돼 있었다 — 이번에 연결한다.

**위반유형 판별 방법**: 새 필드나 별도 분류 로직 없이, OCR이 이미 추출하는 `law_code` 필드가
도로교통법 제32조·제33조·제34조(주정차·정차 금지)에 해당하는지 정규식으로 매칭해 분기한다.
`법조문_참고자료_142조_14조.md`, ARCH-001 §9-2 참고.

`MG`는 v1.0의 "1단계 키워드 매칭 → 2단계 LLM" 구조에서 **v1.0 후반에 이미 "LLM 단일 호출"로
단순화**됐고, v2.0에서는 이 구조 자체는 그대로 유지된다 (이번 축소는 law_code·채널·벌점 쪽만
해당하며 MG의 판정 로직 자체는 건드리지 않았다).

## 6. 기한 계산 규칙 (deadline_gate_node) — v3.9: notice_stage별 실행 순서 분기

| notice_stage | 기산일 | 기한 | 계산 방식 |
|---|---|---|---|
| 사전통지 | 사전통지서 수령일 | 10일 이상 | `opinion_deadline` 필드 그대로 사용 (별도 필드 불필요) |
| 1차 고지서 | 고지서 수령일 | 법정 60일 고정 | ⚠️ `opinion_deadline`(인쇄된 납부기한)과 별도로 `notice_received_date + 60일`을 직접 계산 |

**(v3.4 해소)** `notice_received_date`는 OCR이 추출하는 값이 아니라 **Supervisor가
`user_appeal_reason`과 동일한 방식으로 사용자에게 물어 공급하는 필드**로 확정됐다 —
`fine_notice_analysis`(OCR Agent) 실제 코드에 발송일 계열 필드 자체가 없다는 게 확인됐기
때문이다. `reason_intake_node`가 사유와 함께 이 값도 같이 요청하도록 확장한다 (ARCH-001 §9-3
참고). 고지서에 인쇄된 "발송연월일"을 OCR이 추출해 자동 계산하는 방안은 장기 백로그로 남긴다.

**⚠️ (v3.9 해소) 1차 고지서에서 `deadline_gate_node`의 실행 순서 문제**: `notice_received_date`가
Supervisor 공급 필드로 확정되면서, 1차 고지서의 `deadline_gate_node`는 이 필드 없이는 계산 자체가
불가능해졌다. 그런데 기존 순서는 `deadline_gate_node`(=`DCHK`)가 `reason_intake_node`보다
먼저였다 — 값을 확인하는 노드보다 그 값을 쓰는 노드가 먼저 실행되는 순서 모순이었다. **해결**:
1차 고지서 경로만 `law_code_check_node → reason_intake_node(사유+수령일 확인) →
deadline_gate_node` 순으로 재배치했다. 사전통지는 `opinion_deadline`이 OCR 필드라 기존 순서
(`deadline_gate_node`가 맨 먼저) 그대로 유지한다. 상세는 §7, ARCH-001 §9-7 참고.

`computed_deadline < 오늘` 이면 `deadline_passed=true`, `judgment_status=denied`로 즉시 종료하고
`risk_classification_node`/`merit_classification_node`는 실행하지 않는다.

## 7. law_code 처리 방식 (v3.0 — 경량 검증으로 복원)

v1.0에서는 정규화→조회→하드블록(재확인 1회 → 실패시 종료)까지 있었으나, v2.0에서 "판정에 기여하지
않는다"는 이유로 전부 제거했다. **v3.0에서 그 판단을 재검토했다** — law_code 데이터는 팀의 법령DB
파이프라인이 이미 자동으로 최신 상태를 유지해주므로, 추가 유지관리 비용이 사실상 0이다. 판정에
기여하지 않는다는 사실 자체는 여전히 유효하지만, 유지비용이 0이라면 문서 품질(정확한 법조항 인용)
목적으로 가볍게 검증할 가치가 있다고 재평가했다.

### `law_code_check_node` (LDB_CHECK) 동작 방식

| 단계 | 규칙 | 결과 |
|---|---|---|
| 조회 | `law_code`를 법령DB 캐시에서 단일 조회 (재시도 없음) | `law_code_verified = true/false` |
| 실패 시 | **파이프라인을 막지 않는다** | 판정(`E`)은 그대로 진행되고, `law_code_verified=false`만 기록 |
| 가이드 반영 | ⑥번 disclaimer 문구를 조건부로 변경 | `true`면 가벼운 확인 문구, `false`면 "원본과 대조해 직접 확인하라"는 구체적 경고 |

v9 하드블록과의 핵심 차이는 **재확인 루프와 Supervisor 왕복이 없다**는 것이다. 검증에 실패해도
Supervisor를 다시 부르지 않고, 한 번의 결과를 그대로 가이드에 반영하고 끝낸다.

**(v3.9) 1차 고지서 경로에서는 이 노드가 맨 먼저 실행된다**: `law_code`는 어느 notice_stage든
OCR이 이미 제공하는 필드라 다른 값에 의존하지 않는다. 1차 고지서 경로는 `deadline_gate_node`가
Supervisor 공급 필드(`notice_received_date`) 없이는 실행 불가능해서 뒤로 밀려났기 때문에(§6
참고), `law_code_check_node`가 자연스럽게 맨 앞으로 온다. 덕분에 `input_required`로 돌아갈
때도 `law_code_verified`를 `partial_result`에 계속 포함할 수 있다 (다만 `computed_deadline`은
이 시점엔 계산 전이라 포함 못 한다 — 사전통지 경로의 `input_required`와 다른 점).

> OCR Agent 측 `_LAW_CODE_RE` 정규식(V-04)은 "법조문처럼 생겼는지"만 확인하는 형식 검증이며,
> `LDB_CHECK`는 실제 법령DB 조회로 존재 여부까지 확인한다는 점에서 더 엄격하다. `law_code`가
> `null`인 경우는 OCR Agent의 `CRITICAL_FIELDS` 판정에서 이미 `partial`로 걸러지므로 본 Agent에
> 도달하지 않는다 (즉결심판 서식 제외 — 범칙금 트랙이라 `LDB_CHECK` 자체를 거치지 않음).

## 8. RG 분류 규칙 (risk_classification_node) — v18: risk_trigger_category 출력 추가

| 단계 | 방식 | 출력 |

| 0단계 (v3.8 신설) | **도난 예외 체크 — 카테고리 A보다 먼저 실행.** "도둑", "도난", "훔쳐서", "차를 도둑맞아" 등 도난 관련 키워드 매칭 | 매칭 시 즉시 `risk_flag=false`, `risk_trigger_category=None`. **A/B/C 판단으로 넘어가지 않고 종료** |

**(v3.8) 왜 도난이 0단계(최우선)인가**: "도둑이 운전했다"는 표면적으로 카테고리 A 키워드와

않는다 — 카테고리 A는 성공/실패 무관하게 "밝혀진 특정 운전자"가 즉시 생기지만, 도난은 성공하면
아예 처분 불가로 끝나고 실패해도 특정된 운전자가 없어 3호가 적용될 근거 자체가 없다. 그래서
카테고리 A 판정보다 먼저 도난 여부를 체크해 걸러낸다. 상세는 `법조문_참고자료_142조_14조.md`
"도난은 별도 사유다" 절 참고.

**(v18) `risk_trigger_category`를 두는 이유**: E/가이드 단계에서 카테고리 C 특유의 조건부
disclaimer 프레이밍("성공 시 무위험/실패 시 전환 위험")을 적용할지 판단하려면 어느 카테고리가
매치됐는지 알아야 한다. A·B는 이런 조건부 구조가 없는 직접적 위험이므로, A/B가 매치되면
무조건 위험 경고를 우선 적용하고 C는 그 경고에 덧붙이는 정도로만 참고한다 (§4 참고).

**(v3.5 해소) 카테고리 C 표현 범위 확정**: 트리거 기준은 "142조 문구 매칭"이 아니라
**"화자 본인이 위반 당시 운전자였음을 전제로 정황을 설명하는 진술 전반"**이다 — 142조 문구로만
한정하면 1차 고지서 단계의 질서위반행위규제법 제14조 정황요소(동기·목적·방법·결과, 태도,

RG도 동일하게 읽는 것 — RG·MG 독립성 유지).
