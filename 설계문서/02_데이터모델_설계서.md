## 1. 개요

본 문서는 판단 Agent의 데이터 구조, 판정 로직에 쓰이는 열거형, State 스키마, RG×MG 조합 매트릭스,
검증 규칙을 정의한다. OCR Agent가 출력하는 필드(`notice_stage`, `opinion_deadline` 등)를 입력으로
그대로 받으며, 필드 의미는 DATA-002 §4-2 매트릭스를 따른다.

## 2. 핵심 열거형 (Enum)

### 2-1. JudgmentStatus (v2.0에서 2개 값 제거, v3.0에서 되살리지 않음)

| 값 | 의미 | 후속 처리 |
|----|------|---------|
| `"success"` | 판정 완료 (`verdict_node` 통과) | `overall_possibility`·`risk_flag` 활용 |
| `"denied"` | 기한 경과로 판정 자체가 "불가" | 가이드만 반환, 판정 필드 없음 |
| `"input_required"` | `user_appeal_reason` 누락 | Supervisor 재질문 요청 |
| `"not_applicable"` | 범칙금 — 이의신청서 생성 대상 아님 | 절차 안내 전용 가이드 반환 |

> v1.0에 있던 `"law_code_unverified"`(재확인 1회 요청)와 `"unable_to_verify"`(재확인 실패, 판단
> 종료)는 v2.0에서 law_code 검증 하드블록 자체가 제거되며 함께 삭제됐다. **v3.0에서 law_code
> 검증을 경량 형태로 복원했지만, 이 두 상태값은 되살리지 않는다** — 검증 실패가 `judgment_status`
> 자체를 바꾸지 않고 `law_code_verified` 필드(§3)로만 반영되기 때문이다. Supervisor 재호출을
> 유발하지 않는다는 게 v9 하드블록과의 핵심 차이다.

### 2-2. MeritLevel (MG 출력) — 변경 없음

| 값 | 의미 |
|----|------|
| `"강함"` | 참조 법조문(시행규칙 제142조 등)에 명확히 해당 |
| `"보류"` | 열거 목록엔 없으나 귀책없음 취지 또는 정황요소(질서위반행위규제법 제14조) 해당 가능성 |
| `"낮음"` | 참조 법조문과 명백히 무관 |

### 2-3. RiskFlag (RG 출력) — 변경 없음

| 값 | 의미 | 트리거 |
|----|------|--------|
| `true` | 신원노출 위험 있음 | 1단계 키워드 매칭 또는 2단계 LLM confidence 높음/애매 |
| `false` | 신원노출 위험 없음 | 2단계 LLM이 명확히 무관 판정 (confidence 낮음) |

> `risk_flag`와 별개로, `residual_risk_notice`(RG로 사전에 걸러낼 수 없는 절차상 잔여 리스크)는
> `risk_flag` 값과 무관하게 **과태료 판정 결과 전체에 항상 포함**된다 (⑥번 disclaimer 고정 문구).

### 2-4. OverallPossibility (E 출력, `judgment_status=success`일 때만 존재) — 변경 없음

| 값 | 사용 조건 |
|----|----------|
| `"의견_제출시_인정가능"` | `notice_stage=사전통지` |
| `"이의제기_인용가능"` | `notice_stage=1차 고지서` |

### 2-5. (v1.0에서 제거) ~~IssuingAuthorityType~~

발부기관 유형(경찰/지자체) 판별 자체가 v2.0에서 삭제됐다. 접수채널 안내가 발부기관 구분 없이 단일
문구("서면 원칙 + 관할 기관 직접 확인")로 통일됐기 때문이다.

## 3. LangGraph State 스키마 (v3.0)

```python
from typing import Optional
from typing_extensions import TypedDict, Literal

JudgmentStatus = Literal[
    "success", "denied", "input_required", "not_applicable",
]
MeritLevel     = Literal["강함", "보류", "낮음"]


class AppealJudgmentState(TypedDict, total=False):
    # ── OCR Agent 결과 (structured_result 평탄화 재사용) ─────────────
    fine_type:                          Optional[str]   # "과태료" | "범칙금"
    notice_stage:                       Optional[str]   # "사전통지" | "1차 고지서" | "즉결심판"
    violation_text:                     Optional[str]
    opinion_deadline:                   Optional[str]   # YYYY-MM-DD
    payment_deadline_2nd:               Optional[str]
    issuing_authority:                  Optional[str]   # 가이드 ③에 그대로 노출만 함 (판별 안 함)
    law_code:                           Optional[str]   # LDB_CHECK가 경량 검증, ⑥ disclaimer 조건부 문구에 사용

    # ── Supervisor 공급 (OCR 결과에 없는 값) ─────────────────────────
    user_appeal_reason:                 Optional[str]

    # ── law_code_check_node (LDB_CHECK) 출력 (v3.0 복원) ─────────────
    law_code_verified:                  Optional[bool]   # 실패해도 파이프라인은 계속 진행

    # ── deadline_gate_node 출력 ───────────────────────────────────────
    computed_deadline:                  Optional[str]    # notice_stage별 계산된 실제 기한
    deadline_passed:                    Optional[bool]

    # ── risk_classification_node(RG) 출력 ────────────────────────────
    risk_flag:                          Optional[bool]
    risk_stage_matched:                 Optional[str]    # "keyword" | "llm" | None
    risk_confidence:                    Optional[float]

    # ── merit_classification_node(MG) 출력 ───────────────────────────
    merit:                              Optional[MeritLevel]
    merit_basis:                        Optional[str]    # LLM이 근거로 인용한 조문 요약

    # ── verdict_node(E) 출력 ──────────────────────────────────────────
    judgment_status:                    Optional[JudgmentStatus]
    overall_possibility:                Optional[str]

    # ── guide_generation_node 출력 ────────────────────────────────────
    guide:                              Optional[dict]   # ①~⑥ 키를 갖는 dict

    # ── Supervisor 수신 ───────────────────────────────────────────────
    agent_results:                      dict
```

### v1.0 대비 제거된 필드

| 제거된 필드 | 제거 사유 |
|---|---|
| `law_code_reverification_attempted` | law_code 하드블록 재확인 절차 자체가 삭제 |
| `law_code_normalized`, `law_code_valid`, `law_code_fail_stage` | law_code 정규화·조회·검증 로직 삭제 |
| `issuing_authority_type`, `online_channel`, `channel_verified` | 발부기관 판별·접수채널 화이트리스트 삭제 |

## 4. RG × MG 조합 매트릭스 (verdict_node 핵심 로직) — 변경 없음

| | risk_flag = false | risk_flag = true |
|---|---|---|
| **merit = 강함** | 가능성 높음, 리스크 없음 → 안심하고 진행 | 사유는 인정될 만하나 표현 방식이 운전자 특정형 → 문구 조정 권고 |
| **merit = 보류** | 판단 애매, 위험 없음 → 증거 보강 권유 | 판단도 애매하고 위험도 있음 → 신중한 톤, 전문가 상담 권유 |
| **merit = 낮음** | 인정 어려움, 위험 없음 → 기대치 낮춰 안내 | 승산 낮고 위험까지 있음 → 진행 재고 권고 |

- 두 값은 별도 필드로 출력되며 하나의 점수로 합산하지 않는다.
- 출력 순서는 항상 `risk_flag`를 `merit`보다 먼저 노출한다.

## 5. notice_stage별 판단 기준 매핑 (MG 컨텍스트 주입 규칙) — 변경 없음

| notice_stage | 판단 성격 | MG가 LLM에 주입하는 법조문 |
|---|---|---|
| 사전통지 | 의견제출 (질서위반행위규제법 제16조) | 시행규칙 제142조 열거 목록 원문 |
| 1차 고지서 | 정식 이의제기 (비송사건절차) | 시행규칙 제142조 + 질서위반행위규제법 제14조(동기·목적·방법·결과, 태도와 정황, 연령·재산상태·환경) |

`MG`는 v1.0의 "1단계 키워드 매칭 → 2단계 LLM" 구조에서 **v1.0 후반에 이미 "LLM 단일 호출"로
단순화**됐고, v2.0에서는 이 구조 자체는 그대로 유지된다 (이번 축소는 law_code·채널·벌점 쪽만
해당하며 MG의 판정 로직 자체는 건드리지 않았다).

## 6. 기한 계산 규칙 (deadline_gate_node) — 변경 없음

| notice_stage | 기산일 | 기한 | 계산 방식 |
|---|---|---|---|
| 사전통지 | 사전통지서 수령일 | 10일 이상 | `opinion_deadline` 필드 그대로 사용 |
| 1차 고지서 | 고지서 수령일 | 법정 60일 고정 | ⚠️ `opinion_deadline`(인쇄된 납부기한)과 별도로 **수령일+60일**을 직접 계산 |

`computed_deadline < 오늘` 이면 `deadline_passed=true`, `judgment_status=denied`로 즉시 종료하고
`risk_classification_node`/`merit_classification_node`는 실행하지 않는다.

## 7. law_code 처리 방식 (v3.0 — 경량 검증으로 복원)

v1.0에서는 정규화→조회→하드블록(재확인 1회 → 실패시 종료)까지 있었으나, v2.0에서 "판정에 기여하지
않는다"는 이유로 전부 제거했다. **v3.0에서 그 판단을 재검토했다** — law_code 데이터는 팀의 법령DB
파이프라인이 이미 자동으로 최신 상태를 유지해주므로, 추가 유지관리 비용이 사실상 0이다. 판정에
기여하지 않는다는 사실 자체는 여전히 유효하지만, 유지비용이 0이라면 문서 품질(정확한 법조항 인용)
목적으로 가볍게 검증할 가치가 있다고 재평가했다.

### `law_code_check_node` (LDB_CHECK) 동작 방식

| 단계 | 규칙 | 결과 |
|---|---|---|
| 조회 | `law_code`를 법령DB 캐시에서 단일 조회 (재시도 없음) | `law_code_verified = true/false` |
| 실패 시 | **파이프라인을 막지 않는다** | 판정(`E`)은 그대로 진행되고, `law_code_verified=false`만 기록 |
| 가이드 반영 | ⑥번 disclaimer 문구를 조건부로 변경 | `true`면 가벼운 확인 문구, `false`면 "원본과 대조해 직접 확인하라"는 구체적 경고 |

v9 하드블록과의 핵심 차이는 **재확인 루프와 Supervisor 왕복이 없다**는 것이다. 검증에 실패해도
Supervisor를 다시 부르지 않고, 한 번의 결과를 그대로 가이드에 반영하고 끝낸다.

> OCR Agent 측 `_LAW_CODE_RE` 정규식(V-04)은 "법조문처럼 생겼는지"만 확인하는 형식 검증이며,
> `LDB_CHECK`는 실제 법령DB 조회로 존재 여부까지 확인한다는 점에서 더 엄격하다. `law_code`가
> `null`인 경우는 OCR Agent의 `CRITICAL_FIELDS` 판정에서 이미 `partial`로 걸러지므로 본 Agent에
> 도달하지 않는다 (즉결심판 서식 제외 — 범칙금 트랙이라 `LDB_CHECK` 자체를 거치지 않음).

## 8. RG 분류 규칙 (risk_classification_node) — 변경 없음

| 단계 | 방식 | 출력 |
|---|---|---|
| 1단계 | 고신뢰 키워드 매칭 (예: "제가 운전 안 했어요", "다른 사람이 몰았어요", "범칙금으로 전환") | 매칭 시 즉시 `risk_flag=true`, `risk_stage_matched="keyword"` |
| 2단계 | 1단계 미매칭 시 LLM 구조화 분류 (`is_identity_related`, `confidence`) | `confidence` 높음/애매 → `risk_flag=true`, 낮음 → `risk_flag=false` |

재현율 우선 원칙: 애매한 구간은 보수적으로 `risk_flag=true` 처리. MG와 달리 RG는 v2.0에서도
2단계 구조를 그대로 유지한다 (놓쳤을 때 실제 불이익으로 이어지는 안전 문제이기 때문).

## 9. 법령DB 참조 조항 목록 (v3.0)

| 조항/데이터 | 용도 | 조회 방식 |
|---|---|---|
| 질서위반행위규제법 제7조 | MG 2차 참고 (고의·과실 없음) | 배치 동기화 (크론잡) |
| 질서위반행위규제법 제14조 | MG 1차 고지서 단계 정황요소 | 배치 동기화 |
| 질서위반행위규제법 제16조 | 사전통지·의견제출 절차 근거 | 배치 동기화 |
| 질서위반행위규제법 제17조 | MG 2차 참고 (연령·재산상태·환경 감경) | 배치 동기화 |
| 질서위반행위규제법 제20조 | 정식 이의제기 60일 기한 근거 | 하드코딩 상수, 별도 수동 검토 |
| 도로교통법 제160·161·163조 | 과태료·범칙금 부과 근거 | 배치 동기화 |
| 도로교통법 시행규칙 제142조 | MG 1차 소스 (부득이한 사유 열거) | 배치 동기화 |
| **개별 고지서 `law_code`** | **(v3.0 복원) `LDB_CHECK`의 경량 검증 대상** | **요청 시 단일 조회 (재시도 없음)** |
| ~~도로교통법 시행규칙 별표28 (벌점 기준표)~~ | `ZP`가 쓰려던 데이터 | **대기 — API 응답이 파싱 가능한 구조화 텍스트인지 미확인, 동기화 대상 아님** |

동기화 정책(캐시 범위, 크론 주기, 폴백)은 ARCH-001 v3.0의 팀 파이프라인 재사용 원칙을 따른다.
v1.0의 하드블록에 있던 재확인 루프는 v3.0에서도 되살리지 않았다 — `LDB_CHECK`는 실시간 단일
조회이지 배치 동기화 대상이 아니다.
